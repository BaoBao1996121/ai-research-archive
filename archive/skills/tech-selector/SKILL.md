# Tech Selector Skill

> 给定一个技术选型问题，系统性地收集约束、枚举候选、多维度对比、淘汰不可行项，最终输出明确推荐而非一堆选项让用户自己挑。

### Overview

技术选型是研究工作中最高频的决策场景。好的选型不是"把 10 个方案都列出来"，而是帮用户**快速排除不可行的、聚焦到 1-2 个值得深入的**。

本 Skill 从本工作区 5 次独立选型实践中提炼（知识库检索×9方案、部署方案×9级、评估方案×10、漂移防御×10、自迭代×10），将反复出现的"约束收集 → 候选枚举 → 淘汰筛 → 深度对比 → 决策树"模式固化为可复用流程。

核心理念：**技术可行但经济不可行 = 不可行；功能强大但团队用不了 = 不可行。** 选型不是技术秀，是约束条件下的最优匹配。

## 1. 触发条件

当用户提出以下类型的请求时激活此 Skill：
- "帮我选一个 XX 工具/框架"
- "A 和 B 哪个好？"
- "做 XX 用什么方案？"
- "对比一下这几个选择"
- 提供了多个候选技术，期望得到推荐
- 任何隐含"从多个选项中挑一个"的需求

## 2. 执行流程

### Phase 1: 约束画像（Constraint Profiling）

在列举任何候选方案**之前**，先搞清楚约束条件。因为约束决定了哪些方案根本不用看。

#### 必须确认的六个维度

向用户确认以下信息（如果用户未主动说明）：

| 维度 | 要问的问题 | 为什么重要 |
|------|-----------|-----------|
| **场景** | 具体要解决什么问题？当前方案（如有）哪里不行？ | 避免"想要更快的马"陷阱 |
| **规模** | 数据量/用户量/调用频次大概什么量级？ | 小规模和大规模的最优解往往完全不同 |
| **预算** | 可接受的成本范围？（含 API 费用、人力、运维） | 淘汰经济不可行的方案 |
| **团队** | 团队技术栈？有多少人？AI/ML 经验如何？ | 淘汰团队执行不了的方案 |
| **基础设施** | 已有什么？（云服务/自建服务器/本地开发） | 排除不兼容的方案 |
| **时间** | 多久需要上线？是 PoC 还是生产？ | PoC 和生产的选型标准差别巨大 |

**简化规则**：如果用户明确只是做技术调研（非实际选型），可以跳过预算和时间维度，但场景和规模必须确认。

### Phase 2: 候选枚举（Candidate Enumeration）

这一步执行信息搜集协议（Gather），不能仅凭记忆：

1. **先查已有报告** — 检索 KNOWLEDGE_INDEX.md 和 reports/ 中是否已有相关选型结论
2. **再搜外部信息** — GitHub Stars/活跃度、官方文档、社区评价、第三方 Benchmark
3. **枚举 5-10 个候选** — 每个用一句话说清楚"它是什么、核心卖点是什么"

输出格式：

```markdown
### 候选方案速览

| # | 方案 | 一句话描述 | Stars/成熟度 | 核心卖点 |
|---|------|-----------|-------------|---------|
| 1 | XX   | ...       | ...         | ...     |
| ...                                            |
```

#### 2.5 完备性反查（Completeness Reverse-Check）

枚举完候选后，**在进入淘汰之前**，用以下三问做逆向检查——确保候选池没有结构性盲区：

```
□ 该领域的 Top 5 厂商/平台各自有对应产品吗？（大厂反查）
  → 列出头部玩家，逐一确认是否已在候选池中
□ 有没有"模型绑定型"或"生态绑定型"产品被隐含过滤掉？
  → 比如只搜"通用跨模型框架"会漏掉 Claude Agent SDK（绑定Claude）、MAF（绑定Azure）
□ 有没有最近 6 个月更名/重组的项目被旧名遮蔽？
  → 比如 AutoGen → MAF，搜旧名找不到新产品
```

**为什么需要这一步**：正向搜索天然偏向通用、高 SEO 的项目。生态绑定型、新更名型产品在搜索结果中排名低但可能是特定约束下的最优解。30 秒的反查能堵住这个盲区。

如果反查发现遗漏，补充到候选表后再进入 Phase 3。

### Phase 3: 快速淘汰（Kill Round）

这是选型中**最有价值的一步**——不是找最好的，而是先排除不行的。

对每个候选进行三重检验：

| 检验 | 标准 | 淘汰示例 |
|------|------|---------|
| **技术可行性** | 能不能解决核心问题？有没有硬性技术限制？ | "不支持中文" → 淘汰 |
| **经济可行性** | 在目标规模下成本可接受吗？ | "日均10万调用 × $0.01 = $1K/天" → 看预算 |
| **执行可行性** | 团队能不能用起来？学习曲线多陡？ | "需要 Kubernetes 集群但团队没有" → 淘汰 |

**淘汰要给理由**。被淘汰的方案不是坏方案，只是在当前约束下不合适。条件变了可能就是最优解。

输出格式：

```markdown
### 淘汰结果

| 方案 | 结果 | 原因 |
|------|------|------|
| XX   | ❌ 淘汰 | 经济不可行：月成本 $30K 超预算 10 倍 |
| YY   | ❌ 淘汰 | 技术不可行：不支持流式输出 |
| ZZ   | ✅ 进入深度对比 | — |
| ...  |      |      |

存活方案：N 个（建议 2-4 个）
```

### Phase 4: 深度对比矩阵（Deep Comparison）

对存活方案做多维度对比。维度根据场景选择，但以下是高频通用维度：

| 维度类别 | 常见维度 |
|---------|---------|
| **功能** | 核心功能覆盖度、独特能力、局限性 |
| **性能** | 延迟、吞吐、准确率（有 Benchmark 数据最好） |
| **成本** | 初始成本、运行成本、规模化成本曲线 |
| **工程** | 文档质量、社区活跃度、集成难度、维护成本 |
| **生态** | 插件/扩展生态、与已有工具链的兼容性 |
| **风险** | 供应商锁定、项目活跃度、License |

对比矩阵格式：
```markdown
| 维度 | 方案 A | 方案 B | 方案 C | 胜出 |
|------|--------|--------|--------|------|
| 功能 | ...    | ...    | ...    | B    |
| 性能 | ...    | ...    | ...    | A    |
| 成本 | ...    | ...    | ...    | C    |
| ...  |        |        |        |      |
```

### Phase 5: 决策输出（Decision）

最终输出必须包含：

1. **明确推荐**（不是"看你需求"，而是"推荐 X，因为 Y"）
2. **决策树**（用 Mermaid 或条件列表，让读者根据自己的细节条件微调）
3. **风险提示**（推荐方案的最大风险是什么，什么时候需要换方案）

```markdown
### 推荐

**首选：方案 X**
- 推荐理由：（2-3 句话）
- 最大风险：（1 句话）
- 适用条件：（什么情况下这个推荐成立）

**备选：方案 Y**
- 什么时候选它：（X 不适用时的替代条件）

### 决策参考

如果你的情况是 A → 选 X
如果你的情况是 B → 选 Y  
如果你的情况是 C → 先做 PoC 再决定
```

## 3. 质量标准

一个好的选型报告应该让读者在 30 秒内知道"该选什么"，在 5 分钟内知道"为什么"，在 30 分钟内能自己做出微调决策。

- **有推荐、有理由** — 不甩一堆选项让用户自己挑
- **有淘汰、有解释** — 被排除的方案说清楚为什么（条件变了可能重新考虑）
- **有成本估算** — 至少粗估量级（$10/月 vs $1K/月 vs $10K/月）
- **有数据支撑** — 对比维度尽量有数字（Stars、Benchmark、延迟），没有的标"待验证"
- **信息来源标注** — 关键事实标注来源（URL + 日期），避免过时信息误导决策

## 4. 反模式

以下是选型报告中常见的"看起来有用、实际没帮助"的模式：

| 反模式 | 为什么是问题 | 正确做法 |
|--------|------------|---------|
| 列了 10 个方案但没推荐 | 信息过载，决策瘫痪 | 淘汰到 2-3 个，明确推荐 |
| "各有优劣，看需求" | 等于没说 | 给出约束条件下的明确推荐 |
| 所有维度权重相同 | 现实中总有最关键的 1-2 个维度 | 根据约束突出关键维度 |
| 只看功能不看成本 | 技术可行≠经济可行 | 成本必须是一级维度 |
| 只看官方文档 | 营销 ≠ 真实体验 | 交叉验证：Issue、社区评价、Benchmark |
| 只搜通用框架，漏掉生态绑定型 | 候选池有结构性盲区，结论看似全面实则遗漏 | Phase 2.5 完备性反查：大厂清单 + 绑定型产品 + 近期更名项目 |
