## MCP Server 快速验证工作流

**评分**: 7/10 | **标签**: MCP, 调试, 工具验证, VS Code

**摘要**: 配置 MCP Server 后，使用 Python 子进程直接发送 JSON-RPC 请求验证端到端连接，比依赖 VS Code 自动发现快 10 倍。

### 💡 验证 MCP Server 配置时使用"三层验证"工作流，可以在 5 分钟内定位问题根因，而不是"改配置→重启 VS Code→测试→猜原因"的低效循环。

- **适用场景**: 配置或调试 VS Code MCP Server 时。
- **行动建议**: 三层验证：
  1. **层1 - 脚本可执行性**: 直接在终端运行 MCP Server 脚本，确认无语法错误
  2. **层2 - JSON-RPC 探测**: 用 Python subprocess+httpx 发送 tools/list 请求，确认工具注册和 LLM 调用均正常
  3. **层3 - VS Code 显示**: 确认层1/2通过后，重启 VS Code 并检查 tools 列表
  - 如果层1/2通过但层3失败，问题在 VS Code MCP Client 层而非 Server 配置

## 低置信度 LLM 推荐问题的零前端改动策略

**评分**: 8/10 | **标签**: 前端, 推荐, 接口设计

**摘要**: 为 LLM 低置信度回答追加推荐问题时，复用了已有的 fallback 场景推荐按钮渲染，仅后端修改即可落地。

### 💡 在已有多场景推荐按钮的前端系统中，新增推荐场景时优先选择"复用已有 scene"而非"新增 scene"，这样可以零前端改动完成功能上线。

- **适用场景**: 前端已有通用推荐按钮组件但后端需要新增推荐触发条件时。
- **行动建议**: 1. 检查前端推荐按钮组件的 scene 枚举和已有渲染逻辑。2. 选择语义最接近的现有 scene 复用。3. 在后端 done 事件中附带 recommended_questions 字段。4. 更新接口文档标注新增场景，但无需修改前端代码。

## TTS 音色切换的端到端验证工作流

**评分**: 7/10 | **标签**: TTS, 调试, 音色, 端到端测试

**摘要**: 调查 Kokoro 音色切换不生效时，使用了"API 代理层验证 → 目标服务直测 → 服务端 voices 端点查询 → .env 配置审计"四步定位法，精准找到根因（旧版服务不支持英文音色）。

### 💡 TTS 音色/语速切换不生效时的排查顺序应该是：1) API 代理层（GET /api/config/tts）确认当前值正确；2) TTS 服务端直测（POST /v1/tts with new voice）确认服务是否响应；3) 查询服务端 /v1/voices 确认实际支持的音色列表；4) .env 配置审计确认是否有遗留的硬编码常量。不要假设 GUI 下拉列表和实际支持的音色一致。

- **适用场景**: 排查 TTS 音色切换不生效或听起来都一样的问题。
- **行动建议**: 1. 查 API 层确认配置已正确更新。2. 直测 TTS 服务验证不同 voice 参数是否产生不同的语音。3. 查询服务端支持的 voices 列表。4. 检查 .env 和代码中的硬编码常量。5. 检查缓存——TTS 音频缓存 key 如果不含 voice 参数，切换音色后会命中旧缓存。
