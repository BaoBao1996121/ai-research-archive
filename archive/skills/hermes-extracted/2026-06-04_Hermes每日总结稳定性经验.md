# Hermes 每日总结稳定性经验 · 2026-06-04

## 结论

Hermes 已能读取并分析当日 Copilot + Codex 双源会话，但不能只依赖首轮 `_index.md` 判断质量；当 `_index.md` 与脚本输入或二次调查冲突时，必须以脚本输入和 `investigation.md` 为准。

## 本次验证事实

- 数据采集脚本：`%USERPROFILE%\.hermes\scripts\read_copilot_sessions.py`
- 当前任务：`daily-ai-session-review`，job id `0222a904ae9f`
- 输入覆盖：19 个会话，其中 Copilot 8 个、Codex 11 个
- 脚本输出预算：约 77KB stdout，避免 Hermes 把超大 stdout 判定为无输出
- 最新稳定运行：2026-06-04 22:08 触发，约 1 分钟完成，4 次 DeepSeek 调用，cron 状态 ok

## 发现的问题

1. 旧版脚本受 `COPILOT_MAX_SESSIONS=5` 影响，只采到 5 个 Copilot 会话。
2. 过大的脚本 stdout 曾导致 Hermes scheduler 判定 `script produced no output`。
3. Codex JSONL 中包含 AGENTS/environment/permissions 等注入上下文，若不滤除，会把 Codex 技术讨论误归纳为“AGENTS.md 迁移”。
4. Hermes skill 会读取已有 `_index.md`，即使 prompt 要求重建，仍可能保留旧覆盖表；因此需要二次调查文件校正。

## 已做修复

- `read_copilot_sessions.py` 同时读取 Copilot transcripts 和 Codex sessions。
- 会话数下限固定为 30，避免外部环境变量把采集限制到 5。
- 过滤 Codex 注入上下文：AGENTS、environment、permissions、skills/plugins 等块不进入摘要输入。
- 工具输出压缩到 500 字符，避免工具日志淹没真实用户讨论。
- 总输入预算降到稳定范围，保留所有会话但均分每会话片段。
- cron prompt 已要求以脚本输入重建覆盖审计，不得沿用旧 `_index.md`。

## 以后每日总结的质量门槛

每天检查三件事：

1. 脚本输入头部必须显示 Copilot 和 Codex 两类来源，以及各自会话数。
2. `_index.md` 之外，必须检查是否存在 `investigation.md` 或 `deep-digest.md`；如果二次调查指出首轮遗漏，以二次调查为准。
3. 抽查 Codex 会话主题，不能把所有 Codex 会话统一归为 AGENTS.md 或环境指令；至少要识别真实技术主题，例如 RAG 消融、ASR 优化、文件传输、Agent 上下文压缩、飞书数据入库等。
