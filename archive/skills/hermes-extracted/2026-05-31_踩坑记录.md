## 前端构建失败修复与工作流

**评分**: 6/10 | **标签**: 前端构建, 默认导出, 导入错误, 任务优先级, 代码清理

**摘要**: 修复因默认导出缺失导致的前端构建失败，并展示了自主推进本地安全任务的工作流模式。

### 💡 当模块只提供命名导出（named exports）而组件使用默认导入（default import）时，构建会报错。修复方法是在模块末尾添加 `export default api;`。
- **适用场景**: 使用 React 或类似前端框架，且 API 层使用 axios 实例并只导出了具体方法（如 `searchKnowledge`）时，如果新组件尝试 `import api from '../api'` 就会触发此错误。
- **行动建议**: 在创建新组件或模块时，先检查目标模块的导出方式（默认导出 vs 命名导出），确保导入语法匹配。如果模块需要同时支持两种导入方式，可以同时提供 `export default` 和 `export { ... }`。

### 💡 在用户不在场时，可以优先执行本地安全任务（如前端构建、代码清理），避免阻塞远程或需用户交互的操作（如扫码授权、SSH 部署）。
- **适用场景**: 当待办队列包含多种类型任务（本地、远程、需用户交互）且用户暂时无法响应时。
- **行动建议**: 将任务按依赖类型分类：本地安全任务（可自主执行）> 远程非破坏性任务 > 需用户交互任务。优先执行第一类，提升整体效率。

### 💡 构建成功后，清理未使用的导入（如 `Table`、`DatabaseOutlined`）可以减少 lint 警告，保持代码整洁，但非关键问题可以延后处理。
- **适用场景**: 在修复构建错误后，检查并清理明显的未使用导入，但不必追求零警告（如 `useEffect` 依赖缺失等预存问题可跳过）。
- **行动建议**: 修复构建错误后，快速扫描新修改文件中的未使用导入并移除，但不要陷入修复所有预存 lint 警告的陷阱，优先保证功能正确。

## TTS多语言管线配置踩坑

**评分**: 8/10 | **标签**: TTS, Kokoro, 多语言, 管线配置, HuggingFace, voice文件, 静默失败

**摘要**: Kokoro TTS 中文模型仓库不含英文 voice 文件，需从完整版仓库加载英文管线并正确路由，否则英文 TTS 静默失败。

### 💡 Kokoro TTS 的中文专用模型仓库（如 Kokoro-82M-v1.1-zh）只包含中文 voice 文件（z* 前缀），英文 voice 文件（a*/b* 前缀）存在于完整版仓库（Kokoro-82M-v1.1）。如果只初始化中文管线，所有请求都会走中文管线，英文 voice 会因找不到对应 .pt 文件而报错。
- **适用场景**: 使用 Kokoro TTS 支持多语言语音合成时，尤其是部署环境通过 HuggingFace 镜像站（hf-mirror.com）加载模型。
- **行动建议**: 初始化 TTS 管线时，根据 voice 前缀分别使用对应语言的 repo_id：英文（a*/b*）用完整版仓库，中文（z*）用中文专用仓库。模型权重可共用，仅 voice 文件需从对应仓库加载。

### 💡 TTS 静默失败（前端收到 audio_error 但文字正常显示）的根因往往是后端管线配置错误，而非网络或前端问题。排查时应优先检查 TTS 服务日志和模型仓库的 voice 文件完整性。
- **适用场景**: 多语言 TTS 系统调试，尤其是后端返回 success=false 但无明确错误信息时。
- **行动建议**: 在 TTS 服务启动时，主动检查并打印所有可用 voice 列表；对每个请求记录使用的管线类型和 voice 文件路径，便于快速定位。

### 💡 通过直接调用 TTS 接口（如 Invoke-RestMethod）测试特定 voice 和文本组合，可以快速验证 voice 文件是否存在，比 SSH 进容器检查文件更高效。
- **适用场景**: 远程调试 TTS 服务，尤其是容器化部署时。
- **行动建议**: 将 TTS 接口测试命令（如 curl 或 PowerShell Invoke-RestMethod）加入项目文档或 Makefile，作为部署后的冒烟测试步骤。

## 文件编码与 Python 读取

**评分**: 7/10 | **标签**: 文件编码, UnicodeDecodeError, Python, errors=replace, 混合编码

**摘要**: 读取文件时出现 UnicodeDecodeError 的根因是文件中包含当前编码方式无法解码的字节序列，使用 `errors='replace'` 可以让解码跳过非法字节而非崩溃。

### 💡 Python 读取文件遇到 UnicodeDecodeError 时，默认的 strict 模式会直接抛出异常终止程序，而使用 `open(path, 'r', encoding='utf-8', errors='replace')` 可以让解释器用替换字符（�）替代无法解码的字节序列，继续读取文件剩余内容。
- **适用场景**: 处理用户上传的文件、遗留系统数据、爬取内容等来源不可控、可能包含混合编码的文件时。
- **行动建议**: 1. 在 `open()` 函数中显式指定 `encoding='utf-8'` 和 `errors='replace'`。2. 对于更复杂的场景，可先用 `chardet` 或 `cchardet` 探测编码，再决定读取策略。3. 注意 `errors='replace'` 会静默丢失数据，生产环境应记录日志便于后续排查。4. 其他可用策略：`errors='ignore'`（删除非法字节）、`errors='backslashreplace'`（保留原始字节的转义序列，便于调试）。

### 💡 文件编码问题具有传染性——一个文件在 Windows 上正常，在 Linux 上报错，或反之，通常是因为不同平台的默认编码不同（Windows CP936/GBK vs Linux UTF-8）。显式指定 encoding 是跨平台兼容的关键。
- **适用场景**: 跨平台开发、Docker 容器化部署、CI/CD 流水线中文件读取。
- **行动建议**: 永远不要依赖系统默认编码（`locale.getpreferredencoding()`），始终在 `open()` 中显式指定 `encoding=` 参数。
