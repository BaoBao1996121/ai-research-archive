# Chapter 3: Agent 的五件武器

> 📍 前置：完成 Chapter 2（理解了 ReAct 循环）
> 🎯 完成本章后你能：说出 Agent 的五种基本组合模式；判断一个任务适合用哪种模式；理解 Claude Code 的架构图
> ⏱️ 预计时间：25 分钟阅读 + 5 分钟练习

---

## 为什么要知道这些？（WHY）

Chapter 2 你学会了 Agent 的核心——ReAct 循环。但一个光秃秃的循环只能做简单任务。真实世界的 Agent 需要处理复杂场景：

- 一个任务需要**分多步**按顺序完成（先搜、再分析、再输出）
- 一个任务需要**分几路**同时做（同时搜五个网站）
- 一个任务需要**不同的专家**处理不同部分（一个 Agent 写代码、另一个审代码）
- 一个任务需要**反复打磨**直到满意（写→评→改→再评→再改）

这些不是什么高深的理论。Anthropic（Claude 的开发商）和 Google（ADK 框架的开发商）各自独立地总结出了几乎相同的模式。说白了：**全世界的 Agent 系统，拆开来看都是这五种基本组合的排列组合**。

像乐高一样——零件就那么几种形状，组合出来的东西千变万化。

---

## 五种基本模式（WHAT）

### 模式 1: 提示链（Prompt Chaining）

**一句话**：步骤 A → 步骤 B → 步骤 C，人为规定好顺序。

```
输入 → [Step 1] → 检查 → [Step 2] → 检查 → [Step 3] → 输出
         LLM调用    ✓/✗     LLM调用    ✓/✗     LLM调用
```

**用厨师类比**：先切菜 → 检查切好没 → 再炒菜 → 检查火候 → 最后装盘。每一步的输出是下一步的输入，步骤之间可以加"关卡"检查。

**适合什么场景**：
- 先写大纲 → 检查大纲 → 根据大纲写文章
- 先生成代码 → 自动审查代码 → 生成测试
- 先分析需求 → 设计方案 → 实现方案

**你 Chapter 1 的 SKILL.md 就是一个提示链**——Step 1 搜索 → Step 2 筛选 → Step 3 生成报告。

### 模式 2: 路由（Routing）

**一句话**：根据输入类型，分发到不同的处理流程。

```
               ┌→ [处理器 A] — 退款请求
输入 → [路由器] ┼→ [处理器 B] — 技术问题
               └→ [处理器 C] — 一般咨询
```

**用前台类比**：医院挂号处——"发烧去内科、骨折去骨科、体检去门诊"。路由器的活就是**分类**，不做具体处理。

**适合什么场景**：
- 客服系统：不同类型的问题交给不同的专属 Agent
- 智能成本控制：简单问题用小模型（便宜），复杂问题用大模型（贵但准）

### 模式 3: 并行化（Parallelization）

**一句话**：多路同时干，最后汇总。

```
       ┌→ [Task A] ─┐
输入 → ┼→ [Task B] ─┼→ 汇总 → 输出
       └→ [Task C] ─┘
```

**有两种子类型**：

| 子类型 | 怎么做 | 例子 |
|--------|-------|------|
| **分段并行** | 把任务拆成不重叠的部分 | 同时搜 5 个网站 |
| **投票并行** | 同一任务做 3 次，取多数结果 | 3 个 LLM 各自审代码，2 个以上说有 bug 才算有 bug |

**Claude Code 的秘密武器**：它的 `toolOrchestration.ts` 实现了**自动并发分区**——只读工具（搜索、读文件）自动并行执行，写入工具（编辑文件）串行执行。你不用操心，它自己知道哪些能同时干。

### 模式 4: 编排者-工作者（Orchestrator-Workers）

**一句话**：一个"经理"动态分配任务给多个"员工"。

```
            ┌→ [Worker 1] ─┐
[编排者] → ├→ [Worker 2] ─┤→ [编排者汇总]
            └→ [Worker N] ─┘
```

**跟并行化的区别**：并行化的子任务是**预定义**的（你在代码里写死了分成几路）。编排者模式的子任务是**LLM 动态决定**的——"这个代码改动需要改 3 个文件，你、你、你，各改一个"。

**真实案例——Claude Code 的 AgentTool**：主 Agent 可以动态派生子 Agent。比如你说"重构这个模块"，主 Agent 可能派出：
- 子 Agent 1：先分析依赖关系
- 子 Agent 2：修改核心类
- 子 Agent 3：更新测试
每个子 Agent 有独立的上下文和工具集。

### 模式 5: 评估-优化循环（Evaluator-Optimizer）

**一句话**：一个生成、一个评分，反复迭代直到满意。

```
         ┌──────────────────────────┐
         │                          │
         ▼                          │
  [Generator]  →  [Evaluator]  →  不够好？──┘
       │                │
       │              够好了
       │                │
       ▼                ▼
                    最终输出
```

**用写论文类比**：你写一稿（Generator），导师看了提意见（Evaluator），你改二稿，导师再看……直到导师说"行了，可以发"。

**适合什么场景**：
- 翻译的反复打磨
- 代码质量的持续改进
- 任何"有明确质量标准、但初始版本不够好"的任务

## 五种模式的速查表

| # | 模式 | 核心思路 | 适用场景 | 你已经见过的例子 |
|---|------|---------|---------|----------------|
| 1 | 提示链 | 步骤 A→B→C 按顺序 | 步骤间有依赖 | Ch1 的 SKILL.md |
| 2 | 路由 | 先分类再处理 | 输入类型多样 | — |
| 3 | 并行化 | 多路同时干 | 子任务独立 | Claude Code 自动并发 |
| 4 | 编排者 | 经理动态分配 | 子任务数量不固定 | Claude Code AgentTool |
| 5 | 评估优化 | 生成→评→改→评… | 有明确质量标准 | Skill 自迭代（Ch12） |

**最重要的一句话——来自 Anthropic**：

> "力量不在于单个模式有多强，在于你怎么**组合**它们。"

一个真实的 Agent 系统往往是多种模式嵌套：外层是评估-优化循环，内层是编排者-工作者，每个工作者内部是提示链。Claude Code 的架构就是这样——看起来复杂，拆开来看就是这五种基本模式的组合。

## 动手环节（HOW）：看懂 Claude Code 的架构

回忆 Chapter 2，我说 Claude Code 有五十万行代码但核心是 ReAct 循环。现在你多了五件武器的分析视角。来看一张 Claude Code 的架构简图，试着标注每个部分用了哪种模式：

```
┌──────────────────────────────────────────────────────┐
│                Claude Code 架构                       │
│                                                      │
│  [用户输入]                                           │
│      │                                               │
│      ▼                                               │
│  [查询引擎] ← 🔄 模式 5（评估优化）的外层             │
│      │         （模型输出 → 检查是否完成 → 继续/停止）  │
│      ▼                                               │
│  [核心循环 query.ts] ← 🔄 ReAct 循环                 │
│      │                                               │
│      ├─→ [工具编排 toolOrchestration.ts]              │
│      │       ├── 只读工具 → ⚡ 模式 3（自动并行）      │
│      │       └── 写入工具 → 串行执行                   │
│      │                                               │
│      ├─→ [AgentTool] ← 🎭 模式 4（编排者派生子Agent） │
│      │                                               │
│      └─→ [上下文压缩] ← 📋 模式 1（链式处理）          │
│              snip → micro → auto → reactive           │
│                                                      │
│  [路由系统] ← 🔀 模式 2                               │
│      ├── CLI 模式 → 标准交互                           │
│      ├── SDK 模式 → API 接入                           │
│      └── Remote 模式 → 远程协作                        │
└──────────────────────────────────────────────────────┘
```

**练习**：对照上面的图回答：
1. Claude Code 的工具执行用了模式几？为什么只读和写入的处理不同？
2. AgentTool（派生子 Agent）用了模式几？跟模式 3 有什么区别?
3. 上下文压缩的四级链（snip→micro→auto→reactive）属于模式几？

## 回到你的 Agent：它用了哪些模式？

你 Chapter 1 的 Agent，用了哪些模式？

| 部分 | 模式 | 说明 |
|------|------|------|
| SKILL.md 的 Step 1→2→3 | 提示链 | 步骤是你定义好的 |
| Agent 核心循环 | ReAct | Agent 运行时提供的 |
| web_fetch 多个网站 | 可能并行 | 取决于运行时实现 |

它**没有**用到路由、编排者、评估优化。这完全正常——简单任务不需要。

但如果你想让 Agent 做更复杂的事——比如"搜集新闻→写分析报告→让另一个 Agent 审稿→根据反馈修改"——你就需要组合使用这些模式了。这是后面的事。
