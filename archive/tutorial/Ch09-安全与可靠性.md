## 为什么 Agent 跑久了就乱？（WHY）

你在 Spiral 1 搭了 Agent，Spiral 2 给了它知识和好指令。在短对话里它表现不错。

但当你让它做一个大任务——比如"把这个代码库重构一遍"或"写一个完整的 Web 应用"——就出问题了：

- 对话到 50 轮以后，它开始忘记最初的指令
- 上下文窗口快满了，它开始"胡言乱语"
- 做到一半宣布"任务完成！"——实际上还剩一半没做
- 前面改好的代码被后面的修改覆盖了

这些不是偶发事件。Anthropic 在用最强模型（Opus 4.5）+ 完整工具链做大型任务时，**系统性地遇到了同样的问题**。

说白了：**Agent 的所有可靠性问题，都源于一个物理限制——上下文窗口是有限的。** 对话越长，越早的信息被越后面的信息"稀释"。这像一个人的工作记忆——同时记住的事情是有限的，加的越多，前面的就越模糊。

## 核心概念（WHAT）

### 五大失败模式

| # | 失败模式 | 表现 | 根因 |
|---|---------|------|------|
| F1 | **一次性尝试过多** | 试图一口气实现整个系统，上下文耗尽后留下半成品 | 缺乏任务分解 |
| F2 | **过早宣布胜利** | 做了一部分就说"任务完成" | 缺乏全局目标清单 |
| F3 | **指令漂移** | 对话后期忘记早期的规则和约束 | 注意力衰减 + 上下文竞争 |
| F4 | **上下文溢出** | 对话太长导致超出窗口限制 | 无压缩机制 |
| F5 | **回归破坏** | 修复新 bug 时破坏了之前正常的功能 | 缺乏验证机制 |

F1 和 F2 的共同根因是——**Agent 没有一个持久化的"项目状态"来锚定行为**。F3 是本工作区在 [指令遵守验证与长期漂移检测研究报告](../reports/05-%E8%AF%84%E4%BC%B0%E4%B8%8E%E8%B4%A8%E9%87%8F/R17_%E6%8C%87%E4%BB%A4%E9%81%B5%E5%AE%88%E9%AA%8C%E8%AF%81%E4%B8%8E%E9%95%BF%E6%9C%9F%E6%BC%82%E7%A7%BB%E6%A3%80%E6%B5%8B.md) 中深入研究过的问题。

### 指令漂移：三层递归困境

```
Layer 0: AI 不遵守指令
  → 解决方案：写检查机制

  Layer 1: 检查机制本身也不被遵守
    → 解决方案：自动化检查

    Layer 2: 自动化机制也被遗忘
      → 解决方案：???
```

这是一个真正的系统设计问题。核心洞察：**从"自愿遵守"到"强制执行"的跨越，是解决这个问题的关键。** 就像软件工程中"单元测试存在但没人跑"和"CI 自动跑测试"是完全不同的质量保障水平。

漂移的五个驱动因素：

| 因素 | 机制 | 可控性 |
|------|------|:---:|
| 注意力衰减 | 长对话中 system prompt 权重被稀释 | 中 |
| 上下文竞争 | 用户当前请求 vs 系统指令冲突时，模型倾向用户 | 低 |
| 任务聚焦效应 | 专注具体问题时忽略全局规则 | 中 |
| 模型版本漂移 | 同一 prompt 在不同模型版本上表现不同 | 低 |
| 规则膨胀 | 规则太多互相矛盾 | 高 |

### 解法一：上下文压缩（Compaction）

当对话接近窗口上限时，用 LLM 自己来压缩对话历史：

```python
"""
上下文压缩：保留关键信息，压缩冗长的对话历史
"""
def compact_conversation(messages: list, client, max_tokens: int = 100000) -> list:
    """
    当对话 tokens 接近上限时，压缩早期对话
    
    策略：保留 system prompt + 最近 N 轮 + 压缩中间部分
    """
    total_tokens = estimate_tokens(messages)
    
    if total_tokens < max_tokens * 0.8:  # 还没到 80%，不需要压缩
        return messages
    
    # 始终保留的：system prompt + 最近 5 轮
    system_msg = messages[0]  # system prompt
    recent = messages[-10:]    # 最近 5 轮（每轮=user+assistant）
    middle = messages[1:-10]   # 要被压缩的中间部分
    
    # 用 LLM 摘要中间部分
    summary_response = client.chat.completions.create(
        model="qwen-plus",
        messages=[{
            "role": "user",
            "content": f"""请将以下对话历史压缩为简明摘要。保留：
1. 所有做出的决策和理由
2. 所有修改过的文件和内容
3. 所有未完成的任务
4. 发现的问题和解决方案

对话历史：
{format_messages(middle)}"""
        }]
    )
    
    summary = summary_response.choices[0].message.content
    
    return [
        system_msg,
        {"role": "assistant", "content": f"[对话历史摘要]\n{summary}"},
        *recent,
    ]
```

**但 Compaction 不够。** 它是有损压缩——细节会丢失。Anthropic 发现，光靠 Compaction，Agent 仍然会 F1（一口气做太多）和 F2（提前宣布完成）。

### 解法二：双 Agent Harness 架构

Anthropic 提出的完整解法：

```
┌─ Session 1: Initializer Agent ──────────────────┐
│                                                   │
│  用户 Prompt → 生成 feature_list.json（200个功能）  │
│              → 创建 init.sh（启动脚本）             │
│              → 初始化 Git + 首次提交               │
│              → 创建 progress.txt（进度日志）        │
└───────────────────────────────────────────────────┘
                    ↓ 持久化文件
┌─ Session 2~N: Coding Agent ─────────────────────┐
│                                                   │
│  每次启动 → Boot Sequence:                        │
│    1. 读 progress.txt（上一班做到哪了）             │
│    2. 读 git log（最近改了什么文件）                │
│    3. 跑 init.sh（启动开发服务器）                  │
│    4. 跑测试（验证环境健康）                        │
│                                                   │
│  然后 → 从 feature_list.json 拿下一个任务          │
│       → 实现 → 测试 → git commit → 更新 progress  │
└───────────────────────────────────────────────────┘
```

核心思想：**像轮班工程师一样交接。** 每个新 Agent 实例不靠记忆（Compaction），靠**持久化的项目状态文件**来了解全局。

四大持久化工件：

| 工件 | 作用 | 类比 |
|------|------|------|
| `feature_list.json` | 全部功能点清单 + 完成状态 | 看板上的任务卡片 |
| `progress.txt` | 时间线进度日志 | 交接班记录本 |
| `init.sh` | 环境启动脚本 | 新人入职指南 |
| Git 提交历史 | 增量代码变更记录 | 版本控制 |

### 解法三：硬约束 + 软约束混合架构

对于指令漂移，最有效的防线是：

```
硬约束（骨架）                        软约束（血肉）
┌─────────────────────┐              ┌─────────────────────┐
│ 自动化脚本                │              │ LLM 自检                │
│ CI/CD 管线                │              │ Subagent 互审           │
│ wiki_lint.py            │              │ System prompt 规则      │
│ 确定性检查(regex/格式)    │              │ 自省检查清单             │
└─────────────────────┘              └─────────────────────┘
      ↑ 不可绕过                            ↑ 可能被遗忘
      ↑ 100% 执行率                         ↑ 80-95% 执行率
```

**硬约束做骨架（确保底线）+ 软约束做血肉（提升质量）**。不要指望 Agent "自觉"遵守所有规则——把关键规则变成自动化检查。

### 解法四：SDK 权限系统 — Hooks 拦截

如果你用 Agent SDK（Ch4 方式二），权限控制可以做得更精细。Claude Agent SDK 提供了 Hooks 拦截系统——在工具执行前/后插入检查逻辑：

```
Agent 想执行 bash("rm -rf /")
         │
         ▼
    ┌─────────────┐
    │ PreToolUse   │ ← Hook 在这里拦截
    │ 检查命令是否  │
    │ 在白名单内    │
    └──────┬──────┘
           │
    ┌──────┴──────┐
    │ deny（拒绝）  │ → 直接阻止，Agent 收到"操作被拒绝"
    │ ask（询问）   │ → 暂停，等人类确认
    │ allow（放行） │ → 执行工具
    └─────────────┘
```

权限评估的 5 层流水线（优先级从高到低）：

| 层 | 检查 | 说明 |
|---|------|------|
| 1 | Hooks | 你自定义的拦截逻辑（最高优先） |
| 2 | Deny Rules | 黑名单（"永远不许执行 rm -rf"） |
| 3 | Permission Mode | 全局模式（plan/auto-edit/full-auto） |
| 4 | Allow Rules | 白名单（"只允许读取 .py 文件"） |
| 5 | canUseTool | 工具自身声明的权限要求 |

**最安全模式**：白名单 + `dontAsk`（不允许 Agent 通过"说服"人类来突破限制）。

> 📌 这个 5 层模型的设计思路和 Linux 的 SELinux/AppArmor 类似——**默认拒绝，显式允许**。详见 [Claude-Agent-SDK从入门到实战完全指南](../reports/04-%E5%B7%A5%E7%A8%8B%E5%AE%9E%E8%B7%B5/R27_ClaudeAgentSDK%E5%85%A5%E9%97%A8%E5%88%B0%E5%AE%9E%E6%88%98.md) §5 权限系统。
