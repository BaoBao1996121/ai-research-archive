## 为什么上下文很重要？（WHY）

Chapter 4 你搭了一个能用的 Agent。但你可能已经发现一个问题：当你让它处理一个真实项目时——比如这个知识库的 1884 个文件——它就懵了。

为什么？因为你的 Agent 有"近视眼"。

LLM 的上下文窗口（目前最大 ~200K tokens）就是 Agent 唯一能"看到"的范围。而一个中等规模的代码库（比如 Claude Code 源码，47.7 万行代码）换算成 Token 有 **759 万**——是窗口的 **38 倍**。

说白了：**Agent 不是不聪明，是看不见。**

这就像让一个很聪明的人在完全黑暗的房间里修电路——手电筒（上下文窗口）只能照到一小块区域。问题不是他不会修，而是他看不到全貌。

上下文工程（Context Engineering）要解决的就是：**怎么在有限的手电筒光束里，照到最关键的那部分。**

> 🔗 一句话预告：Andrej Karpathy 说得好——"上下文窗口就是 LLM 的工作记忆。管理好它，比换一个更大的模型更重要。"

## 核心概念（WHAT）

### 问题的本质：不是"怎么塞更多"，而是"怎么选更准"

很多人的第一反应是"等窗口更大就行了"。不行。即使给你一个无限大的窗口：

| 挑战 | 说明 |
|------|------|
| **Token 成本** | 200K tokens 一次调用约 $0.6（Claude），日均 1000 次 = $600/天 |
| **注意力衰减** | 研究表明 LLM 对中间位置的信息关注度显著降低（"Lost in the Middle" 效应） |
| **信噪比** | 塞进去 99% 是噪声，LLM 反而更容易出错 |
| **延迟** | Token 越多，首个 Token 的生成延迟越高 |

正确的思路是选择性注入——像老练的外科医生一样，只把需要的器械放在手边。

### 分层上下文架构：Agent 视野的三个层次

我们在本工作区的实验（01_repo_map.py + 03_smart_context.py）验证了一个核心方案：**分层上下文**。

```
┌────────────────────────────────────────────────┐
│               LLM 上下文窗口                     │
│                                                 │
│  ┌───────────────────────────────────────────┐  │
│  │ Layer 0: 系统指令 (~500 tokens)            │  │
│  │   "你是一个代码助手，遵循以下规则..."         │  │
│  ├───────────────────────────────────────────┤  │
│  │ Layer 1: 全局地图 (~2万 tokens)             │  │
│  │   目录级 Repo Map — 每个模块有什么           │  │
│  ├───────────────────────────────────────────┤  │
│  │ Layer 2: 局部签名 (~5万 tokens)             │  │
│  │   当前编辑文件 + 直接依赖的 API 签名          │  │
│  ├───────────────────────────────────────────┤  │
│  │ Layer 3: 焦点代码 (~10万 tokens)            │  │
│  │   当前编辑区域的完整实现                      │  │
│  ├───────────────────────────────────────────┤  │
│  │ Layer 4: 用户指令 + 对话历史                 │  │
│  └───────────────────────────────────────────┘  │
└────────────────────────────────────────────────┘
```

**越外层的信息越精简，越内层的信息越详细。** 就像地图——你不需要每次导航都看到地球上每一棵树，你只需要：世界地图（知道大方向）→ 城市地图（知道走哪条路）→ 街景（知道具体转弯在哪）。

### 四种 Repo Map 粒度：实验数据

这是实验 01（01_repo_map.py）对 Claude Code 源码（1884 文件）的实测结果：

| Map 级别 | Token 数 | 压缩比 | 信息量 | 适用场景 |
|---------|---------|--------|-------|---------|
| **Directory** | 20,556 | 1:369 | 每个目录有什么模块 | 全局视野，"仓库里有什么" |
| **Skeleton** | 114,913 | 1:66 | 每个文件有哪些符号 | 架构理解，"每个文件干什么" |
| **Standard** | 182,496 | 1:42 | 函数签名和参数类型 | 编码辅助，"API 怎么调用" |
| **Detailed** | 245,265 | 1:31 | 完整类型定义 | 深度编码，"接口的每个字段" |

**关键发现**：Directory Map 用 2 万 tokens 就能让 Agent 看到整个 759 万 tokens 代码库的全貌——**压缩了 369 倍**。全部 1884 个文件的解析 + Map 生成仅需 **2.5 秒**。

### 依赖感知：Agent 不该盲目扩展视野

实验 02 的另一个重要发现：**不能无脑递归依赖**。

| 编辑的文件 | 1 层依赖（文件数） | 2 层依赖（文件数） | 1 层 Token | 2 层 Token |
|-----------|:---:|:---:|:---:|:---:|
| `BashTool.tsx` | 45 | 175 | 275K | 860K |
| `commands/commit.ts` | 5 | 127 | 13K | 302K |
| `screens/REPL.tsx` | 223 | 832 | 1,559K | 3,390K |

REPL.tsx 的 2 层依赖覆盖了 **全仓 44% 的文件**——基本等于没筛选。而 commit.ts 的 1 层依赖只需要 5 个文件（13K tokens），已经足够。

**经验法则：1 层依赖通常就够了。只有 Agent 明确说"我需要看 X 的实现"时，才按需展开第 2 层。**

### PageRank 排序：找到代码库的"脊梁"

实验 03 用 PageRank 算法对文件重要性排序。有趣的发现：

- `ink.ts` 被引用最多（442 次），但 PageRank 排名第 5——因为引用它的主要是"叶子"UI 组件
- `bootstrap/state.ts` PageRank 第 1——因为引用它的都是**其他核心模块**，传递价值高
- `utils/intl.ts` 只被 13 个文件引用，但 PageRank 第 13——因为引用它的都是核心文件

**一句话：被谁引用比被多少人引用更重要。** 这跟互联网的 PageRank 原理完全一致：一个被纽约时报链接的小博客，比一个被 100 个垃圾站链接的网站更重要。

### 大型项目实战：上下文的"冷启动"问题

理论很美好，但当你面对一个真实的大型项目（如 35 万行 C++/C# 代码库）时，会遇到一个理论没覆盖的问题——**冷启动**：

> Agent 首次打开项目时，copilot-instructions.md 是空的（或只有默认模板）。它不知道项目是做什么的、架构是什么样的、核心模块在哪里。就像新人第一天上班，连工位在哪都不知道。

本工作区的 多仓代码库知识建设实战研究报告（原稿交叉引用，本归档未解析） 在真实项目上诊断了 5 大瓶颈并落地了解决方案：

| 瓶颈 | 症状 | 解法 |
|------|------|------|
| **冷启动** | Agent 不知道项目是什么 | 重写 copilot-instructions（项目概览+架构+导航） |
| **跨仓断裂** | 两个仓库的 Agent 互相不知对方 | 多根工作区 + 跨仓依赖映射文档 |
| **层级缺失** | 纯代码无业务上下文 | 目录级 `.instructions.md`（C++/C# 分区指引） |
| **Skill 冲突** | 42 个 Skill 目录有重复 | 权威来源原则（每个 Skill 只在一处维护） |
| **平台知识盲区** | Agent 不懂平台框架 | 新建平台级 copilot-instructions |

**经验法则**：copilot-instructions.md 控制在 **1500-2000 tokens** 内（项目概览 + 核心架构 + 导航指引）。太短没用，太长 Agent 注意力会被稀释。

如果你手头有 tree-sitter 环境，也可以用以下最小代码自己实现 Directory Map 生成（不依赖 tree-sitter，纯目录扫描）：

```python
"""
最简 Repo Map：扫描目录结构 + 文件行数，生成 Agent 可消费的概览
"""
import os
from pathlib import Path

def generate_directory_map(root: str, extensions=('.py', '.ts', '.tsx', '.js')) -> str:
    """生成目录级 Map"""
    lines = [f"# Repository Map: {Path(root).name}\n"]
    
    for dirpath, dirnames, filenames in os.walk(root):
        # 跳过隐藏目录和 node_modules
        dirnames[:] = [d for d in dirnames if not d.startswith('.') and d != 'node_modules']
        
        relevant = [f for f in filenames if Path(f).suffix in extensions]
        if not relevant:
            continue
        
        rel_dir = os.path.relpath(dirpath, root)
        total_lines = 0
        for f in relevant:
            with open(os.path.join(dirpath, f), 'r', errors='ignore') as fh:
                total_lines += sum(1 for _ in fh)
        
        lines.append(f"\n## {rel_dir}/ ({len(relevant)} files, {total_lines:,} lines)")
        for f in sorted(relevant):
            filepath = os.path.join(dirpath, f)
            with open(filepath, 'r', errors='ignore') as fh:
                line_count = sum(1 for _ in fh)
            lines.append(f"  - {f} ({line_count} lines)")
    
    return '\n'.join(lines)

# 使用
if __name__ == '__main__':
    map_text = generate_directory_map('.')
    print(f"Map 长度: {len(map_text)} 字符, ~{len(map_text)//4} tokens")
    print(map_text[:2000])  # 预览前 2000 字符
```

### 实验 2：智能上下文组装

接下来，用实验 03 的思路写一个简化版的上下文组装器：

```python
"""
简化版：根据当前编辑文件，自动组装 Agent 上下文
"""
import ast
import os

def extract_imports(filepath: str) -> list[str]:
    """提取 Python 文件的 import 目标"""
    with open(filepath, 'r') as f:
        tree = ast.parse(f.read())
    
    imports = []
    for node in ast.walk(tree):
        if isinstance(node, ast.Import):
            for alias in node.names:
                imports.append(alias.name)
        elif isinstance(node, ast.ImportFrom):
            if node.module:
                imports.append(node.module)
    return imports

def build_context(target_file: str, repo_root: str, budget_tokens: int = 50000) -> str:
    """
    为编辑 target_file 构建最优上下文
    
    策略：
    1. 始终包含 Directory Map（~2K tokens）
    2. 包含 target_file 完整内容
    3. 包含直接依赖的文件签名（函数/类定义首行）
    4. 按 budget 截断
    """
    parts = []
    used_tokens = 0
    
    # Layer 1: Directory Map
    dir_map = generate_directory_map(repo_root)
    map_tokens = len(dir_map) // 4
    parts.append(f"## 仓库概览\n{dir_map}")
    used_tokens += map_tokens
    
    # Layer 2: 当前文件完整内容
    with open(target_file, 'r') as f:
        content = f.read()
    file_tokens = len(content) // 4
    parts.append(f"\n## 当前文件: {target_file}\n```python\n{content}\n```")
    used_tokens += file_tokens
    
    # Layer 3: 直接依赖的签名
    imports = extract_imports(target_file)
    for imp in imports:
        if used_tokens >= budget_tokens:
            break
        # 尝试找到对应文件
        imp_path = os.path.join(repo_root, imp.replace('.', '/') + '.py')
        if os.path.exists(imp_path):
            signatures = extract_signatures(imp_path)
            sig_tokens = len(signatures) // 4
            parts.append(f"\n## 依赖: {imp}\n{signatures}")
            used_tokens += sig_tokens
    
    return '\n'.join(parts)

def extract_signatures(filepath: str) -> str:
    """提取文件中所有函数/类的签名（不含实现）"""
    with open(filepath, 'r') as f:
        tree = ast.parse(f.read())
    
    sigs = []
    for node in ast.walk(tree):
        if isinstance(node, (ast.FunctionDef, ast.AsyncFunctionDef)):
            args = ast.dump(node.args)  # 简化：实际应格式化参数
            sigs.append(f"def {node.name}(...)  # line {node.lineno}")
        elif isinstance(node, ast.ClassDef):
            bases = ', '.join(b.id for b in node.bases if hasattr(b, 'id'))
            sigs.append(f"class {node.name}({bases}):  # line {node.lineno}")
    return '\n'.join(sigs)
```
