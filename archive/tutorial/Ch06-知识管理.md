## 为什么需要知识管理？（WHY）

Chapter 5 你学了怎么让 Agent 看懂代码库。但代码只是 Agent 需要的知识的一部分。

想象你雇了一个什么都会的新员工，但他对你们**公司的业务**一无所知。他不知道你们的产品是什么、客户是谁、内部流程怎么走、上次出了什么事故。每天来都问一遍"我们公司是做什么的？"——这就是没有长期记忆的 Agent。

更要命的是：**Agent 每次新会话都是"失忆"状态。** 上一次对话中它学到了"用户偏好用 TypeScript"、"这个项目的部署流程是 XYZ"——下一次全忘了。

知识管理要解决的核心问题：**怎么把庞大的业务知识灌给 Agent，让它随时能用、不会忘？**

---

## 核心概念（WHAT）

### 你以为的解法：RAG。但 RAG 有陷阱。

Retrieval-Augmented Generation（RAG）是最流行的方案——把知识切块、向量化、存到向量数据库，Agent 提问时检索最相关的块。

看起来很完美，但实际用起来你会撞到三堵墙：

| 问题 | 说明 | 举例 |
|------|------|------|
| **召回率不足** | 向量相似≠语义相关。嵌入模型对精确匹配和跨文档推理表现差 | 搜"审批流程超时怎么处理"，召回了"审批流程图"但没召回"超时降级策略" |
| **上下文断裂** | 切块后每个块丢失了全文背景 | "它的值为 300ms"——"它"是什么？原文档里很清楚，切块后就不知道了 |
| **Embedding 黑盒** | 你不知道为什么召回了这个而不是那个，出了问题很难调 | 召回率从 90% 掉到 60%，你甚至不知道从哪开始排查 |

> 📌 Karpathy 在 2025 YC 演讲中的原话："I copy-pasted the whole thing to an LLM. And I just grabbed what I wanted, and it just worked out of the box."——把整个文档直接喂给 LLM，比搞 RAG 简单还效果好。

### 十大方案全景：不只有 RAG

我们的研究调研了十种知识注入方案：

```
成本 ↑
  │
  │  Fine-tuning ⑨      ← 把知识烧进模型权重（效果好但贵且不灵活）
  │
  │  GraphRAG ⑥         ← 构建知识图谱（关系推理强，但实施复杂）
  │  RAPTOR ⑤           ← 树状分层摘要（多层推理好，预处理成本高）
  │
  │  Contextual RAG ⑦   ← 增强版 RAG（给每个块加上下文前缀）
  │  知识蒸馏 ④          ← LLM 预先消化知识，生成精炼版
  │
  │  Agent 自主检索 ⑧    ← Agent 用搜索工具自己找（灵活但不可控）
  │  Self-Route ⑩        ← 模型自己判断用 RAG 还是全量注入
  │
  │  ★ Wiki 法 ①        ← 预处理为 LLM 友好格式 → 全量/分段注入
  │  Prompt Caching ③   ← 利用 API 缓存便宜地注入大量上下文
  │  Context Stuffing ② ← 全塞进去（最简单，小知识库有效）
  │
  └────────────────────────────── 复杂度 →
```

### 推荐策略：Wiki 法 + Prompt Caching

对于中小型知识库（500 页以内），**Wiki 法是当前最优解**。核心思路三步走：

**第一步：整理为 Markdown**

把所有知识整理成结构化的 Markdown 文件：

```
knowledge-base/
├── 00-overview.md          # 一句话说清楚这个库是干什么的
├── 01-core-concepts.md     # 核心概念和定义
├── 02-business-rules.md    # 业务规则
├── 03-workflows.md         # 工作流程
├── 04-reference-data.md    # 参考数据/表格
├── 05-faq.md               # 常见问题
└── index.md                # 目录索引（LLM 友好）
```

**第二步：创建 index.md（LLM 导航入口）**

```markdown
# 知识库名称

> 一句话：这个知识库包含 XX 系统的完整业务规则和操作文档

## 文档列表
- 核心概念（原稿引用文件未随本次归档发布）: 所有基础概念定义
- 业务规则（原稿引用文件未随本次归档发布）: 审批、权限、限额规则
- 工作流程（原稿引用文件未随本次归档发布）: 标准操作流程

## 快速查询
- 审批超时怎么处理 → business-rules.md#timeout-policy
- 新员工权限配置 → workflows.md#onboarding
```

**第三步：按需拼装上下文**

```python
def build_knowledge_context(question: str, kb_path: str) -> str:
    """
    Wiki 法：根据问题拼装知识上下文
    
    策略：总是包含 overview + index，其余按相关性选入
    """
    context = []
    
    # 始终包含：概览 + 索引
    context.append(read_file(f"{kb_path}/00-overview.md"))
    context.append(read_file(f"{kb_path}/index.md"))
    
    # 简单关键词匹配选择相关文件（生产环境可用 BM25）
    for md_file in sorted(Path(kb_path).glob("*.md")):
        content = md_file.read_text()
        # 如果文件内容与问题有关键词重叠，加入上下文
        if any(kw in content.lower() for kw in extract_keywords(question)):
            context.append(content)
    
    return "\n---\n".join(context)
```

### Wiki 法 vs RAG：什么时候用什么？

| 判断维度 | Wiki 法更优 | RAG 更优 |
|---------|-----------|---------|
| 知识库大小 | < 500 页 | > 500 页 |
| 更新频率 | 低-中（可以人工维护 Markdown） | 高（自动化索引更新） |
| 精确度要求 | 高（需要精确数值、完整流程） | 中（大致准确即可） |
| 知识关联性 | 强（概念互相依赖） | 弱（每个文档独立） |
| 实施复杂度 | 低（Markdown + 拼接） | 高（向量数据库 + 嵌入模型） |
| 调试难度 | 低（直接看注入了什么） | 高（Embedding 是黑盒） |

> 📌 **实用判断**：如果你的知识库用 Markdown 写完能塞进一个上下文窗口（~200K tokens ≈ 300 页纯文本），直接用 Wiki 法 + Prompt Caching。只有当规模超出这个范围时，才值得上 RAG。

### 当知识库真的很大时：RAG 的四代演进

Wiki 法有天花板——知识库超过 200K tokens 时塞不进窗口。这时候 RAG 是正确的选择。但 RAG 不是一成不变的，它经历了四代演进：

```
第一代: Naive RAG (2023)          第二代: Advanced RAG (2024)
┌──────────────────────┐         ┌──────────────────────┐
│ 文档 → 固定切块       │         │ 文档 → 语义切块       │
│      → Embedding     │         │      → 混合检索       │
│      → 向量检索       │  ──→   │      (向量+BM25)     │
│      → 直接塞给LLM   │         │      → Rerank 重排   │
│                      │         │      → 上下文截断     │
└──────────────────────┘         └──────────────────────┘
         ↓                                ↓
第三代: Modular RAG (2025)        第四代: Agentic RAG (2026)
┌──────────────────────┐         ┌──────────────────────┐
│ 多路检索（图+向量+关键词）│        │ Agent 自主决定:       │
│ 可配置管线            │  ──→   │   - 搜还是不搜？      │
│ 插件化每个环节        │         │   - 搜哪个源？        │
│ 自适应策略            │         │   - 结果够不够？      │
│                      │         │   - 需要追加搜索？    │
└──────────────────────┘         └──────────────────────┘
```

**关键认知**：大多数"RAG 效果不好"的吐槽，都是卡在第一代。升级到第二代（混合检索 + Rerank）通常能解决 80% 的问题。

RAG 的核心链路和优化优先级：

| 环节 | 做什么 | 优化优先级 | 投入产出比 |
|------|-------|:---:|:---:|
| **数据清洗** | 去重、修格式、清噪声 | P0 🔴 | 极高 |
| **分块** | 把文档切成合适的块 | P0 🔴 | 高 |
| **Embedding** | 把文本变成向量 | P1 🟡 | 中 |
| **检索** | 找最相关的块 | P0 🔴 | 高 |
| **重排** | 对检索结果精排序 | P1 🟡 | 高 |
| **生成** | LLM 基于上下文回答 | P2 🟢 | 中 |

> 📌 **生产暗坑**：数据质量 >> 模型质量。花在清洗数据上的 1 小时，顶得上换一个更贵模型的 10 倍效果。详见 [RAG从入门到生产落地完全指南](../reports/04-%E5%B7%A5%E7%A8%8B%E5%AE%9E%E8%B7%B5/R30_RAG%E4%BB%8E%E5%85%A5%E9%97%A8%E5%88%B0%E7%94%9F%E4%BA%A7%E8%90%BD%E5%9C%B0.md)。

### 三层上下文架构：Schema + Wiki + Skills

在真实的大型项目（如 35 万行代码库）中，单一方案往往不够。本工作区的 [Code-Wiki代码仓库业务知识组织实验报告](../reports/02-%E7%9F%A5%E8%AF%86%E7%AE%A1%E7%90%86%E4%B8%8E%E4%B8%8A%E4%B8%8B%E6%96%87/R13_CodeWiki%E4%BB%A3%E7%A0%81%E4%BB%93%E5%BA%93%E4%B8%9A%E5%8A%A1%E7%9F%A5%E8%AF%86%E7%BB%84%E7%BB%87.md) 验证了一个重要发现：**Wiki 和 Skills 不是替代关系，而是互补关系。**

```
┌─────────────────────────────────────────────────────┐
│  三层上下文 = Schema + Wiki + Skills                  │
│                                                      │
│  Layer 1: Schema（~2K tokens，常驻）                  │
│  ┌──────────────────────────────────────────────┐   │
│  │ copilot-instructions.md / CLAUDE.md           │   │
│  │ → 项目概览、架构、导航、核心约束                  │   │
│  │ → 每次对话都注入，是 Agent 的"入职手册"          │   │
│  └──────────────────────────────────────────────┘   │
│                                                      │
│  Layer 2: Wiki（~12K tokens，全局知识）               │
│  ┌──────────────────────────────────────────────┐   │
│  │ 业务术语表、设计决策记录、修改场景手册             │   │
│  │ → 回答 What/Why（"这个概念是什么？为什么这样设计？"）│  │
│  │ → Schema 引用 Wiki 目录，Agent 按需查阅          │   │
│  └──────────────────────────────────────────────┘   │
│                                                      │
│  Layer 3: Skills（按需加载，专家知识）                 │
│  ┌──────────────────────────────────────────────┐   │
│  │ SKILL.md 文件，每个 ~500-2000 tokens            │   │
│  │ → 回答 How（"怎么执行这个任务？"）                │   │
│  │ → 只在需要时激活，不占常驻预算                     │   │
│  └──────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────┘
```

**实验数据**：在 35 万行医疗影像项目上，Wiki 用 Skills **2.4% 的 Token 预算**覆盖了 Skills **0% 覆盖**的知识空白。组合后上下文覆盖率从 60% 提升到 95%。

> 📌 **选择建议**：
> - 小项目（< 5K 行）：Schema 层就够了（写好 CLAUDE.md）
> - 中项目（5K-50K 行）：Schema + 几个核心 Skills
> - 大项目（> 50K 行）：三层全上——Schema + Wiki + Skills

## 动手做（HOW）

### 实验：给本知识库画一个"画像"

本工作区就是一个现成的知识库。用以下脚本分析它的结构：

```python
"""
知识库画像：分析工作区的知识结构
"""
from pathlib import Path
import os

def analyze_knowledge_base(root: str) -> dict:
    """分析知识库的规模和结构"""
    stats = {
        'total_files': 0,
        'total_chars': 0,
        'total_tokens_est': 0,
        'by_type': {},
        'largest_files': [],
    }
    
    for md_file in Path(root).rglob("*.md"):
        # 跳过 node_modules 等
        if 'node_modules' in str(md_file) or '.git' in str(md_file):
            continue
        
        content = md_file.read_text(encoding='utf-8', errors='ignore')
        chars = len(content)
        tokens_est = chars // 4  # 粗估：1 token ≈ 4 字符
        
        stats['total_files'] += 1
        stats['total_chars'] += chars
        stats['total_tokens_est'] += tokens_est
        
        # 按目录分类
        rel_path = md_file.relative_to(root)
        top_dir = rel_path.parts[0] if len(rel_path.parts) > 1 else '根目录'
        stats['by_type'][top_dir] = stats['by_type'].get(top_dir, 0) + tokens_est
        
        stats['largest_files'].append((str(rel_path), tokens_est))
    
    stats['largest_files'].sort(key=lambda x: -x[1])
    stats['largest_files'] = stats['largest_files'][:10]
    
    return stats

# 使用
stats = analyze_knowledge_base(r'f:\AI2025\Agent研究')
print(f"📊 知识库画像")
print(f"  文件数: {stats['total_files']}")
print(f"  总 Token: ~{stats['total_tokens_est']:,}")
print(f"  能否一次塞入 200K 窗口: {'✅ 可以' if stats['total_tokens_est'] < 200000 else '❌ 需要分层'}")
print(f"\n📂 各目录 Token 分布:")
for dir_name, tokens in sorted(stats['by_type'].items(), key=lambda x: -x[1]):
    print(f"  {dir_name}: ~{tokens:,} tokens")
print(f"\n📄 最大文件 Top 5:")
for path, tokens in stats['largest_files'][:5]:
    print(f"  {path}: ~{tokens:,} tokens")
```

运行后你会发现：本工作区的 24 篇报告总共约 170K tokens——刚好卡在一个上下文窗口的边界。这正好说明了为什么我们选择了 Wiki 法（KNOWLEDGE_INDEX.md 作为索引），而不是上 RAG。
