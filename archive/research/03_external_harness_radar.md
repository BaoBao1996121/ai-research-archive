# 外部协议雷达分析

## 问题
如何选择适合 Crazy 项目的外部协议？

## 判断
基于外部协议雷达分析，A2A 和 MCP 协议是 Crazy 项目的核心协议。

## 规则
1. **技术成熟度**：优先选择经过广泛验证的协议。
2. **社区支持**：选择有活跃社区和定期更新的协议。
3. **文档完善度**：协议文档需清晰、完整，便于快速上手。
4. **与现有技术栈的兼容性**：协议需与 Crazy 项目的技术底座（如 Redis Streams、记忆机制等）兼容。
5. **可扩展性**：协议需支持未来的功能扩展和复杂场景。
6. **安全性**：协议需具备完善的安全机制，防止潜在风险。
7. **性能**：协议需在性能上满足 Crazy 项目的需求。

## 例外
- 协议处于早期阶段，尚未经过充分验证。
- 协议缺乏社区支持，维护风险较高。

## 检查清单
1. **文档审查**：阅读协议官方文档，确认其功能是否符合项目需求。
2. **代码示例评估**：查看协议的代码示例，评估其复杂度和可实现性。
3. **兼容性测试**：确认协议与 Crazy 项目的技术底座兼容。
4. **安全性评估**：审查协议的安全机制，确认其能否满足项目需求。
5. **性能测试**：评估协议在实际使用中的性能表现。
6. **社区支持评估**：查看协议的社区活跃度和维护情况。
7. **最终决策记录**：记录选择协议的理由和依据，便于后续追溯和调整。

# Crazy 项目技术雷达速查卡

## 问题
如何快速了解 Crazy 项目的技术选型和关键机制？

## 判断
Crazy 项目是一个事件驱动、常驻的 A2A 项目，核心机制包括 A2A-lite、工具网关、上下文管理等。

## 规则
1. **A2A 协议实现**：
   - 事件驱动的 A2A 交互
   - 使用 Redis Streams 实现上下文管理
   - 结合 MCP（Model Context Protocol）进行模型上下文管理

2. **工具网关**：
   - 集成 Claude Code 的 hooks 和 mailbox 设计
   - 引入工具调用（skill、func、mcp）机制

3. **上下文管理**：
   - 使用 Redis Streams 实现可靠的消息队列
   - 结合记忆机制（memory）和上下文外置（context offloading）

4. **运行时机制**：
   - 沙箱隔离（sandbox）
   - 浏览器使用（browser usage）
   - 长程任务遵循度保证（long-term task adherence）

5. **自进化机制**：
   - 配套的测试和评估框架
   - 进化方向把控和可控性保证

## 例外
- 当前实现未覆盖完整的 A2A 和 MCP 协议，仅实现核心子集（A2A-lite）
- 自进化机制尚未完全实现，仍需进一步开发和验证

## 检查清单
1. 验证 A2A 协议实现是否满足事件驱动和常驻需求
2. 确认 Redis Streams 是否正确实现上下文管理
3. 检查工具网关是否集成 Claude Code 的 hooks 和 mailbox 设计
4. 验证运行时机制是否满足沙箱隔离和浏览器使用需求
5. 确保自进化机制的测试和评估框架已初步实现
