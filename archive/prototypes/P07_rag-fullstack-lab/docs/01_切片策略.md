# L01 · 文档切片（Chunking）：决定召回天花板的环节

> 一句话定位：**切片是 RAG 中最被低估、影响最大的环节。**切错了，后面再炫的技术都救不回来。
> 在本项目对应：[pipeline/ingest.py](../pipeline/ingest.py) · `ingest.strategy` 配置

## 🎯 学完你应该能

- 讲清楚为什么"切多大"是个 trade-off
- 区分 fixed / structural / semantic / parent-child / contextual 五种切片范式
- 知道你的语料应该用哪种切法（不再无脑 512）

---

## 1. 一个能让你立刻明白的失败 case

假设有这么一段文档：

```markdown
## R72 Agent 记忆系统横评

工作记忆负责短期上下文，由 LLM context window 直接承载。
情节记忆存储具体交互历史，常用 vector store 实现。
语义记忆存储抽象事实，可用 KG 或 embedding 表达。
程序记忆存储"如何做"，对应 Skill 系统。
```

你用 **fixed 512 字符**切片，恰好切在了"情节记忆"那一行：

```
chunk1 结尾：…工作记忆负责短期上下文，由 LLM context window 直接承载。情节记忆存
chunk2 开头：储具体交互历史，常用 vector store 实现。语义记忆存储抽象事实…
```

用户问："情节记忆是什么？"

🤬 **chunk1 没说完，chunk2 没头没尾，向量检索两个都召不回**——召回失败的根本原因不是 embedding 弱，是**切片把答案撕碎了**。

这就是 80% 的"我们 RAG 不准"问题的真相。

## 2. 切片的 5 种范式（从笨到聪明）

### 范式 A · Fixed 固定窗口（baseline）

最暴力。按字符或 token 数滑窗，带 overlap 减少边界丢失。

```python
# pipeline/ingest.py
def chunk_fixed(text, source, *, size=512, overlap=64):
    for i, start in enumerate(range(0, len(text), size - overlap)):
        yield text[start:start + size]
```

**适合**：纯文本（小说、新闻），无明显结构
**缺陷**：会切断语义单元（如上面的 case）

### 范式 B · Structural 结构感知（推荐起点）

按文档天然结构切：Markdown 的标题层级、HTML 的标签、PDF 的章节。

```yaml
# configs/v1_hybrid.yaml 起就用这种
ingest:
  strategy: markdown_header
  max_size: 1500
```

我们的实现保留了**标题路径**作为元数据，例如：
```
chunk.metadata = {"header_path": "R72 > 记忆类型 > 情节记忆"}
```

**为什么强**：
- 同一章节内的内容大概率语义相关，整段保留不撕碎
- 标题路径本身就是检索信号（向量检索时会编码进去）
- 父子关系天然存在 → 后续 parent-doc 直接能用

**适合**：结构化文档（你的 reports/、tutorial/、API doc、Wiki）
**缺陷**：纯文本无标题就退化成 fixed

### 范式 C · Semantic 语义切分

用 embedding 检测段落间的语义跳跃点，自动找切片边界。

```python
# 伪代码
sentences = split_by_punctuation(text)
embeds = embedder.encode(sentences)
for i in range(1, len(sentences)):
    sim = cosine(embeds[i], embeds[i-1])
    if sim < 0.7:  # 语义跳跃 → 切开
        yield current_chunk
        current_chunk = []
```

**适合**：无结构但有清晰话题边界的长文（访谈记录、论坛帖子）
**缺陷**：贵（要先 embed 一遍才能切），且对阈值敏感
**P07 状态**：暂未实现，欢迎贡献。LangChain 的 SemanticChunker 是参考实现。

### 范式 D · Parent-Child（小召回，大上下文）

切两套：
- **Child chunk**（小，~200 字）：用来 embedding 和检索
- **Parent chunk**（大，~1500 字）：检索命中 child 后，**实际喂给 LLM 的是 parent**

为什么有效？
- Child 小 → 向量更聚焦，召回精度高
- Parent 大 → LLM 看到完整上下文，不至于断章取义

P07 的简化实现：用 markdown_header 切片 + `compress.mode: parent_doc`，自动按 source 文件去重，相当于"小 chunk 召回，大文件上下文"。完整 parent-child 映射留待生产化。

### 范式 E · Contextual Retrieval（Anthropic SOTA）

> 这是 2024 年 9 月 Anthropic 提出的范式。声称把 top-20 召回失败率降低 49%。

每个 chunk 在 embedding **之前**，先用 LLM 给它生成 50-100 字的"上下文说明"：

```
原 chunk: "营收同比增长 3%。"

加上下文：
"以下内容来自 R34 报告关于 Hermes 项目 2024 Q3 表现的章节。
营收同比增长 3%。"
```

为什么有效？因为原 chunk 单独看不知道**说的是哪家公司、哪个季度**——加上上下文，向量编码就锚定到正确语境了。

代价：每个 chunk 要调一次 LLM。Anthropic 用 Prompt Caching 把成本压到原来的 1/10。

**P07 状态**：[docs/20_ContextualRetrieval.md](20_ContextualRetrieval.md) 重点待写章节。

## 3. 怎么选？决策树

```
你的文档...
├── 有清晰的标题/章节结构？（Markdown / HTML / 论文）
│   ├── 是 → Structural（P07 默认推荐）
│   └── 否 ↓
├── 是长文本但有自然段落？（小说 / 访谈）
│   └── Semantic（精度好，贵）
├── 是高价值检索场景？且能承担 LLM 调用成本？
│   └── Contextual（最强，最贵）
└── 简单原型 / 数据量小 / 没耐心调？
    └── Fixed 512 + overlap 64 起步
```

**实战 Top 推荐**：先用 Structural 起步 → eval 看看哪些题召回失败 → 看失败 case 是否因为 chunk 单独看缺上下文 → 再决定要不要上 Contextual。

## 4. 怎么调 chunk_size？

这是初学者最常问的问题。**没有银弹**，但有 trade-off：

| chunk_size | 召回精度 | 信息完整性 | 何时合适 |
|---|---|---|---|
| 128-256 | ⬆️ 高 | ⬇️ 低，容易断 | 短回答场景（FAQ） |
| 512 | 中 | 中 | 通用 baseline |
| 1024-1500 | ⬇️ 低（内含太多噪声） | ⬆️ 高 | 长上下文回答（综述） |
| 3000+ | ❌ 几乎不能用 | 太大稀释关键信息 | 不推荐 |

**亲手测**：
```bash
# 改 configs/baseline.yaml 里的 ingest.size，跑 eval
# 把 [256, 512, 1024] 各跑一遍，画出 size-pass_rate 曲线
```

你会发现曲线是**倒 U 形**——这是 RAG 工程师的基本功。

## 5. 避坑指南

| 坑 | 现象 | 解法 |
|---|---|---|
| 直接用 LangChain 的 RecursiveCharacterTextSplitter 不调参 | chunk 大小不均匀，有的 50 字有的 800 字 | 显式指定 separators 和 chunk_size |
| Markdown 标题切片但忘记保留 header_path | 召回到一段"营收增长 3%" 不知道说哪家公司 | metadata 必须存 header_path |
| Overlap 设太大（如 256/512） | 索引膨胀 1 倍，相同内容反复出现 | overlap 不超过 chunk_size 的 15% |
| 中文按 token 切片用错 tokenizer | 切在汉字中间，乱码 | 中文按字符切，或用 jieba 分词后按词切 |
| 表格被切散 | 表头和数据行分到两个 chunk | 切片前预处理：表格转 Markdown 并整段保留 |

## 6. 在 P07 里立刻验证

```bash
# 1. baseline 用 fixed
python eval/run_eval.py -c configs/baseline.yaml

# 2. 切到 v1_hybrid（仅切片改成 markdown_header，其他不变）
python eval/run_eval.py -c configs/v1_hybrid.yaml

# 3. 对比看哪些 case 因为切片改善
python eval/run_eval.py --compare configs/baseline.yaml configs/v1_hybrid.yaml
```

**重点观察**：哪些题在 v1 变好了？大概率是那些答案跨段的 case——结构化切片让答案不再被撕碎。

## 7. 与生产的距离

| P07（教学） | 生产环境 |
|---|---|
| 单进程切片 | Spark / Ray 分布式切片 |
| 切完直接灌库 | 切完先去重（hash）、过滤短文（< 50 字）、敏感数据脱敏 |
| 全量重建 | 增量切片（仅处理 mtime 改变的文件） |
| 文本-only | 还要切表格、图、代码块（各自单独索引） |
