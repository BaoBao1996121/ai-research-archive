# L22 · 评估体系：怎么知道你的 RAG 真的变好了

> 一句话定位：**没 eval 的 RAG 调优，全是错觉。** 这一篇讲清楚 RAG 该测什么、怎么测、怎么读结果。
> 在本项目对应：[eval/eval_set.yaml](../eval/eval_set.yaml) · [eval/run_eval.py](../eval/run_eval.py)

## 🎯 学完你应该能

- 区分检索质量和生成质量两类指标，知道各自在量什么
- 会写 eval case（用 P07 的 yaml 格式）
- 解读 P07 的对比报告，找出"为什么变好/变坏"

---

## 1. RAG 评估的两层结构

```
┌─────────── 检索质量（Retrieval Metrics） ───────────┐
│  Hit@K       前 K 个结果中是否包含相关文档           │
│  MRR         相关文档排名的倒数（越小越好被排名前）  │
│  Recall@K    召回了多少比例的相关文档                │
└──────────────────────────────────────────────────────┘
                          │
                          ▼ 假设检索没问题
┌─────────── 生成质量（Generation Metrics） ──────────┐
│  Faithfulness   答案是否忠于检索到的资料（不胡编）   │
│  Answer Relev.  答案是否切题                          │
│  must_contain   关键事实是否提及（最简单的硬断言）    │
└──────────────────────────────────────────────────────┘
```

**为什么要分两层**：当一个 case 答错时，你必须知道是**召回错了**（资料根本没找对）还是**生成错了**（资料对但 LLM 答歪了）——两种问题修法完全不同。

---

## 2. P07 的评估指标

P07 实现了三类，覆盖最常用的：

### must_contain（硬断言）
```yaml
must_contain: ["Profile", "Strategy", "Execute", "Verify"]
```
答案中必须包含所有这些字符串。简单粗暴但**有效**——它直接对应"用户能否从答案中得到关键事实"。

### ground_truth_keywords（关键词召回率）
```yaml
ground_truth_keywords: ["psev", "画像", "策略", "执行", "验证"]
```
不要求全部命中，算覆盖比例。比 must_contain 更宽松，适合多种正确答案的开放题。

### LLM-as-judge（软质量）
```python
JUDGE_PROMPT = """请按 0-5 分评估候选回答相对于参考答案的质量。
评分维度：正确性 / 完整性 / 不胡编"""
```
让另一个 LLM 当法官打分。建议用**比生成模型更强的模型当 judge**（如 qwen3.6:35b 给 qwen3:8b 打分），减少"自己人帮自己人"的偏差。

### 还差什么（建议你扩展）

P07 当前没实现的，但生产应该补：

| 指标 | 怎么实现 |
|---|---|
| **Hit@K** | eval_set 里加 `ground_truth_docs`，跑完看 retrieved_docs 命中率 |
| **MRR** | 算 ground_truth_docs 在 retrieved_docs 中第一次出现的位置倒数 |
| **Faithfulness（RAGAS 风格）** | LLM judge 多一维：「这段答案中的事实是否在 context 里能找到？」 |
| **回答延迟** | 跑 eval 时记录 t0/t1，画 P50/P95 latency |

## 3. 一份合格 eval 集长什么样

P07 的种子集 12 条，作为起点。**生产建议至少 50-100 条，覆盖 4 类难度**：

| 类别 | 占比 | 作用 |
|---|---|---|
| Easy（事实题） | 30% | 防回归：基础能力别退化 |
| Medium（概念题） | 30% | 主战场：大多数提升体现在这里 |
| Hard（跨文档综合） | 25% | 考验顶尖配方 |
| Adversarial（无答案陷阱） | 15% | 防幻觉：能否说"我不知道" |

**写好 case 的 3 个原则**：
1. **答案明确**：你能脑补出正确答案，否则没法评判
2. **must_contain 选关键词**：选**最稀有最具区分度**的词，避免无意义关键字（如"是"、"的"）
3. **Adversarial 必须有**：故意问知识库里没有的，看 RAG 会不会幻觉

## 4. 怎么读对比报告

P07 的 `--compare` 输出：

```
变好: 4   变坏: 1   持平: 7
通过率 58.3% → 75.0%
Judge  3.2 → 4.1

变好的 case:
  ✅ q004 (Hybrid 召回那道)
  ✅ q006 (Contextual 救的那道)
  ...

变坏的 case（必须看！）:
  ❌ q010 (HyDE 把假答案带偏的那道)
```

**重点是变坏的那 1 条**——总分提升不代表所有题都变好。**RAG 调优最大的陷阱：拿到总分提升就开心地合并，没注意某一类题悄悄变烂了**。

## 5. 在 P07 里立刻动手

```bash
# 1. 跑 baseline 拿初分
python eval/run_eval.py -c configs/baseline.yaml

# 2. 看 eval/results/ 下生成的 json，研究每条 case 的判定原因

# 3. 改 configs/baseline.yaml 任意一行（如 ingest.size: 256）

# 4. 再跑，对比
python eval/run_eval.py --compare configs/baseline.yaml configs/baseline.yaml
# (如果两个配置文件相同会报错，用 cp baseline.yaml mytest.yaml 改后再跑)
```

## 6. CI Gate：把 eval 卡进流水线

```bash
# 1. 锁定 baseline
python eval/run_eval.py -c configs/baseline.yaml
cp eval/results/baseline_*.json eval/baseline_locked.json

# 2. 改动后跑 gate 检查
python eval/run_eval.py -c configs/v1_hybrid.yaml --gate eval/baseline_locked.json --threshold 0.05
```

任何**通过率下降 > 5%** 或 **judge 平均分下降 > 0.3** 都会让脚本 exit 1，可直接挂 GitHub Actions / pre-commit。

这就是 EDD（Evaluation-Driven Development）在 RAG 上的落地。

## 7. 避坑指南

| 坑 | 现象 | 解法 |
|---|---|---|
| eval 集太小（< 10 条） | 单条波动就翻盘，无法判断 | 至少 30 条；理想 100+ |
| 全部 easy 题 | baseline 就 95% 通过，没区分度 | 必须放 30%+ 难题 |
| 没 adversarial | 系统幻觉严重但 eval 一片绿 | 加无答案陷阱题 |
| judge 用自己生成的模型 | 偏向自己 | 用更强或不同家的模型当 judge |
| 总分变好就合并 | 某些 case 悄悄变坏 | 必须看 per-case diff |

## 8. 与生产评估框架的关系

| 框架 | 关系 |
|---|---|
| **RAGAS** | RAG 专门评测库。Faithfulness / Answer Relev / Context Precision / Recall 四指标 |
| **TruLens** | 三件套（answer/context/groundedness）+ 在线监控 |
| **DeepEval** | RAG 评测 + 单测风格集成 |
| **P07** | 教学骨架。学完后可平滑迁移到 RAGAS（指标兼容） |

P07 没用现成框架是为了让你**亲手实现**评估逻辑，理解每个指标在算什么。生产推荐 RAGAS。
