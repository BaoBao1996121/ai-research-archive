# L00 · RAG 导论：为什么需要 RAG，以及它到底在解决什么

> 一句话定位：RAG = 让 LLM 在回答前先去**外部知识库找资料**，把"靠记忆答题"变成"开卷考试"。

## 🎯 学完你应该能

- 区分 RAG 和微调（Fine-tuning），知道什么时候用哪个
- 用三个词概括 RAG 的核心：**Retrieve → Augment → Generate**
- 理解 RAG 全链路 8 个环节各自在解决什么子问题

---

## 1. 一个让你立刻明白的失败 case

直接问 GPT-4：「PSEV 框架的四个阶段分别是什么？」

它会怎么答？

- ❌ 一种可能：编一套看似合理但完全错的解释（**幻觉**）
- ❌ 另一种可能："我不知道你说的 PSEV 是什么"（**知识缺失**）
- ❌ 第三种可能：把它和 PSE-V 等其他名字混淆（**张冠李戴**）

为什么？因为 PSEV 是这个工作区**自己的方法论**，不在任何 LLM 的训练数据里。

LLM 的知识来自训练。训练数据有三大限制：
1. **时效**：截止某个日期，之后的事一无所知（你的 Qwen3.6 是 2026-04 才发布的，3 月训练的模型不会知道）
2. **私有**：你的公司文档、内网知识、最新的项目代码模型都没见过
3. **长尾**：训练里出现 1 次和出现 1000 次的概念，模型记忆牢固度天差地别

**RAG 就是给 LLM 装一个外接 U 盘。**

---

## 2. RAG 是什么：三个动作

```
                 ┌──── Retrieve ────┐
   你的问题 ───→ │   去知识库找资料  │ ──→ 找到几段相关文本
                 └──────────────────┘
                          │
                          ▼
                 ┌─── Augment ──────┐
                 │  把资料拼到 prompt│
                 └──────────────────┘
                          │
                          ▼
                 ┌──── Generate ────┐
                 │  LLM 基于资料作答 │
                 └──────────────────┘
```

就这么简单。但**简单的概念，落地时每一步都是坑**——这就是为什么有 P07 这个项目要把每一步拆开来做实验。

---

## 3. RAG vs Fine-tuning：什么时候用哪个

| 场景 | 用 RAG | 用 Fine-tuning |
|---|---|---|
| 知识会经常更新 | ✅ 改文档即可 | ❌ 每次都要重训 |
| 知识规模大（GB 级） | ✅ 检索就行 | ❌ 训练数据量爆炸 |
| 需要**精确**事实（数字、名字、引用） | ✅ 直接给原文 | ❌ 模型仍会幻觉 |
| 需要追溯来源 | ✅ 能给出 [来源1] | ❌ 黑盒 |
| 需要改变模型的**风格** | ❌ Prompt 调不动 | ✅ 这是 FT 的强项 |
| 需要教会模型新的**能力** | ❌ RAG 只补充事实 | ✅ 例如新指令格式 |
| 有海量标注数据 | 可不用 | ✅ 数据是燃料 |

**实战经验**：90% 的「让 LLM 用我们公司知识答题」需求，正确解法是 RAG，不是 FT。
但二者并不互斥——**优秀方案常常是 FT 一个领域 base 模型 + RAG 喂实时知识**。

## 4. RAG 全链路 8 环节速览

每一环都对应 P07 里一个可独立替换的模块：

| # | 环节 | 解决什么子问题 | 不做好会怎样 |
|---|---|---|---|
| ① | **Ingest 切片** | 长文档怎么切成 LLM 能装下的小块？ | 切错了 → 答案被劈成两半，永远召不全 |
| ② | **Embed 嵌入** | 文本怎么变成可比较的向量？ | 嵌入弱 → 语义近的找不到 |
| ③ | **Index 索引** | 几百万向量怎么快速检索？ | 索引慢 → 查询要等 5 秒 |
| ④ | **QueryTransform 改写** | 用户问题措辞和文档措辞不一致怎么办？ | 不改写 → 长尾问题召回失败 |
| ⑤ | **Retrieve 召回** | 用什么策略找到 top-k？ | 仅 dense → 术语/缩写/人名召不回 |
| ⑥ | **Rerank 重排** | 召回 top-50 中哪 5 个最相关？ | 不重排 → 相关文档排在 50 名外 |
| ⑦ | **Compress 压缩** | 怎么把召回的多段文本喂给 LLM？ | 直接拼 → context 太长，关键信息被稀释 |
| ⑧ | **Generate 生成** | 怎么让 LLM 严格依据资料答题？ | prompt 弱 → LLM 又开始幻觉 |

> 🎓 RAG 工程师的核心能力 = **能定位问题出在哪个环节，并知道该用哪个工具修复**。
> 这个项目就是让你把这种能力练出来。

## 5. 三个真相，决定你的 RAG 是好是烂

### 真相 1：垃圾进，垃圾出（Garbage In, Garbage Out）

如果切片切错了，后面再炫酷的 reranker 也救不回来。**Ingest 决定了召回的天花板。**

### 真相 2：召回是 RAG 的 80% 难度，生成只是 20%

LLM 已经够强了——只要给它正确的资料，它基本不会答错。
**RAG 系统的失败 90% 是召回失败，不是生成失败。** 这就是为什么 P07 把召回相关的环节做了 5 个（②③④⑤⑥）。

### 真相 3：评估是 RAG 的灵魂

没有 eval 集，所有"我感觉这个改进有效"都是错觉。
**EDD（Evaluation-Driven Development）= 写改动前先有 eval。** P07 内置 eval 引擎和 12 条种子 case，逼你养成这个习惯。

## 6. 在 P07 里跑通你的第一个 RAG

```bash
cd prototypes/P07_rag-fullstack-lab
.\.venv\Scripts\Activate.ps1
python run.py -c configs/baseline.yaml -q "PSEV 框架是什么？"
```

你会看到：
1. 系统先去索引找到相关 chunks（带分数和来源）
2. 把 chunks 拼成 context 喂给 qwen3:8b
3. LLM 输出答案

第一次跑会下载 bge-m3 模型（~2GB）+ 建索引（~3min）。后续秒级。
