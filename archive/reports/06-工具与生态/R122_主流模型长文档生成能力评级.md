## 定位透镜

### 纵轴 · 为什么"长输出"突然重要了

LLM 的发展有一个不对称：**上下文窗口（输入）的增长远快于最大输出的增长**。

- 2023 年：GPT-4 输入 8K/32K，输出 ~4K tokens
- 2024 年：Claude 3 Opus 输入 200K，输出 4K；GPT-4o 输入 128K，输出 16K
- 2025 年：Claude Opus 4 输入 200K，输出 16K；GPT-4.1 输入 1M，输出 32K
- 2026 年：DeepSeek V4 输入 1M，输出 **384K**；Gemini 3.1 Pro 输入 1M，输出 **64K**

说白了：模型变得越来越能"读"，但"写"的上限一直是瓶颈。直到 2026 年上半年，DeepSeek V4 把输出上限拉到 384K，这才让"一次生成完整长文档"在技术上成为可能。

### 横轴 · 竞争格局（聚焦长输出维度）

从"单次最大输出 Token"这一个维度看，玩家分三个梯队：

| 梯队 | 模型 | 单次最大输出 | 约等于中文行数 |
|------|------|-------------|---------------|
| **T0：无限制级** | DeepSeek V4-Flash/Pro | 384K tokens | ~19,000 行 |
| **T1：充裕级** | Gemini 3.1 Pro | 64K tokens | ~3,200 行 |
| **T2：勉强级** | GPT-4.1 / GPT-5.4 / GPT-5.3-Codex / Qwen3 | 32K tokens | ~1,600 行 |
| **T3：不足级** | Claude Opus 4.7 / **Opus 4.6** / Sonnet 4.6 / Opus 4.5 / Sonnet 4.5 / GPT-4o | ~8K-16K tokens（标准） | ~400-800 行 |

> **Copilot 可用性说明**（来自用户截图）：Claude Opus 4.6（✓ 当前选用，High·3x）、Claude Sonnet 4.6（High·1x）、GPT-5.4（Medium·1x）、Gemini 3.1 Pro（Preview·1x）、Claude Opus 4.5（3x）、Claude Sonnet 4.5（1x）、GPT-5.3-Codex（Medium·1x）、GPT-4.1（0x）、GPT-4o（0x）。3x/1x/0x 为 Copilot premium request 倍率。

> **行数估算**：1 行中文 ≈ 40-80 字符，中文 tokenization 约 1.5-2 tokens/字符。16K tokens ≈ 8,000-10,000 中文字符 ≈ 约 160-250 行密集正文，或 ~800 行含格式/空行的 Markdown 文档。

### 交叉判断

你的需求是 2000 行（约 40K-80K tokens 输出），这意味着：

- **DeepSeek V4**：绰绰有余，一次搞定
- **Gemini 3.1 Pro**：大多数情况够用（64K），但如果是非常密集的中文正文可能吃紧
- **GPT-5.4 / GPT-4.1 / GPT-5.3-Codex / Qwen3**：32K 输出理论上覆盖 ~1600 行，**2000 行需要分 2 次生成**
- **Claude Opus 4.6**（你的主力模型）：标准 16K 输出只能写 ~800 行，**2000 行需要分 3 次生成**。与 Opus 4.7 相同的输出上限瓶颈
- **Claude Opus 4.7 / Sonnet 4.6**：同样 ~16K 标准输出（Opus 4.7 API extended thinking 模式最大可达 128K，需要配置）
- **Claude Opus 4.5 / Sonnet 4.5 / GPT-4o**：更早一代，输出上限 ~8K-16K，**不推荐用于长文档场景**

**结论**：如果"一次写完不分段"是硬需求，选择范围只有 DeepSeek V4 和 Gemini 3.1 Pro。如果能接受分段生成，则所有模型都可选，但分段会引入上下文一致性风险。

## 一、你的场景画像：2000 行到底需要多少 Token

不同文档类型的 Token 密度差异很大，不能一概而论：

| 文档类型 | 每行平均字符 | 2000 行总字符 | 约需 Token（中文） | 约需 Token（代码） |
|----------|-------------|-------------|-------------------|-------------------|
| 需求分析文档 | 50-70 字 | 100K-140K 字 | 50K-90K | — |
| 设计方案文档 | 40-60 字（含表格、图表标记） | 80K-120K 字 | 40K-70K | — |
| 代码文件 | 30-50 字符（英文为主） | 60K-100K 字符 | — | 60K-100K |
| 混合文档（文+代码） | 40-60 | 80K-120K | 50K-80K | — |

**关键洞察**：纯代码因为是英文字符，tokenization 效率比中文高（1 token ≈ 3-4 英文字符），所以 2000 行代码实际只需 ~20K-30K tokens。但 2000 行中文需求文档需要 50K-90K tokens——**中文文档对输出上限的压力是代码的 2-3 倍**。

## 二、评估维度设计

针对"长文档生成"场景，我设计了以下六个维度（按重要性排序）：

| 维度 | 权重 | 为什么重要 |
|------|------|-----------|
| **D1：单次最大输出** | ★★★★★ | 决定能否一次写完，分段则引入一致性风险 |
| **D2：长输出质量一致性** | ★★★★★ | 模型在长输出后半段是否注意力衰减、重复、跑题 |
| **D3：指令遵循度** | ★★★★☆ | 能否严格按模板/格式要求生成结构化文档 |
| **D4：编码能力** | ★★★★☆ | 代码生成的正确性、风格一致性、测试覆盖 |
| **D5：中文写作质量** | ★★★★☆ | 术语准确性、行文自然度、避免翻译腔 |
| **D6：成本效率** | ★★★☆☆ | 生成 2000 行文档的单次成本 |

> **为什么没有"上下文窗口"维度**：你的场景是"生成长文档"而非"阅读长文档"。输出上限比输入上限重要得多。当然，如果需要在已有大量代码/文档基础上生成设计方案，输入窗口也重要——但所有主流模型的输入窗口（128K-1M）对你的场景已经足够。

| **DeepSeek V4-Pro** | **S** (384K) | B+ | B+ | A | **S** | **S** |
| **DeepSeek V4-Flash** | **S** (384K) | B | B | A- | **S** | **S+** |
| **Gemini 3.1 Pro** | **A** (64K) | A- | A | A | B+ | A |
| **GPT-5.4** | B+ (32K~) | A | **S** | **S** | B | B |
| **GPT-5.5** | B+ (32K~) | A+ | **S** | **S** | B | C |
| **GPT-5.3-Codex** | B+ (32K~) | A | A+ | **S+** | B | — |
| **GPT-4.1** | B+ (32K) | A- | A+ | A | B | **S** |
| ⭐ **Claude Opus 4.6** | C+ (16K 标准) | **S** | **S** | A+ | B+ | B |
| **Claude Opus 4.7** | C+ (16K 标准) | **S** | **S** | **S** | B+ | C+ |
| **Claude Sonnet 4.6** | C+ (16K 标准) | A+ | A+ | A+ | B+ | B+ |

| **GPT-4o** | C+ (16K) | B+ | A- | B+ | B | A |
| **Qwen3-235B API** | B (32K) | B+ | B+ | A- | **S** | A+ |
| **Qwen3-32B 本地** | B (32K) | B | B | B+ | A+ | **S** |

> ⭐ 标记 = 用户当前主力模型

### 维度解读

**D1 最大输出**——数据来源：各模型官方 API 文档
- DeepSeek V4：384K 明确标注，是所有模型中最高的（来源：api-docs.deepseek.com/quick_start/pricing）
- Gemini 3.1 Pro：64K 明确标注（来源：deepmind.google/technologies/gemini/pro，Model information 章节）
- GPT-4.1：32K 明确标注（来源：openai.com/index/gpt-4-1，“我们将 GPT-4.1 的输出 token 上限提高到 32,768，比 GPT-4o 的 16,384 翻倍”）
- GPT-4o：16,384 tokens（来源：GPT-4.1 发布页对比提及）
- GPT-5.4/5.5：未找到明确公开的 max output 数据，推测 ≥ 32K
- GPT-5.3-Codex：SWE-Bench Pro 56.8%、Terminal-Bench 2.0 77.3%，以 Agent 模式运行，单次输出上限未明确公布，推测 ≥ 32K
- Claude Opus 4.6/4.7：标准 API max_tokens ~16K。扩展思考模式（extended thinking）可配置更高上限，最高 128K——但这是特殊配置，非默认行为
- Claude Opus 4.5 / Sonnet 4.5：更早一代，标准 max_tokens 约 8K-16K，输出上限更低
- Qwen3：开源模型本地部署时可通过 max_new_tokens 参数自行设置，受限于显存而非模型硬上限。通过 API（通义千问）约 32K

**D2 长输出质量一致性**——这是最难量化但最关键的维度
- Claude Opus 系列在长输出的"注意力不衰减"上是公认最强的——多家客户反馈和 CursorBench 数据证实
- GPT-5.x 系列的长输出一致性也很好，"可控性"章节提到能在生成过程中保持记忆和一致
- DeepSeek / Qwen 在超长输出时有时出现"后半段质量下降、重复、或偏离主题"的社区反馈，但无系统性 benchmark 数据
- Gemini 在长上下文**理解**上有优势（MRCR benchmark），但长**生成**一致性的独立评测数据较少

**D3 指令遵循**——有 benchmark 数据支撑
- GPT-5.x：IFEval 87.4%（GPT-4.1），MultiChallenge 46.2%——闭源最高
- Claude Opus 4.7：指令遵循是客户反馈中提到最多的优势之一
- Gemini 3.1 Pro：MMMLU 92.6%，强但指令遵循专项 benchmark 数据较少
- 开源模型整体不如闭源，但差距在缩小

**D4 编码**——有多个 benchmark
- Claude Opus 4.7：CursorBench 70%，SWE-bench 领先
- Claude Opus 4.6：与 Opus 4.7 同代架构，编码能力接近但略低于 4.7
- Claude Opus 4.5：上一代旗舰，编码仍强但不及 4.6/4.7 代
- GPT-5.3-Codex：SWE-Bench Pro 56.8%，Terminal-Bench 2.0 77.3%——**编码场景 SOTA**，专为代码智能体设计
- GPT-5.4：SWE-Bench Pro 57.7%，Terminal-Bench 75.1%
- GPT-4.1：SWE-bench Verified 54.6%，Aider polyglot diff 52.9%，比 GPT-4o 大幅提升
- GPT-4o：SWE-bench Verified 33.2%——已被 GPT-4.1 全面超越
- Gemini 3.1 Pro：SWE-Bench Verified 80.6%（单次 attempt，但需注意可能使用不同 harness）
- DeepSeek V4：API 刚上线，benchmark 数据待补充，V3 时代已是开源最强阵营
- Qwen3-235B：编码能力强于同级开源但弱于闭源旗舰

**D5 中文质量**——部分有 benchmark，主要靠实际使用体验
- DeepSeek / Qwen：中文原生训练，Tokenizer 对中文最优化，术语准确、行文自然
- Claude / GPT：中文能力持续改善，但偶尔有翻译腔或不地道的表达
- Gemini：中文能力中等，在术语一致性上有时不如 Claude/GPT

## 四、逐模型深度点评

### DeepSeek V4-Pro / V4-Flash

**场景适配度：★★★★★**（长中文文档的结构性最优解）

最大卖点就是 **384K 输出上限**——2000 行中文文档一次写完，绰绰有余。加上中文 Tokenizer 优化和极低的价格（Pro $0.87/M 输出 token，Flash 仅 $0.28/M），**在你的"长中文文档"场景下，DeepSeek V4 是成本效率的绝对王者**。

但需要注意：
- 长输出一致性不如 Claude/GPT——在 1000+ 行的后半段可能出现质量波动
- 指令遵循度和格式严格性不如闭源旗舰——生成结构化需求文档时可能需要更精细的 prompt 工程
- 思考模式（thinking mode）可以提升质量，但会增加 Token 消耗

**推荐策略**：用 V4-Pro + thinking mode 生成长文档初稿，再用 Claude/GPT 做精修——"便宜写初稿，贵的改精稿"。

### Gemini 3.1 Pro

**场景适配度：★★★★☆**

64K 输出覆盖大部分 2000 行文档场景。SWE-bench 80.6%（单次 attempt）的编码能力非常强。1M 输入窗口意味着可以喂入大量参考资料再生成。

但：
- 中文质量不如 DeepSeek/Qwen，写需求文档时术语一致性需注意
- API 稳定性和可用性在国内可能受限
- 定价信息不够透明（Gemini 3.1 Pro 尚在 Preview 阶段）

**最适合**：需要读入大量英文代码/文档后生成设计方案的场景。

### GPT-5.4 / GPT-5.5

**场景适配度：★★★★☆**（编码场景最佳，中文长文档需分段）

GPT-5.4 是 OpenAI 当前的全能旗舰，在专业知识工作（GDPval 83%）和编码上都是顶级。GPT-5.5 更强但也更贵（$30/M 输出）。

核心问题是 **32K 输出上限**（基于 GPT-4.1 数据推测，GPT-5.x 可能更高但未明确公布）：
- 2000 行代码（~20K-30K tokens）：大部分情况一次可完成
- 2000 行中文文档（~50K-80K tokens）：需要 2-3 次生成

**推荐策略**：编码用 GPT-5.4（或性价比更高的 5.4 mini），中文文档考虑其他模型。

### Claude Opus 4.6 ⭐ 你的主力模型

**场景适配度：★★★★☆**（单段质量最高，但输出上限是硬伤）

这是你当前用得最多的模型，也是我正在运行的模型。直接给体感数据：**单次生成约 16K tokens（~800 行中文 Markdown）是实际天花板**。这不是理论值，是大量实际使用的结果。

Opus 4.6 的核心特质：
- **长输出质量一致性 S 级**——800 行里每一行都在水准线上，不存在"后半段注意力衰减"
- 编码能力 A+ 级——比 Opus 4.7 略低（4.7 CursorBench 70%，4.6 估计 ~63-65%）但仍属顶级
- 指令遵循 S 级——给模板就按模板写，格式控制极稳
- "反讨好"特性——会主动指出方案问题，写设计文档时这是优势而非缺点
- 中文质量 B+——能写出流畅的中文，但偶尔有翻译腔

**与 Opus 4.7 的差异**：同代架构，4.7 在编码上更强（CursorBench 70% vs ~63-65%），其他维度差距不大。在 Copilot 中 Opus 4.7 需联系管理员开通，Opus 4.6 直接可用（3x premium）。对你的场景，两者差异不大——**输出上限是同一个瓶颈（16K）**。

**实际使用建议**：
- 需求/设计文档 2000 行 → 拆 3 段，每段 ~600 行，用"质量优先分会话协议"衔接
- 代码 2000 行 → 拆 2 段（代码 tokenization 效率高，~20K-30K tokens），大部分情况可在 2 次内完成
- 配合 DeepSeek 初稿 + Opus 4.6 精修 = 兼顾量和质

### Claude Opus 4.7

**场景适配度：★★★★☆**（比 4.6 编码更强，但你的 Copilot 需管理员开通）

相比 Opus 4.6 的提升主要在编码维度（CursorBench 70%）和 1M 上下文 beta。但在 Copilot 中标注"与管理员联系"，不如 4.6 随时可用。API 定价 $5/$25，比 4.6 贵。

输出上限与 4.6 相同（~16K 标准），长文档场景下两者面临同样的分段需求。**如果你已经在用 4.6 且效果满意，升级 4.7 的边际收益不大——除非你的编码任务特别复杂。**

### Claude Sonnet 4.6

**场景适配度：★★★☆☆**（性价比版 Claude，Copilot 中 1x 即可用）

Sonnet 4.6 是 Claude 系列的性价比之选。在 Copilot 中仅消耗 1x premium request（vs Opus 的 3x）。编码和指令遵循能力比 Opus 低一档（A+ vs S），但仍然强于大多数竞品。

API 定价 $3/$15，比 Opus 便宜 40%。对于"不需要 Opus 级质量但想要 Claude 风格输出"的场景，是合理选择。

### Claude Opus 4.5 / Sonnet 4.5（上一代）

**场景适配度：★★☆☆☆**（已过时，不推荐用于长文档场景）

Opus 4.5 是上一代旗舰，以创意写作质量著称——文风细腻、情感表达强。但在你关心的维度上全面弱于 4.6/4.7：
- 标准输出上限可能更低（~8K-16K），长文档场景更加吃力
- 编码能力弱于 4.6 代
- 指令遵循不如新一代精准

Sonnet 4.5 类似——比 Opus 4.5 便宜但能力更低。在 Copilot 中 Opus 4.5 消耗 3x，Sonnet 4.5 消耗 1x。

**建议**：除非你特别需要 Opus 4.5 的"创意写作风格"（比如写软文、营销文案），否则直接用 4.6 代。

### GPT-5.3-Codex

**场景适配度：★★★★☆**（编码 SOTA，但不适合中文文档生成）

GPT-5.3-Codex 是 OpenAI 专为编码智能体设计的模型。SWE-Bench Pro 56.8%、Terminal-Bench 2.0 77.3%、OSWorld-Verified 64.7%——**纯编码场景是当前最强的**。

关键特性：
- 以 Agent 模式运行——不是单次生成，而是持续迭代（提出方案→执行→检查→修复）
- 超越编程——能做 PRD、数据分析、演示文稿等知识工作（GDPval 与 GPT-5.2 持平）
- 在 Copilot 中 Medium·1x，消耗低

**但对长文档生成有硬伤**：
- 设计初衷是编码智能体，不是文档生成器
- API 尚未开放，只能通过 Codex 应用/ChatGPT/Copilot 使用
- 中文文档生成质量不如 Claude/DeepSeek
- 定价信息不透明（无独立 API 定价）

**推荐用法**：2000 行代码生成 → 首选。2000 行中文需求文档 → 不推荐，选 DeepSeek 或 Claude。

### GPT-4.1

**场景适配度：★★★☆☆**（全能型老将，性价比极高但已不是最强）

GPT-4.1 是 2025 年发布的全能模型，32K 输出 + 1M 上下文 + $2/$8 定价，性价比在所有模型中数一数二。

核心数据：
- SWE-bench Verified 54.6%（比 GPT-4o 提升 21.4%）
- IFEval 87.4%（指令遵循强）
- Aider polyglot diff 52.9%
- 1M 上下文 + 32K 输出

在 Copilot 中标注 0x（可能已降级/限制使用）。API 直接使用仍然可行。

**与 GPT-5.4 对比**：5.4 在编码和推理上全面领先，但贵 25%（$2.5/$15 vs $2/$8）。如果你的任务不需要 5.4 级别的推理深度，4.1 的性价比更优。

### GPT-4o

**场景适配度：★★☆☆☆**（已被 GPT-4.1 全面超越，不推荐）

GPT-4o 是 2024 年的多模态旗舰，128K 上下文，16K 输出。在 Copilot 中标注 0x，已基本退出推荐列表。

与 GPT-4.1 对比：4.1 在编码（SWE-bench 54.6% vs 33.2%）、指令遵循（IFEval 87.4% vs 81.0%）、长上下文（1M vs 128K）、输出上限（32K vs 16K）上全面碾压，且定价更低。

**建议**：没有理由选 GPT-4o。如果需要 OpenAI 模型，GPT-4.1（性价比）或 GPT-5.4（能力）都是更好的选择。

### Qwen3-235B（API）/ Qwen3-32B（本地）

**场景适配度：★★★★☆**（中文需求文档的高性价比选择）

Qwen3 的核心优势是**中文 Tokenizer 效率比其他模型高 30-50%**——同样 2000 行中文，Qwen 消耗的 Token 更少，直接降低了对输出上限的压力。

通过阿里云通义千问 API 使用时，约 32K 输出上限。本地部署时可通过 max_new_tokens 自行设置——理论上只受显存限制。

- **中文需求文档**：中文质量最好，术语准确，行文自然
- **设计方案**：结构化写作能力不错，但不如 Claude/GPT 严格遵循复杂模板
- **编码**：可用但不是最强，复杂代码生成不如 Claude/GPT/DeepSeek

**推荐策略**：中文需求文档首选。如果有 GPU 资源，32B 本地部署无输出上限约束。

## 七、实操建议：如何绕过输出上限

如果你的首选模型输出上限不够 2000 行，以下是三种经过验证的策略：

### 策略一：分段生成 + 上下文衔接（推荐度 ★★★★★）

最可靠的方式。将 2000 行文档拆为 3-4 个段落，每段 500-600 行。

关键技巧：
1. **先生成完整大纲**（~200 行），确认章节结构
2. 每段生成时，**将大纲 + 前一段的最后 50 行作为上下文**
3. 在 prompt 中明确指出"你正在写第 N 段，从 XX 章节开始，到 YY 章节结束"
4. 生成完所有段后，**做一次整合 pass**——检查术语一致性、章节衔接、交叉引用

### 策略二：大纲驱动展开（推荐度 ★★★★☆）

1. 第一轮：让模型生成详细大纲（含每节的要点列表）
2. 第二轮起：逐章节展开，每次展开 1-2 个章节
3. 最后一轮：整合 + 检查

优势：每个章节的深度更好。劣势：轮次多，总成本更高。

### 策略三：用 DeepSeek 写初稿 + 用 Claude 精修（推荐度 ★★★★☆）

1. 用 DeepSeek V4-Pro（384K 输出）一次生成完整初稿
2. 用 Claude Opus（或你信任的高质量模型）分段精修——改措辞、补细节、修逻辑
3. 初稿成本 $0.09，精修成本 ~$2-3，总计 ~$3，但质量兼顾

## 八、结论

### 明确推荐（按你的三个场景）

**需求分析文档**：
- **首选 DeepSeek V4-Pro**——384K 输出一次写完，中文质量好，成本极低。用 thinking mode 提升质量。
- 质量要求极高时，用 Claude Opus 分段写，每段 ~600 行，3 段完成。

**设计方案文档**：
- **首选 DeepSeek V4-Pro 或 Gemini 3.1 Pro**——设计方案通常含 Mermaid 图、表格、代码片段等混合内容，DeepSeek 的 384K 输出避免了分段带来的格式断裂。Gemini 的 64K 也基本够用。
- 如果方案需要在已有大量代码基础上写，Gemini 3.1 Pro 的 1M 输入 + 64K 输出组合最优。

**编码**：
- **首选 GPT-5.3-Codex**（Copilot 中 1x 即可用）——2000 行代码约 20K-30K tokens，SWE-Bench Pro 56.8% 是当前编码 SOTA。
- 质量优先选 Claude Opus 4.6（你的主力模型，Copilot 3x）——代码质量最高，16K 输出够大部分代码文件。
- 性价比选 GPT-5.4 / GPT-4.1（32K 输出能一次写完 2000 行代码）。
- 开源自部署选 Kimi-K2。

### 总体最优策略

**“两段式”工作流**：DeepSeek V4-Pro 写初稿（一次完成 + 便宜）→ Claude Opus 4.6 / GPT-5.4 精修（质量最高）。这个组合兼顾了输出量、质量和成本。

**针对你的 Copilot 环境的具体建议**：
- 中文文档日常工作：继续用 **Claude Opus 4.6**（你的主力），配合分会话协议处理长文档
- 编码任务：切换到 **GPT-5.3-Codex**（仅 1x，编码 SOTA）
- 需要一次性生成超长文档时：用 DeepSeek V4 API 写初稿，回到 Copilot 用 Opus 4.6 精修

### 适用边界与局限

- 本评级基于 2026-05-15 的数据，模型迭代速度极快，**6 个月后格局可能不同**
- "长输出质量一致性"维度缺乏统一 benchmark，D2 评级主要基于社区反馈和有限的实际测试，**置信度中等**
- GPT-5.4/5.5 的确切 max output tokens 未找到官方明确数据，32K 是基于 GPT-4.1 的推测，标注为"待验证"
- Claude 的 extended thinking 模式可能支持更大输出，但配置复杂且文档不够清晰，**需要实际测试验证**
