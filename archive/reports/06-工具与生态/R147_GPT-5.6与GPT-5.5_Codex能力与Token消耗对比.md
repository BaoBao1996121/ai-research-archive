# R147 · GPT-5.6 与 GPT-5.5：Codex 能力、Token 与使用策略

> 调研日期：2026-07-10  
> 定位：在 [R98_2026主流LLM大模型横评](R98_2026%E4%B8%BB%E6%B5%81LLM%E5%A4%A7%E6%A8%A1%E5%9E%8B%E6%A8%AA%E8%AF%84.md) 的 GPT-5.5 基线上，新增 GPT-5.6 Sol / Terra / Luna、Codex Token 费率、推理档位和速度模式对比。  
> 结论：原来的 `GPT-5.5 + xhigh（极高）+ fast（快速）` 不是性价比配置；建议默认改为 `GPT-5.6 Sol + high（高）+ standard（标准）`，日常任务进一步下沉到 `Terra + high/medium + standard`。

## 1. 30 秒结论

**GPT-5.6 的核心不是“同样能力多花 Token”，而是把模型档位、推理档位与并行模式拆开，并在多数长任务上提高每 Token 产出。**

- `GPT-5.6 Sol` 与 `GPT-5.5` 的 Codex 单位 Token 费率相同，但公开评测显示 Sol 在编码、计算机操作、专业工作和科学任务上多数更强。
- `GPT-5.6 Terra` 的单位费率是 GPT-5.5 的 50%，多项 Coding Agent 评测达到或略超 GPT-5.5，适合做默认工作模型。
- `GPT-5.6 Luna` 的单位费率是 GPT-5.5 的 20%，多数常规任务可用，但复杂工具调用、超长上下文和高难度推理存在明显天花板。
- `xhigh` 会增加内部推理 Token；`max` 比 xhigh 更激进，应只给真正困难且可验证的任务。
- Codex `fast` 是服务速度档，不降低推理量。官方文档显示 GPT-5.5 fast 约快 1.5 倍，但按 2.5 倍积分计费。

## 2. 定位透镜

**纵向看，5.6 是从“单一旗舰”转向“同代三档能力”；横向看，实际体验由模型、推理、速度和并行四个旋钮共同决定。**

```mermaid
graph LR
    A["任务"] --> B["模型档位：Sol / Terra / Luna"]
    B --> C["推理档位：none → max"]
    C --> D["服务速度：standard / fast"]
    D --> E["并行方式：单 Agent / ultra"]
    E --> F["质量、耗时、Token、积分"]
```

| 维度 | 控制什么 | 对 Token / 积分的主要影响 |
|---|---|---|
| 模型 | 基础能力与单位 Token 费率 | Sol=5.5；Terra=0.5×；Luna=0.2× |
| 推理强度 | 单 Agent 思考深度 | 越高通常内部推理 Token 越多 |
| 速度 | 相同模型的服务吞吐 | GPT-5.5 fast：1.5×速度、2.5×积分 |
| ultra | 多 Agent 并行 | 默认 4 Agent；缩短墙钟时间，但总 Token 上升 |

生命周期判断：GPT-5.6 于 2026-07-09 全面发布，处于 GA 初期。模型费率和能力文档已经更新，但 Codex Speed 页面尚未列出 5.6 的 fast 费率，迁移时需要从 Usage 面板实测。

## 3. 能力对比

**Sol 是稳定升级，Terra 是最值得关注的性价比档，Luna 更像高质量快速工作模型而不是完整替代。**

以下为 OpenAI 发布页披露的评测结果；除 Artificial Analysis 指数外，多数为 OpenAI 运行或汇总的评测，不能视为完全独立审计。

| 评测 | 5.6 Sol | 5.6 Terra | 5.6 Luna | 5.5 | 判断 |
|---|---:|---:|---:|---:|---|
| Agents' Last Exam | 52.7% | 50.4% | 50.3% | 46.9% | 三档均高于 5.5 |
| Coding Agent Index | 80.0 | 77.4 | 74.6 | 76.4 | Sol/Terra 更强，Luna 略低 |
| SWE-Bench Pro | 64.6% | 63.4% | 62.7% | 59.4% | 三档均更强 |
| DeepSWE 1.1 | 72.7% | 69.6% | 67.2% | 67.0% | Luna 近似持平 |
| Terminal-Bench 2.1 | 88.8% | 87.4% | 84.7% | 85.6% | Luna 略低 |
| OSWorld 2.0 | 62.6% | 50.2% | 45.6% | 47.5% | Sol 增益大，Luna 略低 |
| BrowseComp | 90.4% | 87.5% | 83.3% | 84.4% | Sol/Terra 更强 |
| MRCR 512K-1M | 73.8% | 72.5% | 41.3% | 74.0% | Sol 与 5.5 持平，Luna 明显弱 |
| Toolathlon | 58.0% | 53.1% | 53.4% | 55.6% | Sol 略强，Terra/Luna 略低 |

主要优势：

- 编码：Sol 在 Coding Agent Index、SWE-Bench Pro、DeepSWE、Terminal-Bench 均高于 5.5。
- Computer Use：Sol 的 OSWorld 2.0 为 62.6%，对比 5.5 的 47.5%，增幅明显。
- 设计与前端：OpenAI 与早期客户报告显示 5.6 的布局、视觉层级、设计判断和成品完整度更好。
- 意图理解：5.6 更容易理解用户想要的是调研、规划、实施还是完整产物，减少反复提示。
- 工具密集任务：Programmatic Tool Calling 可在模型侧处理工具中间结果，减少模型往返和累计上下文。

局限：

- Sol 并非每项都显著领先。512K-1M 长上下文评测与 5.5 基本持平。
- Terra/Luna 在 Toolathlon、部分长上下文和高难度任务上低于 5.5。
- Sol 的生物和网络安全请求会使用更严格的实时检查，合法双用途任务也可能额外等待或被拦截。
- `ultra` 的更高分数来自多 Agent 并行，不能与单 Agent 的 Token 成本直接等同。

## 4. Token 与积分

**Sol 的单位 Token 不涨价，Terra 半价，Luna 五分之一价；真正昂贵的是输出/推理 Token 和 fast 倍率。**

### 4.1 Codex Token 费率

| 模型 | 输入 / 1M | 缓存输入 / 1M | 输出 / 1M | 相对 5.5 |
|---|---:|---:|---:|---:|
| GPT-5.6 Sol | 125 credits | 12.5 credits | 750 credits | 1.0× |
| GPT-5.6 Terra | 62.5 | 6.25 | 375 | 0.5× |
| GPT-5.6 Luna | 25 | 2.5 | 150 | 0.2× |
| GPT-5.5 | 125 | 12.5 | 750 | 1.0× |

输出 Token 的积分率是普通输入 Token 的 6 倍。API usage 中 `reasoning_tokens` 是 `output_tokens_details` 的子项，因此提高推理强度会直接推高昂贵的输出侧用量。

以一次任务使用 20K 普通输入、80K 缓存输入、10K 输出为例：

| 配置 | 同 Token 量积分 | 相对当前配置 |
|---|---:|---:|
| 5.5 standard | 11.0 | 40% |
| 5.5 fast | 27.5 | 100% |
| 5.6 Sol standard | 11.0 | 40% |
| 5.6 Terra standard | 5.5 | 20% |
| 5.6 Luna standard | 2.2 | 8% |

计算假设：GPT-5.5 fast 按 standard 的 2.5 倍积分；5.6 各档按相同 Token 构成计算。5.6 fast 的准确倍率尚未在 Speed 文档公开，不能沿用 2.5 倍作为事实。

### 4.2 同任务 Token 效率

**方向性证据支持 5.6 通常比 5.5 少用 Token，但没有一个适用于所有任务的固定比例。**

- Qodo 的 PR 评测：5.6 相比 5.5 约少 3 倍 Token、约低 2 倍中位延迟。
- Notion：不少 5.5 Agent 在 Terra 上达到相近表现，单位费率减半，Token 再少 16%。
- Rogo：使用 Programmatic Tool Calling 时，质量提升且输出 Token 少 24%，完成时间少 28%。
- Clio：法律工作流质量提升且 Token 少 14%。
- Base44：30 个应用构建对话中，输入少 22%、输出少 23%，整体质量相当或更好。

这些是发布页中的合作伙伴内部评测，任务分布不同，不能直接平均。用于个人预算时，保守估计可先按“同档 10%-25% 更少总 Token”做容量规划，再用 Usage 面板校准；代码评审等特定任务可能远好于这个区间。

### 4.3 API 缓存变化

GPT-5.6 支持显式缓存断点和至少 30 分钟缓存生命周期。缓存读取仍是普通输入的 10%，但缓存写入按普通输入的 1.25 倍计费。这个变化对重复长前缀有利，对低复用、频繁变化的长 Prompt 可能先增后减；Codex 客户端的实际缓存命中应以 Usage 面板为准。

## 5. 原配置诊断

**`5.5 + xhigh + fast` 同时把“思考深度”和“服务速度”拉满，质量高，但积分效率差。**

你原来的配置对应：

- 模型：GPT-5.5，旗舰能力，标准费率与 5.6 Sol 相同。
- 推理强度：`xhigh`，中文 UI 为“极高”，内部推理 Token 较多。
- 速度：`fast`，约 1.5 倍吞吐，但 GPT-5.5 按 2.5 倍积分消耗。

因此，从当前配置切到 `5.6 Sol + xhigh + standard`，即使 Token 数完全不下降，积分也约只剩当前的 40%，即节省约 60%。如果同任务总 Token 再少 20%，积分约只剩当前的 32%，即节省约 68%。这是推算，不是对所有任务的实测保证。

## 6. 推荐配置

**默认推荐 `Sol + high + standard`，日常工作用 Terra，下限任务用 Luna，max/ultra 只按需开启。**

| 场景 | 推荐配置 | 原因 |
|---|---|---|
| 默认复杂开发、调研、方案 | 5.6 Sol + high + standard | 官方建议迁移时测试低一档；基础能力更强，但能否保持原 xhigh 质量需 A/B 验证 |
| 难 Debug、架构决策、跨模块重构 | 5.6 Sol + xhigh + standard | 质量优先但避免 fast 倍率 |
| 高价值且结果可验证的难题 | 5.6 Sol + max + standard | 给更多探索与复核预算；不适合作为全局默认 |
| 日常编码、文档、资料整理 | 5.6 Terra + medium/high + standard | 接近或超过 5.5 的常用能力，单位积分减半 |
| 小改动、格式化、批量初筛 | 5.6 Luna + low/medium + standard | 单位积分为 5.5 的 20%，速度快 |
| 可并行的高价值任务 | Sol + xhigh/max + ultra | 默认 4 Agent 并行；更快、更强，但总 Token 更高 |
| 真正赶时间 | 支持时临时开 fast | fast 是“花积分买等待时间”，不要长期默认开启 |

## 7. 一周迁移验证

**用代表性任务做小样本 A/B，比继续凭感觉选档位更可靠。**

从最近工作中选 10 个任务，至少覆盖：小改动、普通功能、复杂 Debug、长文档调研、前端视觉、多工具任务。固定输入与验收条件，比较三组：

1. 5.5 + xhigh + fast（现状）
2. 5.6 Sol + high + standard（推荐默认）
3. 5.6 Terra + high + standard（日常低成本）

记录：一次通过率、人工返工分钟、总 Token、积分、墙钟时间、工具调用次数。建议门槛：

- Sol high：一次通过率不低于现状，积分低 50% 以上。
- Terra high：一次通过率与现状差距不超过 5 个百分点，积分低 70% 以上。
- fast：只有墙钟时间改善达到 30% 以上且任务确实有时效价值时才保留。

## 8. 开放问题与边界

**当前最大待验证项不是模型能力，而是你账号中 5.6 fast 的可用性、倍率和真实任务分布。**

- ❓ [待验证] Codex Speed 文档仍只列出 GPT-5.5 与 GPT-5.4，未公布 5.6 fast 的积分倍率。
- ❓ [待验证] 官方没有给出“5.6 对 5.5 全任务平均少多少 Token”的统一数字。
- ❓ [待验证] 你的任务中输入、缓存输入、推理输出各占多少，需要 Usage 面板数据。
- ⚠️ 供应商发布页评测有代表性，但不等于你的代码库与工作流。
