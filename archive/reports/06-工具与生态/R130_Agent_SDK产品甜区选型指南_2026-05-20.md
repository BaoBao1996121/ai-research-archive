# Agent SDK 产品甜区分析与选型指南

> 一句话概括：八大主流 Agent SDK 各有明确甜区——LangGraph 精控状态机、CrewAI 最快出 Demo、Pydantic AI 工程师最爱、OpenAI SDK 入门首选、ADK 是 GCP 亲儿子、smolagents 是 Code Agent 极简主义、Agno 做平台级运营、Mastra 是 TS 生态正统。选型的本质不是"谁最强"，而是"你的约束条件把你推向谁"。

## 定位透镜：纵横坐标

### 纵轴 · 演化脉络

Agent SDK 的演化经历了三个清晰的阶段：

**第一阶段（2023 H1）：链式调用时代**。LangChain 开创了"LLM + Tool + Chain"的组合范式，解决了"怎么把 LLM 和外部工具连起来"的基础问题。代价是过度抽象和性能损耗。

**第二阶段（2023 H2 - 2024）：Agent 框架爆发**。AutoGen（微软多 Agent 对话）、CrewAI（角色扮演编排）、LangGraph（状态机精控）相继出现。共同趋势：从"链"向"图/状态机"演进，从单 Agent 向多 Agent 协作演进。

**第三阶段（2025 - 2026 now）：平台化与标准化**。三个标志性事件引爆当前格局：
1. OpenAI 发布 Agents SDK（2025-03），将 Swarm 实验正式化，定义了 Agent/Handoff/Guardrail 三件套
2. Google ADK 2.0 GA（2026-05-19，昨天），从 Gemini 绑定走向 Workflow Runtime + Task API
3. MCP 和 A2A 协议成为行业共识，工具互操作不再是问题

**当前阶段判定**：行业处于"上升期末→成熟期初"的拐点。标志是——API 设计趋同（都有 Agent/Tool/Handoff/Memory）、协议标准化（MCP/A2A）、竞争焦点从"功能有没有"转向"开发体验好不好"和"生产运维省不省心"。

### 横轴 · 竞争格局

八家产品的设计哲学可以用两个维度划分：

```
        控制力高（显式状态管理）
            │
   LangGraph │  ADK 2.0
            │  Mastra
            │
 Python ────┼──── TypeScript
            │
   Pydantic │  
   smolagents│
            │
        控制力低（声明式/约定式）
   CrewAI   │  OpenAI SDK
   Agno     │
```

**设计哲学分野**：
- **显式状态派**（LangGraph/ADK/Mastra）：你画图、你定义状态转移、你控制每一步。代价是模板代码多。
- **约定优于配置派**（CrewAI/OpenAI SDK/Agno）：框架替你管状态，你只需声明角色和任务。代价是定制天花板低。
- **极简派**（smolagents/Pydantic AI）：核心只做一件事做到极致（code execution / type safety），其他靠你自己组合。代价是完整方案需要自己搭。

### 交叉判断

选型的本质不是"谁抽象层级更高"或"谁 Star 更多"，而是三个约束条件的交叉：
1. **你的语言栈**——Python 还是 TypeScript，直接砍掉一半选项
2. **你需要多少控制力**——Demo/PoC 要快，生产系统要精控
3. **你的云绑定意愿**——OpenAI/Google 生态内 vs 厂商中立

## 甜区深度拆解

### 1. LangGraph — 精密状态机

**一句话**：当你的 Agent 工作流需要显式状态管理、条件分支、人工审批节点时，LangGraph 是最成熟的选择。

**甜区**：
- 复杂多步工作流，有明确的状态转移图
- 需要 checkpointing（中断恢复、人工介入后继续）
- 团队有 LangChain 使用经验
- 需要 LangSmith 全链路追踪

**短板**：
- 模板代码量大，简单场景杀鸡用牛刀
- 与 LangChain 耦合（虽然声称可独立使用，但生态黏性明显）
- 学习曲线陡——"状态图思维"对没写过有限状态机的开发者不直觉
- 性能开销（CrewAI 声称在特定场景下比 LangGraph 快 5.76 倍）

**适合谁**：有经验的后端工程师，需要像写状态机一样精确控制 Agent 行为的团队。

---

### 2. CrewAI — 最快出 Demo

**一句话**：声明式角色扮演编排，5 分钟跑通一个多 Agent 协作 Demo。

**甜区**：
- 快速原型验证（Hackathon、Demo Day）
- 任务可以自然地分解为"角色 + 目标 + 背景故事"
- 有 CLI 脚手架（`crewai create crew`），YAML 配置驱动
- Flows 机制补足了 Crews 在确定性流程上的短板

**短板**：
- 角色扮演范式在复杂场景下不如显式状态机可控
- YAML 配置在大型项目中会失控（调试困难）
- 默认遥测采集（虽可关闭，但隐私敏感场景需留意）
- 内部 Prompt 模板对非英语场景不友好
- "独立于 LangChain"但 pyproject.toml 中仍有 langsmith 依赖

**适合谁**：产品经理/AI 爱好者快速验证想法；非严格生产环境下的内部工具。

---

### 3. Pydantic AI — 工程师的框架

**一句话**：如果 FastAPI 让你爱上了 Python Web 开发，Pydantic AI 会让你爱上 Agent 开发。

**甜区**：
- 对类型安全有洁癖的团队（`Agent[Deps, Output]` 泛型全程类型检查）
- 依赖注入（`RunContext`）让工具函数天然可测
- 结构化输出一等公民（`output_type=SupportOutput`，自动重试验证）
- Capabilities 系统实现可组合架构（Thinking + WebSearch 一行搞定）
- Durable Execution 支持长时运行 + 断线恢复
- Pydantic Logfire 提供 OTel 原生可观测性

**短板**：
- 多 Agent 编排能力相对弱（Graph 支持是近期新增，成熟度待验证）
- 版本号 v1.99.0 暗示 v2.0 即将发布——Breaking Changes 风险
- 文档质量高但示例覆盖面窄（企业级场景示例少）
- 社区规模小于 CrewAI/OpenAI SDK

**适合谁**：中高级 Python 工程师；已经在用 Pydantic/FastAPI 的团队；对代码质量和可维护性要求高的生产项目。

---

### 4. OpenAI Agents SDK — 入门之选

**一句话**：OpenAI 官方出品，概念最少、上手最快、与 OpenAI 生态无缝对接。

**甜区**：
- 从 0 开始学 Agent 开发（概念只有 Agent/Tool/Handoff/Guardrail）
- 重度使用 OpenAI API 的团队（内置 Responses API 优化）
- Sandbox Agent 解决长时运行代码执行需求
- Realtime Voice Agent（gpt-realtime-2）目前独家
- 100+ LLM 支持（通过 LiteLLM/any-llm 扩展）

**短板**：
- 虽然声称 provider-agnostic，但最优体验仍绑定 OpenAI 模型
- 版本号仍在 0.x（v0.17.3），API 稳定性未达 1.0 承诺
- 多 Agent 编排只有 Handoff 一种模式（无图结构编排）
- 状态管理基础（Session 级别，无 LangGraph 式 checkpointing）
- 生态工具较少（不如 CrewAI 的预置工具包丰富）

**适合谁**：Agent 开发新手；OpenAI 重度用户；需要最短路径跑通 Agent 的团队。

---

### 5. Google ADK 2.0 — GCP 的亲儿子

**一句话**：v2.0 的 Workflow Runtime + Task API 让 ADK 从"Gemini 绑定 SDK"升级为通用 Agent 框架。

**甜区**：
- 已在 GCP 上运行基础设施的团队（Vertex AI/Cloud Run 无缝集成）
- 需要图结构工作流（Workflow 类支持 routing/fan-out-fan-in/loops/retry）
- Task API 提供结构化的 Agent 间委派（multi-turn/single-turn/mixed）
- 内置 Dev UI（`adk web`）方便本地调试
- Human-in-the-loop 一等支持

**短板**：
- v2.0 刚发布（昨天 GA），生产验证极少——**这是最大风险**
- v1.x → v2.0 有 Breaking Changes（Session schema 不兼容旧版本）
- Python 3.11+ 要求较高（排除部分企业环境）
- 社区资源（教程、示例）远少于 CrewAI/LangGraph
- 非 Google 模型支持仍是二等公民

**适合谁**：GCP 用户；对 Google AI 生态有信心且能承受早期版本风险的团队。

---

### 6. smolagents — Code Agent 极简主义

**一句话**：Agent 的行为就是写 Python 代码片段而非 JSON 工具调用——fewer steps, higher performance。

**甜区**：
- 需要 Agent 执行复杂的多步计算/数据处理
- 对 Agent 步骤数和 Token 消耗敏感（code agent 论文验证减少 30% 步骤）
- HuggingFace 生态用户（Hub 共享 Agent/Tool、Inference Providers）
- 研究/学术场景（核心代码 <1000 行，极其适合阅读和修改）

**短板**：
- 安全风险——code execution 本质上是任意代码执行，必须沙箱化
- `LocalPythonExecutor` **不是安全边界**（官方明确警告）
- 多 Agent 编排是简单的层级制（manager/worker），不如 LangGraph 灵活
- 生产运维工具缺失（无内置追踪、无持久化状态、无 RBAC）
- 对"声明式工具调用"场景反而过度复杂

**适合谁**：数据科学家/研究者；需要 Agent 做复杂计算的场景；愿意自建生产基建的团队。

---

### 7. Agno — 平台级运营

**一句话**：不只是写 Agent 逻辑，而是开箱获得一整个 Agent 平台（API/RBAC/调度/多租户）。

**甜区**：
- 需要把 Agent 作为产品提供给终端用户（SaaS 场景）
- 50+ 开箱即用的 API 端点（SSE/WebSocket）
- 多租户隔离、JWT-based RBAC、人工审批
- 内置 Cron 调度和后台任务
- 100+ 工具集成、Context Providers（Slack/Drive/Wiki）
- 多接口暴露（Slack/Telegram/WhatsApp/Discord/AG-UI/A2A）

**短板**：
- 定位是"平台 SDK"——如果只是做一个内部脚本级 Agent，过于重量级
- 从 phidata 改名而来（2025），品牌认知仍在建立中
- 对 Agent 行为本身（推理/规划/状态管理）的控制力有限
- 框架绑定风险——一旦选了 Agno 平台层，迁出成本较高
- 文档体系相对年轻，深度 troubleshooting 资源少

**适合谁**：要做 Agent-as-a-Service 的团队；需要快速搭建面向多用户的 Agent 产品。

---

### 8. Mastra — TypeScript 正统

**一句话**：如果你的技术栈是 TypeScript/React/Next.js，Mastra 是目前最完整的 Agent 框架。

**甜区**：
- 纯 TypeScript 生态（前后端同构）
- 直观的工作流语法（`.then()` / `.branch()` / `.parallel()`）
- 与 Vercel AI SDK UI / CopilotKit 集成
- 内置 Memory（conversation history + working memory + semantic recall）
- MCP Server 能力（暴露 Agent 为 MCP 服务）
- 内置 Evals + Observability

**短板**：
- TypeScript Only——排除纯 Python 团队
- 双许可证（Apache-2.0 + Enterprise License for `ee/` 目录）
- 从 Gatsby 团队转型而来，Agent 领域专家深度待证明
- 生态工具比 Python 框架少（Python 是 AI/ML 第一语言）
- v1.35.0 版本号但迭代速度极快（每周多次发布），API 稳定性隐忧

**适合谁**：TypeScript/全栈团队；React/Next.js 产品中嵌入 Agent 能力。

## 六大场景选型路径

### 场景 A：快速原型/Demo（1-3 天）

```
约束：最快出活 + 团队无 Agent 经验
  └─ Python → OpenAI Agents SDK（概念最少）或 CrewAI（角色模型直觉）
  └─ TypeScript → Mastra（`npm create mastra@latest` 一键起手）
```

### 场景 B：生产级单 Agent 应用

```
约束：需要可观测性 + 结构化输出 + 类型安全
  └─ Python → Pydantic AI（DI + Logfire + 类型检查三件套）
  └─ TypeScript → Mastra（evals + observability 内置）
```

### 场景 C：复杂多 Agent 编排（有显式状态流转）

```
约束：有条件分支 + 人工审批 + 中断恢复
  └─ 需要最成熟方案 → LangGraph（checkpointing 最强）
  └─ GCP 环境 → ADK 2.0（Workflow Runtime 原生支持）
  └─ TS 生态 → Mastra（.branch() + suspend-and-resume）
```

### 场景 D：Agent-as-a-Product（面向终端用户）

```
约束：多租户 + RBAC + API 暴露 + 多渠道接入
  └─ Python → Agno（开箱即用的平台层）
  └─ TypeScript → Mastra（server adapters + auth）
```

### 场景 E：研究/实验/教育

```
约束：代码可读 + 易修改 + 开源友好
  └─ Code Agent 研究 → smolagents（核心 <1000 行）
  └─ Agent 原理教学 → OpenAI SDK（概念最少最清晰）
  └─ 多模型横评 → Pydantic AI（model-agnostic 最彻底）
```

### 场景 F：已有云生态绑定

```
约束：已在特定云平台上
  └─ OpenAI 生态 → OpenAI Agents SDK（Responses API 优化）
  └─ GCP/Vertex AI → ADK 2.0
  └─ Azure → Semantic Kernel（本报告未覆盖，微软亲儿子）
  └─ 厂商中立 → Pydantic AI 或 LangGraph
```

## 最佳实践（15 条）

### 架构层

1. **从约束条件而非功能清单选型**。选型的起点是"我不能接受什么"（语言绑定？云锁定？学习成本？），而非"谁功能最多"。

2. **分层解耦**：Agent 逻辑层（推理/工具调用）与平台层（API/认证/监控）分离。用 Pydantic AI 写 Agent 逻辑，用 FastAPI 做 API 层，不比用 Agno 全包差——且迁移成本低。

3. **MCP 作为工具标准接口**。2026 年所有主流 SDK 都支持 MCP。把你的工具封装为 MCP Server，Agent 框架换了工具不用重写。

4. **别在 v0.x 上赌生产**。OpenAI SDK（v0.17）和 ADK（v2.0 刚发）都还年轻。如果你的生产系统不能承受 Breaking Changes，选 CrewAI（v1.14）或 Pydantic AI（即将 v2.0 但有明确迁移路径）。

### 开发层

5. **结构化输出优先于自由文本**。所有框架都支持 structured output（Pydantic model / JSON Schema）。强类型输出让下游代码不必 parse 自由文本——减少一半的 Bug。

6. **依赖注入隔离副作用**。Pydantic AI 的 `RunContext[Deps]` 模式是黄金标准——工具函数不直接持有数据库连接/API key，通过 DI 注入，测试时 mock 即可。其他框架没有原生 DI 的，自己用 dataclass 传 context。

7. **工具函数的 docstring 就是给 LLM 看的 Prompt**。所有 SDK 会把工具的 docstring 发给模型。写 docstring 时想象你在教一个新员工用这个工具——参数含义、返回值含义、什么时候该用什么时候不该用。

8. **沙箱执行是底线**。任何涉及代码执行的 Agent（smolagents CodeAgent / OpenAI Sandbox Agent），生产环境 **必须** 用 Docker/E2B/Modal 沙箱。`LocalPythonExecutor` 不是安全边界。

### 生产层

9. **可观测性不是可选项**。OpenTelemetry tracing 是当前共识。Pydantic AI 用 Logfire、LangGraph 用 LangSmith、Agno 内置 OTel。没有追踪的 Agent 生产系统 = 盲人开飞机。

10. **Token 成本预算化**。在 Agent 上线前，用真实场景跑 100 次，统计 P50/P90/P99 的 Token 消耗和延迟。据此设定 max_tokens 和 cost alert。Agent 的成本曲线不是线性的——一个失控的循环能在 10 分钟内烧掉 $50。

11. **Human-in-the-loop 不是"有则更好"，是必需品**。任何会产生外部副作用的工具调用（发邮件/改数据库/创建工单），初期 **必须** 加人工审批。等积累了足够的安全数据后再逐步放开。

12. **设计幂等性**。Agent 可能因为超时/断线/模型幻觉而重试。你的工具函数必须考虑"被调用两次"的情况——用幂等键或 check-before-write。

### 评估层

13. **评估先于开发**。在写第一行 Agent 代码前，先定义"成功"长什么样（准确率？完成率？平均步骤数？用户满意度？）。没有评估标准的 Agent 开发 = 无方向的随机漫步。

14. **对抗测试常态化**。每个 Agent 都需要一组"刻意刁难"的测试用例——模糊指令、矛盾信息、超出能力范围的请求。检验 Agent 是否能优雅降级而非幻觉输出。

### 协议层

15. **A2A 为将来留接口**。即使现在是单 Agent 系统，设计时留好 A2A 接口的可能性。Pydantic AI 和 ADK 已原生支持。当你的 Agent 需要和外部 Agent 交互时（跨团队/跨公司），A2A 是现成标准。

## 反模式与避坑

| # | 反模式 | 为什么是坑 | 正确做法 |
|---|--------|-----------|---------|
| 1 | 看 Star 数选框架 | Star 反映营销力不反映工程质量（CrewAI 51.8K 靠课程引流） | 看最近 6 个月的 commit 频率、Issue 响应速度、Breaking Change 频率 |
| 2 | 用 Agent 做规则引擎的事 | if-else 能搞定的不要用 LLM，每次调用 $0.01-$0.10 | 先问"这个任务需要推理能力吗？"不需要就用传统代码 |
| 3 | 一上来就多 Agent | 多 Agent = 多点失败 + 调试地狱 + Token 翻倍消耗 | 单 Agent + 多工具跑通，瓶颈确认后才拆 Agent |
| 4 | 忽略框架的隐式 Prompt | CrewAI/Agno 在你不知情时注入大量系统 Prompt（角色/背景/目标），消耗 Token 且可能与你的指令冲突 | 查看框架源码中的 prompt 模板，确认不冲突 |
| 5 | 框架全家桶一把梭 | 用了框架的 Memory/RAG/Eval 全套后发现迁移成本极高 | 核心依赖（模型调用/编排）用框架，周边能力（RAG/Memory/Eval）用独立组件 |
| 6 | Demo 阶段不设 guardrail | "反正是 Demo 没关系" → 演示现场 Agent 说了不该说的 | 从第一天就加 input/output guardrail，哪怕是简单的关键词过滤 |
| 7 | 选了 TS 框架却用 Python 做 ML | Mastra 做 Agent 编排很好，但 ML pipeline 还是 Python 的天下 | 用 MCP 桥接——TS 层做编排和 UI，Python 层做 ML 和 RAG |

## 开放问题

1. **ADK 2.0 生产验证**：昨天才 GA，Breaking Changes 文档有了但社区实战反馈为零。6 个月后需要重新评估。
2. **Pydantic AI v2.0 迁移成本**：v1.99.0 → v2.0 的 Breaking Changes 范围还不清楚。密切关注 changelog。
3. **MCP 生态质量**：所有框架都支持 MCP，但 MCP Server 的质量参差不齐（很多社区 Server 是 toy level）。需要建立 MCP Server 质量评估标准。
4. **CrewAI 的 LangChain 依赖是否真的清零**：README 声称独立，但依赖树中仍有 langsmith。需源码验证。
5. **A2A 实际互操作性**：Pydantic AI 和 ADK 都声称支持 A2A，但跨框架的 Agent 能否真正互通，目前无公开验证。
