### 交叉判断

1. **L2 层能力趋同**：各 SDK 现在都支持 tools、streaming、structured output、MCP。单看功能清单已很难区分——设计哲学和 DX（开发体验）才是真正的差异化因素。
2. **L3/L4 正在成为真战场**：ADK v2.0 新增 Workflow Runtime（graph-based 编排），正面硬刚 LangGraph 的核心卖点。Agno 在 Platform 层独占，但 CrewAI AMP 也在发力。
3. **协议标准化降低迁移成本**：MCP（工具）+ A2A（Agent 间通信）+ AG-UI（前端流式）三个协议正在被所有 SDK 采纳——这意味着"选错框架"的代价在降低。

## 3. 各产品甜区一句话

> **甜区 = "这个产品在什么场景下，比所有竞品都更合适"**。不是"能做什么"（都能做），而是"在哪种情况下是无脑正选"。

| SDK | 甜区一句话 | 对应画像 |
|-----|-----------|---------|
| **LangGraph** | 需要**精细状态控制 + 检查点回滚 + HITL**的复杂流程型 Agent | 金融审批流、合规检查链、多步骤 RAG pipeline |
| **CrewAI** | 想用**自然语言声明角色和任务**快速搭起一个多 Agent 协作 Demo | 内容生产团队、市场调研自动化、快速原型 |
| **Pydantic AI** | **Python 类型安全狂热者**、想要"if it compiles, it works"的开发体验 | 后端工程师团队、需要 DI + 结构化输出 + 内置 eval |
| **OpenAI SDK** | **概念最少、10 分钟上手**，只用 OpenAI 模型的简单 Agent | 黑客松、PoC、内部工具、初学者入门 |
| **Google ADK** | **深度绑定 Google Cloud + Gemini**的企业级 Agent | GCP 原住民、需要 Vertex AI 集成、已有 Google 生态 |
| **smolagents** | Agent 需要**批量数据处理、循环/条件逻辑**的计算密集型任务 | 数据分析、爬虫编排、ETL pipeline、研究自动化 |
| **Agno** | 已经有能跑的 Agent 原型，需要**一键变成生产 API 服务** | 从 PoC 到产品的桥梁、全栈独立开发者、需要 RBAC/Session/Trace |
| **MAF (Microsoft)** | **Azure/.NET 企业**需要插件化 + 多语言 + Checkpoint + GroupChat 的多 Agent 系统 | Azure 原住民、.NET 团队、需要 Time Travel 调试的企业流程 |
| **Claude Agent SDK** | **深度 Coding/工具自动化场景**，Agent 逻辑用 Hooks 精确治理，绑定 Claude 模型 | 代码生成/重构 Agent、内部开发者工具、Claude 重度用户 |
| **Mastra** | 团队是 **TypeScript/Next.js 全栈**，不想引入 Python 依赖 | Vercel 部署、前端团队做 AI 功能、全栈 TS 项目 |

## 4. 甜区深度拆解

### 4.1 LangGraph — 精密状态机的王者

**甜区**：你的 Agent 不是"问一下 LLM 就完事"，而是一个有**多步骤、有分支、需要回退、需要人工审批**的复杂流程。

**为什么是它**：
- **Pregel 计算模型**：每个节点独立计算 + 消息传递——天然适合"流程中任何一步可能失败/需要人工介入"的场景
- **Checkpoint 机制**：任意步骤快照 + 回放，断点续跑不丢状态。其他 SDK 要自己实现这个至少 2 周工作量
- **LangSmith 生态**：trace/debug/eval 全链条可视化——生产环境 debug 多步 Agent 的体验领先一个身位

**不适合**：
- 简单的单轮问答增强（杀鸡用牛刀）
- 团队没 Python 经验（学习曲线 1-2 周）
- 抗拒 vendor lock-in（深度使用后迁移成本高）

**护城河**：不在"图编排"本身（ADK v2.0 已跟进），而在 **LangSmith + LangGraph Cloud + Deep Agents** 的垂直整合。

---

### 4.2 CrewAI — 最快出 Demo 的角色编排

**甜区**：产品经理或非深度技术人员也能看懂的"AI 团队协作"——用 YAML 声明角色/目标/任务，5 分钟搭起一个多 Agent Demo。

**为什么是它**：
- **上手速度最快**：`crewai create crew my_project` 一键生成骨架，YAML 写角色和任务
- **Flows + Crews 双模式**：简单场景用 Crews（自主协作），复杂场景用 Flows（精确控制）——两档齿轮覆盖从 Demo 到生产
- **100K+ 社区认证开发者**：教程和案例最丰富

**不适合**：
- 需要精细控制每一步执行顺序的场景（角色"自主决策"有时不可预测）
- 对延迟/Token 消耗敏感的场景（角色间"对话"带来额外开销）
- 核心逻辑需要确定性（"角色协商"本质是不确定的）

**坑**：CrewAI 声称"独立于 LangChain"，但 `crewai[tools]` 仍间接依赖 `langchain-core`。影响不大但要知道。

---

### 4.3 Pydantic AI — 工程师的 Agent 框架

**甜区**：你的团队是一群**写类型注解、用 FastAPI、对代码质量有洁癖**的后端工程师——Pydantic AI 给你的是"写 FastAPI 路由时那种舒适感"。

**为什么是它**：
- **完整类型推断**：`Agent[SupportDependencies, SupportOutput]`——IDE 自动补全到手软，运行时 Pydantic 自动校验
- **依赖注入（DI）**：通过 `RunContext[deps_type]` 注入数据库连接、用户信息等——测试时 mock 极其优雅
- **Capabilities 系统**（新）：把 tools、hooks、instructions 打包为可复用单元——`Thinking()`, `WebSearch()` 即插即用
- **Durable Execution**（新）：跨 API 失败 + 重启保持进度——真正的生产级可靠性
- **Pydantic Logfire**：原生 OpenTelemetry 集成，trace 每次 LLM 调用的入参/出参/耗时/成本

**不适合**：
- 快速 Demo（它的价值在生产阶段，Demo 阶段反而比 CrewAI/OpenAI SDK 慢）
- 不在乎类型安全的团队（用不到优势，反而觉得"定义类型好麻烦"）
- 纯前端/TS 团队

**最近动向（v1.99.0）**：新增 Agent Spec（YAML/JSON 定义 Agent，无代码）、Graph 支持（类 LangGraph 的图编排）、Human-in-the-Loop Tool Approval。正在向全能型演进。

---

### 4.4 OpenAI Agents SDK — 概念最少的入门之选

**甜区**：**初学者第一个 Agent、黑客松 Demo、内部工具原型**——10 分钟从零到有，不需要理解任何框架概念。

**为什么是它**：
- **API 面积最小**：Agent + Tool + Handoff + Guardrail，四个概念就够了
- **Handoff 模式**：多 Agent 协作不需要图、不需要 YAML——一个 Agent "交接"给另一个，代码即文档
- **OpenAI 官方维护**：与 GPT 模型最新能力（如 structured output）天然同步

**不适合**：
- 需要用非 OpenAI 模型（SDK 设计上针对 OpenAI API，虽可扩展但不是一等公民）
- 复杂状态管理、持久化、检查点（没有内置）
- 大规模生产部署（缺少 trace/monitor 生态）

**定位**：OpenAI SDK 是"Agent 编程的 Hello World"——理解了它再去看 LangGraph/Pydantic AI，就知道为什么需要更复杂的工具。

---

### 4.5 Google ADK v2.0 — Google Cloud 的亲儿子

**甜区**：你的基础设施在 **GCP**、模型用 **Gemini**、部署用 **Cloud Run / Vertex AI**——ADK 是 Google 生态内的一等公民。

**为什么是它**：
- **Workflow Runtime**（v2.0 新）：graph-based 执行引擎，支持 routing/fan-out/fan-in/loops/retry/human-in-the-loop
- **Task API**（v2.0 新）：结构化的 Agent-to-Agent 委托——多轮/单轮/混合模式
- **原生 Google 集成**：Vertex AI Search、Cloud Storage、BigQuery、Gemini——零配置
- **adk web** 本地 UI：边开发边调试，体验接近 LangGraph Studio

**不适合**：
- 非 Google Cloud 用户（生态绑定太深）
- 需要稳定 API 的场景（v2.0 Breaking Changes 表明 API 仍在快速迭代）
- Python < 3.11（硬性要求）

**⚠️ 注意**：v2.0.0 于 **2026-05-19 刚 GA**。Session schema 与 1.x 不兼容。现有 ADK 1.x 用户需要迁移。

---

### 4.6 smolagents — 让 Agent 写代码而非调工具

**甜区**：你的 Agent 任务是**数据处理、批量操作、需要循环和条件逻辑**——与其让 LLM 调 10 次工具，不如让它写一段 Python 一次搞定。

**为什么是它**：
- **Code Agent 范式**：LLM 的 action 是 Python 代码片段，不是 tool call JSON——论文实证减少 30% LLM 调用
- **极简核心**：核心逻辑 ~1000 行（agents.py），源码即文档
- **Hub 集成**：`agent.push_to_hub()` / `Agent.from_hub()` 分享/复用 Agent
- **多沙箱选择**：E2B / Modal / Docker / Pyodide+Deno——从云端到边缘都有隔离方案

**不适合**：
- 面向终端用户的服务（代码执行的安全风险——**必须沙箱化**）
- 简单的问答/检索增强（不需要写代码的场景没有优势）
- 需要精确控制 Agent 行为（代码生成本身有不确定性）

**竞争优势的本质**：当 agent 面对"对 500 个 URL 抓取并提取特定字段"这种任务时，tool-calling 范式需要 500 次独立调用（500 次 LLM 决策）；CodeAgent 写一个 for 循环（1 次 LLM 决策 + 1 次代码执行）。差异是数量级的。

---

### 4.7 Agno — 把 Agent 变成生产服务的桥

**甜区**：你已经有一个能跑的 Agent（用任何框架写的），现在需要**一步到位变成带 API / 认证 / Session / Trace / RBAC 的生产服务**。

**为什么是它**：
- **框架无关**：同一个 AgentOS 可以跑 Agno 原生 Agent、Claude SDK Agent、LangGraph Agent
- **20 行代码 → 50+ API 端点**：SSE/WebSocket、session 持久化、cron 调度、多用户隔离
- **Human Approval 内置**：工具级审批流 `confirm=["write", "delete"]`
- **100+ 预置 Toolkit**：Slack、Gmail、Google Drive 等集成即用

**不适合**：
- Agent 逻辑还没写好（Agno 解决的是"怎么跑"不是"怎么写"）
- 对闭源 Control Plane 零容忍（SDK + Runtime 开源，UI 管理界面闭源）
- 已有成熟的后端基础设施（可能与现有 API 网关/身份认证冲突）

---

### 4.8 MAF (Microsoft Agent Framework) — 企业中间件思维的多 Agent

**甜区**：你的团队在 **Azure 生态**、有 **.NET 和 Python 混合技术栈**、需要**企业级多 Agent 协作 + 插件化扩展 + Checkpoint/Time Travel**的复杂系统。

**为什么是它**：
- **插件化内核**：一切能力通过 Plugin 注册——Memory Connector 可插拔、Tool 标准化注册、OTel 原生集成
- **四种多 Agent 拓扑**：Handoff（交接）、GroupChat（群聊协商）、Swarm（蜂群）、层级编排——多 Agent 支持最灵活
- **Checkpoint + Time Travel**：状态管理能力对标 LangGraph，支持任意时间点回放和分支探索
- **多语言对齐**：Python + .NET 双一等公民，适合大型企业混合技术栈团队
- **OTel 原生**：可观测性开箱即用，trace/metrics 直接对接企业已有的 Prometheus/Jaeger/Datadog

**不适合**：
- 非 Azure/Microsoft 生态的团队（生态偏 Azure OpenAI，虽支持多供应商但亲和度明显）
- 快速 Demo（从 AutoGen 演化而来，概念模型较重，上手成本高于 CrewAI/OpenAI SDK）
- Python 侧有时滞后于 .NET（多语言对齐的代价——Python 发版节奏略慢）
- 小团队/独立开发者（它的设计哲学是"企业中间件"，个人项目杀鸡用牛刀）

**与 LangGraph 的核心差异**：

| 维度 | LangGraph | MAF |
|------|-----------|-----|
| 设计哲学 | 状态图驱动 | 插件化中间件 |
| 多 Agent | 图内节点 | 4 种独立拓扑模式 |
| 语言支持 | Python only | Python + .NET |
| 生态亲和 | LangSmith/LangServe | Azure/Semantic Kernel |
| 状态管理 | Checkpoint | Checkpoint + Time Travel |
| 扩展子 Agent | 新节点 + 边 | 新 Agent + Team 拓扑调整（更低门槛） |

**定位总结**：MAF 是 LangGraph 在企业 .NET/Azure 世界的对标物。如果你的企业已有 Azure 基础设施和 .NET 团队，MAF 比 LangGraph 更自然。

---

### 4.9 Claude Agent SDK — Coding Agent 的精准手术刀

**甜区**：你要做的 Agent 是**代码生成/重构/自动化开发工具**，愿意绑定 Claude 模型，需要用 **Hooks 机制精确控制 Agent 行为**。

**为什么是它**：
- **Hooks 治理模型**：不是"事后观察"，而是在 Agent 循环的关键节点（pre-tool-call / post-tool-call / pre-response / error）注入控制逻辑——比其他 SDK 的回调机制更精细
- **Coding 场景优化**：工具集天然面向文件操作、终端执行、代码搜索——Claude Code 就是用这套 SDK 构建的
- **Session Forking**：不是传统的"多 Agent 编排"，而是从当前 session 分叉出子 agent——轻量级并发，不需要图/团队抽象
- **MCP 工具生态**：Claude Agent SDK 是 MCP 协议的第一方实现者——In-process MCP server 零网络开销

**不适合**：
- 需要多供应商模型支持（**仅支持 Claude**——这是最大限制）
- 需要正式的多 Agent 编排（Session Fork 不等于多 Agent 系统——没有协商、没有角色分工）
- 需要内建记忆/状态持久化（无内建通用记忆系统，需自建）
- 需要可观测性（无内建 trace，需外接 Langfuse 等）
- Python Harness 完备度一般（Coding 场景好，通用场景的 harness 基础设施弱于 LangGraph/Pydantic AI）

**与 OpenAI Agents SDK 的对比**：

| 维度 | OpenAI Agents SDK | Claude Agent SDK |
|------|-------------------|------------------|
| 设计哲学 | 极简主义：3 个概念搞定 | 编程工具化：Hooks 精确治理 |
| 模型绑定 | OpenAI（偏） | **Claude（强绑定）** |
| 多 Agent | Handoff 链式转交 | Session Fork（非正式编排） |
| 控制力 | 低（简单回调） | **高**（Hooks 注入每个决策点） |
| 甜区 | 入门/PoC/简单任务 | Coding Agent/精细控制 |
| 可观测 | 内建 Tracing | 无内建，需外接 |
| 状态 | Context Variables（简单 KV） | Session 级（较简单） |

**定位总结**：Claude Agent SDK 不是通用 Agent 框架，是面向 **Coding/工具自动化** 的精准工具。如果你的场景是"做一个类 Claude Code 的东西"，它是最短路径。如果你的场景是通用 Agent，Pydantic AI 或 LangGraph 更合适。

---

### 4.10 Mastra — TypeScript 生态的唯一正统

**甜区**：团队是 **Next.js / React / Node.js 全栈**，想在不引入 Python 的前提下做 AI Agent。

**为什么是它**：
- **TS 原生**：API 设计贴合 TS 开发者习惯，Vercel/Next.js 无缝集成
- **Agents + Workflows + RAG + Eval 全包**：不需要拼凑多个库
- **前端团队友好**：同一语言前后端贯通，部署到 Vercel 一键

**不适合**：
- 需要生产级稳定性的关键业务（成熟度不如 Python 生态选手）
- 需要丰富的 AI 生态集成（Python 生态在模型、向量库、评估工具等方面领先 TS 两年+）
- 团队已有 Python AI 经验

## 5. 六大场景选型路径

### 场景 A：初学者/第一次做 Agent

```
推荐路径：手搓 100 行 → OpenAI SDK → 按需升级
```

**理由**：先理解 ReAct 循环本质（[R44](../04-%E5%B7%A5%E7%A8%8B%E5%AE%9E%E8%B7%B5/R44_%E6%B8%90%E8%BF%9B%E5%BC%8FAgent%E6%9E%84%E5%BB%BA%E5%AE%9E%E6%88%98.md) 有完整教程），再用 OpenAI SDK 感受"框架帮你做了什么"，最后根据实际需求升级。

### 场景 B：PoC / 快速验证想法（< 2 周）

```
推荐：smolagents（数据/代码任务）或 CrewAI（角色协作任务）
备选：OpenAI SDK（最简单的 tool-calling 场景）
```

**理由**：PoC 的核心是速度。smolagents 的 Code Agent 对"帮我处理这批数据"类任务上手极快；CrewAI 的 YAML 声明式对"搭一个多角色协作 demo"最快。

### 场景 C：生产级单 Agent 服务

```
推荐：Pydantic AI（类型安全 + DI + Logfire）
备选：LangGraph 单节点模式 + LangSmith
```

**理由**：生产环境最在乎可维护性、可测试性、可观测性。Pydantic AI 的 DI + 结构化输出 + Logfire trace 三件套在这些维度上最强。

### 场景 D：复杂多步骤编排 + HITL

```
推荐：LangGraph（最成熟） 或 ADK v2.0（Google 生态）
备选：Pydantic AI Graph（尚新但在追赶）
```

**理由**：需要 checkpoint/replay/条件分支/人工审批 时，LangGraph 的 Pregel 模型是经过最多生产验证的方案。ADK v2.0 的 Workflow Runtime 能力接近但生态还在建设中。

### 场景 E：Agent → 生产 API 服务

```
推荐：Agno（框架无关的 Platform 层）
备选：LangGraph Cloud（如果已经用了 LangGraph）
      自建 FastAPI（已有成熟后端团队）
```

**理由**：从"能跑的原型"到"可被用户使用的服务"之间有大量基础设施工作（session 管理、认证、多租户、trace）。Agno 20 行代码搞定这些；自建需要 1-3 个月。

### 场景 F：TypeScript 全栈团队

```
推荐：Mastra
备选：Vercel AI SDK（更轻量但不是 Agent 框架）
```

**理由**：如果团队不想引入 Python，Mastra 是目前唯一覆盖 Agent 完整生命周期的 TS 方案。

## 6. 最佳实践 15 条

### 架构层

**BP-01 · L1 层不要自己搓**
```python
# ✅ 正确：用 LiteLLM 统一模型调用
from litellm import completion
response = completion(model="anthropic/claude-sonnet-4-6", messages=[...])

# ❌ 错误：每个模型单独写 client
from openai import OpenAI
from anthropic import Anthropic
# ... 维护 N 个 client，每次加模型改一堆代码
```
LiteLLM 支持 100+ 模型 + 自动 fallback + budget 控制。统一入口节省的不是"写一次的时间"，是"维护 N 个月的精力"。

**BP-02 · 从最小框架开始，按需升级**
```
单Agent + 几个工具 → OpenAI SDK 或 手搓
需要结构化输出   → 升级到 Pydantic AI
需要状态持久化   → 升级到 LangGraph
需要变成 API    → 加上 Agno 或 FastAPI
```
**绝不要**第一天就上 LangGraph——过度设计的代价比将来迁移更高。

**BP-03 · 框架 ≠ 模型绑定**
```python
# ✅ 通过 LiteLLM 使用任何框架
from pydantic_ai import Agent
agent = Agent('litellm:anthropic/claude-sonnet-4-6', ...)
# 换模型只改字符串，不改代码逻辑
```
除非你明确只用一家模型，否则避免使用框架的原生模型绑定——保留迁移自由度。

### 开发层

**BP-04 · 先 trace 后 debug**
```python
# ✅ 接入 OpenTelemetry（框架无关）
# Pydantic AI → 自带 Logfire
# LangGraph → LangSmith
# 其他 → Langfuse / Phoenix
# 通用 → OpenTelemetry GenAI SemConv
```
**铁律**：任何 Agent 进入测试/生产前，必须有 trace 基础设施。否则出了问题只能 print 大法——在多步 Agent 中这等于盲人摸象。

**BP-05 · 工具函数写成纯函数 + 类型注解**
```python
# ✅ 框架无关的工具定义方式
from pydantic import BaseModel

class SearchInput(BaseModel):
    query: str
    max_results: int = 5

def web_search(input: SearchInput) -> list[dict]:
    """Search the web for information.
    
    Args:
        input: Search parameters including query and max_results
    """
    # 实现...
    return results
```
这样定义的工具可以：① 被任何框架加载 ② 单独测试 ③ 通过 MCP 暴露。不要把工具逻辑和框架耦合。

**BP-06 · 结构化输出是你的安全网**
```python
# ✅ 用 Pydantic 模型约束 LLM 输出
class AnalysisResult(BaseModel):
    summary: str
    confidence: float = Field(ge=0, le=1)
    sources: list[str]
    
agent = Agent('...', output_type=AnalysisResult)
# LLM 输出不符合 schema → 自动重试 → 保证类型安全
```
永远不要假设 LLM 输出格式正确。用 Pydantic 模型约束 = 把"运行时报错"提前到"类型检查阶段"。

### 生产层

**BP-07 · Token 预算 + 超时 + 重试三件套**
```python
# ✅ 任何 Agent 必须有的三个护栏
agent_config = {
    "max_tokens": 4096,         # 单次输出上限
    "max_turns": 10,            # 最大对话轮次
    "timeout": 60,              # 单轮超时（秒）
    "retry_on_429": True,       # Rate limit 自动重试
    "retry_max": 3,             # 最大重试次数
    "total_token_budget": 50000 # 整个会话 Token 预算
}
```
没有预算控制的 Agent = 一张没有额度限制的信用卡交给一个不可预测的 AI。

**BP-08 · 降级策略不是可选的**
```python
# ✅ 至少三级降级
models = [
    "anthropic/claude-sonnet-4-6",  # 主力
    "openai/gpt-5.2",               # 备选
    "deepseek/deepseek-chat",       # 兜底（便宜）
]
# LiteLLM 内置 fallback 支持
```

**BP-09 · Session 持久化从第一天就设计**
```python
# ✅ 即使是 PoC，也用 SQLite 存 session
from agno.storage import SqliteStorage
storage = SqliteStorage(db_file="sessions.db")

# ❌ 把对话历史存在内存里
messages = []  # 进程一重启就全丢了
```
"先跑通再加持久化"听起来合理，实际上改造成本远大于一开始就加。

**BP-10 · 隔离用户数据（多租户安全）**
```python
# ✅ 每个请求携带 user_id，session 按 user 隔离
@app.post("/chat")
async def chat(request: ChatRequest, user: User = Depends(get_current_user)):
    session = await storage.get_or_create(user_id=user.id)
    result = await agent.run(request.message, session=session)
    return result
```
**绝不能**让用户 A 看到用户 B 的 Agent 历史。这是 OWASP 级别的安全要求。

### 评估层

**BP-11 · Agent 上线前必须有 eval**
```python
# ✅ 最小 eval 方案（Pydantic AI / Promptfoo 都支持）
test_cases = [
    {"input": "查一下今天天气", "expected_tool": "weather_tool"},
    {"input": "你好", "expected_behavior": "不调任何工具"},
]
# 跑一遍，通过率 < 90% 就不上线
```

**BP-12 · 用真实失败 case 驱动改进**
```python
# ✅ 收集生产中的失败 case → 加入 eval 集
failures_log = "logs/agent_failures.jsonl"
# 每次线上出问题：
# 1. 记录完整 trace（input + tool calls + output）
# 2. 人工标注"期望行为"
# 3. 加入自动化 eval
```

### 协议层

**BP-13 · MCP 优先，自定义 Tool 其次**
```python
# ✅ 优先使用 MCP server 提供的工具
from smolagents import ToolCollection
tools = ToolCollection.from_mcp("npx -y @modelcontextprotocol/server-filesystem")

# 只有 MCP 生态没有的工具才自己写
```
MCP 工具可被任何支持 MCP 的 Agent 复用。自定义工具只能在你的代码里用。

**BP-14 · 不要过早锁定一个框架**
```python
# ✅ 核心业务逻辑与框架解耦
# business_logic.py — 纯 Python，无框架依赖
def analyze_document(doc: str) -> AnalysisResult: ...
def search_knowledge_base(query: str) -> list[Document]: ...

# agent.py — 只在这里引入框架
from pydantic_ai import Agent
agent = Agent(tools=[analyze_document, search_knowledge_base])
```
框架每年洗一次牌。你的业务逻辑应该能活过三代框架。

**BP-15 · 监控成本，设置告警**
```
# ✅ 必须监控的指标
- 日均 Token 消耗 + 趋势
- 每用户平均成本
- LLM 调用失败率
- 平均响应延迟 (p50/p95/p99)
- 工具调用成功率
```
没有成本监控的 Agent 服务 = "月底收到账单才发现烧了多少钱"。

## 7. 反模式与避坑

| 反模式 | 为什么是坑 | 正确做法 |
|--------|-----------|---------|
| **一开始就上 LangGraph** | 学习曲线陡，PoC 阶段的复杂度是净负担 | 先 OpenAI SDK 验证想法，确认需要状态管理再迁移 |
| **用 CrewAI 做确定性流程** | 角色"自主协商"在需要精确控制的场景里是噪声 | 用 CrewAI Flows 或直接用 LangGraph |
| **用 smolagents 做面向用户的产品** | 代码执行安全风险高，沙箱增加延迟和部署复杂度 | 面向用户用 tool-calling 范式，内部工具再用 CodeAgent |
| **所有模型调用用同一个 SDK** | 单点故障 + 无法按场景选最优模型 | LiteLLM 做路由层，按任务路由到不同模型 |
| **忽略 trace 直接上生产** | 多步 Agent 出问题时完全无法定位 | 第一天就接 Langfuse/Logfire/LangSmith |
| **把框架 API 暴露给前端** | 框架 API 设计不考虑安全/限流/多租户 | 用 Agno 或自建 FastAPI 做一层 API Gateway |
| **ADK v2.0 用于现有 v1.x 生产系统** | Breaking Changes 太多，Session schema 不兼容 | 新项目用 v2.0，现有系统等迁移指南成熟再动 |

## 8. 结论与开放问题

### 核心结论

1. **没有"最好"的 Agent SDK，只有"最匹配场景"的**。本文的甜区矩阵就是为了帮你在 30 秒内判断"我的场景落在谁的领地里"。

2. **2026-05 的格局变化**：Pydantic AI 正在从"类型安全的 Agent SDK"进化为全能型选手（新增 Graph + Durable Execution + Capabilities）；ADK v2.0 从"Gemini 绑定 SDK"升级为正面对标 LangGraph 的图编排框架。两者都在侵蚀 LangGraph 的地盘。

3. **选框架的本质是选"你愿意被谁的观点约束"**：
   - LangGraph → "一切皆状态图"
   - CrewAI → "一切皆角色协作"
   - Pydantic AI → "一切皆类型安全的依赖注入"
   - smolagents → "一切皆可执行代码"
   - Agno → "别管怎么写，先跑起来再说"

4. **协议标准化是最大的趋势红利**：MCP（工具互通）+ A2A（Agent 互通）+ AG-UI（前端互通）正在降低框架锁定风险。选错了？迁移成本在缩小。

### 推荐的"安全路径"

```
如果你今天要从零开始做一个生产级 Agent：
  模型调用层：LiteLLM
  Agent 逻辑层：Pydantic AI（工程质量最高）
  运行时层：Agno 或自建 FastAPI
  监控层：Langfuse（开源）或 Logfire（Pydantic 原生）
```

如果团队是 LangChain 老用户，继续用 LangGraph 也完全正确——它的生态完整性短期内无人超越。

### 开放问题

1. **Pydantic AI 的全能化**（Graph + Durable + Capabilities）会不会让其他轻量 SDK 失去存在意义？还是说复杂度增加后会失去"简单"这个卖点？
2. **ADK v2.0 的 Workflow Runtime** 能否在 Google Cloud 之外建立生态？还是会重蹈 TensorFlow vs PyTorch 的覆辙（好技术但生态输了）？
3. **Agno 的闭源 Control Plane** 长期策略？如果社区出现纯开源 Platform 层替代品，Agno 的护城河在哪？
4. **协议标准化**是否会导致"Agent SDK 不重要了"——即未来只需要一个 MCP client + A2A endpoint + 100 行胶水代码？
