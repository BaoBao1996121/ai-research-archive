## 🧠 心智模型：三层失败模式

> 没有 X 层会发生什么 = 你需要 X 层。先定位症状再补层，不要无脑上全套。

### 三类典型失败案例

```
案例 A：客服 Agent 回答完用户上一句就忘了上下文
  user: "我上周买了那双鞋"
  agent: "请问你上周买了什么？"
  → 缺 L1 Working Memory（连最近几轮都没保留）

案例 B：用户问"我们之前讨论过的方案到底是哪个？"，Agent 答不上
  → 缺 L2 Episodic（没有事件时间线，无法回忆"我们讨论过 X 然后 Y"）

案例 C：用户跨周回来，重新问"我喜欢什么咖啡？"，Agent 一无所知
  → 缺 L3 Semantic（没有把"用户喜欢拿铁"提取成稳定事实）

案例 D：用户上次说"我搬到北京了"，这次问"我住哪？"，Agent 答上海
  → 缺 L4 Conflict Resolution（旧事实没失效）

案例 E：聊了半年，记忆库膨胀到 50 万条，检索 latency 飙到 3 秒
  → 缺 L5 Forget / Consolidation
```

### 三层认知映射（对照 R72 §2.1）

| 层 | 类比人脑 | 数据形态 | 写入时机 | 读取时机 |
|---|---|---|---|---|
| **L1 Working** | 短时记忆 | 最近 N 轮 raw messages | 每轮都写 | 每轮都读 |
| **L2 Episodic** | 情景记忆 | 时间戳事件流 | 每轮都写 | 用户问"什么时候发生过 X" |
| **L3 Semantic** | 语义记忆 | 抽取后的事实条目 | 触发式（攒 N 轮 / 关键事件）| 用户提到与已存事实相关的话题 |
| **L4 Conflict** | 信念修正 | invalid_at 元数据 | 写入新事实时检测 | 读取时过滤 invalid |
| **L5 Forget** | 睡眠整理 | 合并/丢弃 | 后台定期 / 触发 | 间接（影响检索池子）|

> **关键直觉**：L1/L2 是**事实**（消息真的发生过），L3 是**抽取**（从消息归纳出的稳定属性），L4/L5 是**维护**（保持 L3 不腐烂）。混淆这三个角色是新手常见错误——比如把 L1 也做"事实抽取"，那是过度设计。

### 3.1 M0 · 没有记忆的 Agent 长什么样

```python
from openai import OpenAI
oa = OpenAI()

def chat_M0(message: str) -> str:
    resp = oa.chat.completions.create(
        model="gpt-4o-mini",
        messages=[{"role": "user", "content": message}],
    )
    return resp.choices[0].message.content
```

跑一下：

```python
for t in TURNS:
    chat_M0(t)
print(chat_M0(QUERY))
# → "我没有任何关于您的信息..."
```

**症结**：每次调用都是独立请求，连"上一句说了什么"都不知道。这就是为什么需要 L1。

### 3.2 M1 · Working Memory（~50 行 累计）

最朴素的做法：保留最近 N 轮原始消息塞回 prompt。

```python
from collections import deque
from openai import OpenAI

oa = OpenAI()

class WorkingMemory:
    """L1：最近 N 轮原始消息（FIFO）"""
    def __init__(self, max_turns: int = 10):
        self.buffer: deque = deque(maxlen=max_turns)

    def append(self, role: str, content: str):
        self.buffer.append({"role": role, "content": content})

    def to_messages(self) -> list:
        return list(self.buffer)


class AgentM1:
    def __init__(self):
        self.wm = WorkingMemory(max_turns=10)

    def chat(self, user_input: str) -> str:
        self.wm.append("user", user_input)
        resp = oa.chat.completions.create(
            model="gpt-4o-mini",
            messages=self.wm.to_messages(),
        )
        reply = resp.choices[0].message.content
        self.wm.append("assistant", reply)
        return reply


# Demo
agent = AgentM1()
for t in TURNS:
    agent.chat(t)
print(agent.chat(QUERY))
# → 在最近 N 轮内的话能记得（北京、历史书），但 N 之外的会丢
```

**它解决了什么**：单会话内的连贯性。

**它没解决什么**：
- 关掉进程就忘
- 第 11 轮就把第 1 轮挤出去了
- 跨用户混在一起

#### 五家源码对照 · L1 怎么做的

| 框架 | 关键源码 | 写法差异 |
|---|---|---|
| **Hermes** | `agent/context_compressor.py`（[R35](../06-%E5%B7%A5%E5%85%B7%E4%B8%8E%E7%94%9F%E6%80%81/R35_HermesAgent%E8%AE%B0%E5%BF%86%E4%B8%8ESkill%E8%87%AA%E8%BF%AD%E4%BB%A3%E6%BA%90%E7%A0%81%E6%8B%86%E8%A7%A3.md) §3.2）| 不简单截断，而是**触发压缩前 fork 一个子 Agent 做摘要**——这是高阶玩法 |
| **LangGraph** | `langgraph.checkpoint.MemorySaver` | 把全部历史持久化到 thread_id，不主动截断（依赖上层做） |
| **OpenAI Assistants API** | 服务端自动管理 thread | 黑盒，不可定制 |
| **我们的 M1** | `deque(maxlen=N)` | 最朴素的 FIFO，够用即可 |

**抄哪家**：M1 阶段不需要抄任何家——FIFO 是底线方案，等真遇到 token 超限了再升级到 Hermes 的"摘要式压缩"。

### 3.3 M2 · +Episodic（~110 行 累计）

加一层"事件流"——每条消息打时间戳存起来，可以按时间窗口或关键词回忆。

```python
import time
import sqlite3
from typing import List, Dict
from collections import deque
from openai import OpenAI

oa = OpenAI()


class EpisodicMemory:
    """L2：事件流（SQLite + FTS5 全文索引）"""
    def __init__(self, db_path: str = "episodic.db"):
        self.conn = sqlite3.connect(db_path)
        self.conn.executescript("""
            CREATE TABLE IF NOT EXISTS events (
                id INTEGER PRIMARY KEY AUTOINCREMENT,
                user_id TEXT NOT NULL,
                role TEXT,
                content TEXT,
                ts REAL
            );
            CREATE VIRTUAL TABLE IF NOT EXISTS events_fts USING fts5(
                content, content=events, content_rowid=id
            );
            CREATE TRIGGER IF NOT EXISTS events_ai AFTER INSERT ON events
              BEGIN INSERT INTO events_fts(rowid, content) VALUES (new.id, new.content); END;
        """)
        self.conn.commit()

    def append(self, user_id: str, role: str, content: str):
        self.conn.execute(
            "INSERT INTO events(user_id, role, content, ts) VALUES (?,?,?,?)",
            (user_id, role, content, time.time()),
        )
        self.conn.commit()

    def search(self, user_id: str, query: str, limit: int = 5) -> List[Dict]:
        # FTS5 全文检索 + 用户隔离
        cur = self.conn.execute("""
            SELECT e.role, e.content, e.ts FROM events_fts f
            JOIN events e ON f.rowid = e.id
            WHERE events_fts MATCH ? AND e.user_id = ?
            ORDER BY e.ts DESC LIMIT ?
        """, (query, user_id, limit))
        return [{"role": r, "content": c, "ts": t} for (r, c, t) in cur.fetchall()]


class AgentM2:
    def __init__(self):
        self.wm = deque(maxlen=10)
        self.em = EpisodicMemory()

    def chat(self, user_id: str, user_input: str) -> str:
        # 1) 写 episodic
        self.em.append(user_id, "user", user_input)

        # 2) 检索相关历史事件（取关键词，简单做法：用 LLM 提关键词或直接用原文）
        relevant = self.em.search(user_id, user_input, limit=3)
        ctx_block = ""
        if relevant:
            ctx_block = "【相关历史】\n" + "\n".join(
                f"- ({time.strftime('%m-%d', time.localtime(r['ts']))}) {r['content']}"
                for r in relevant
            )

        # 3) 装配 messages
        msgs = []
        if ctx_block:
            msgs.append({"role": "system", "content": ctx_block})
        msgs.extend(self.wm)
        msgs.append({"role": "user", "content": user_input})

        resp = oa.chat.completions.create(model="gpt-4o-mini", messages=msgs)
        reply = resp.choices[0].message.content

        self.wm.append({"role": "user", "content": user_input})
        self.wm.append({"role": "assistant", "content": reply})
        self.em.append(user_id, "assistant", reply)
        return reply


# Demo
agent = AgentM2()
for t in TURNS:
    agent.chat("alice", t)
print(agent.chat("alice", QUERY))
# → 现在即使 N=10 滑出去了，FTS5 也能命中"北京"、"历史"这些关键词
```

**它解决了什么**：
- 跨会话的关键词召回
- 用户隔离（user_id namespace）
- 持久化（关进程也不丢）

**它没解决什么**：
- FTS5 是关键词匹配，"我爱看历史书"和"我喜欢历史类"匹配不上（语义鸿沟）
- 没"事实抽取"——存的是原始消息，回答时模型还要从一堆消息里自己归纳

#### 五家源码对照 · L2 怎么做的

| 框架 | 关键设计 | 源码位置 |
|---|---|---|
| **Hermes** | SQLite + **FTS5**（和我们一样！但加了 LLM 做 query 改写）| `tools/session_search_tool.py`（[R35](../06-%E5%B7%A5%E5%85%B7%E4%B8%8E%E7%94%9F%E6%80%81/R35_HermesAgent%E8%AE%B0%E5%BF%86%E4%B8%8ESkill%E8%87%AA%E8%BF%AD%E4%BB%A3%E6%BA%90%E7%A0%81%E6%8B%86%E8%A7%A3.md) §10）|
| **Mem0** | 不显式分 Episodic 层——所有历史走 Semantic 抽取 | `mem0/memory/main.py: add()` |
| **Letta** | `recall_memory`（最近 N 轮 + archival 全文）| `letta/agent.py: recall_memory_search()` |
| **Zep** | thread.add_messages → 自动建图谱 + 事件节点 | Zep Cloud API（OSS 已弃用）|
| **LangMem** | 不分层，全靠 BaseStore | `langmem/store.py` |

**抄哪家**：Hermes 的 FTS5 路线最直接——SQLite 自带、零部署成本、性能足够支撑百万级条目。Mem0 跳过 L2 直接 L3 的做法是"产品化偷懒"，自建别这么干，因为 L2 是 L3 的兜底（事实抽取漏了的，关键词还能捞回来）。

> **细节硬核**：Hermes 在 query 进入 FTS5 之前，会先调一次 LLM 把"我喜欢什么书"改写成 `book OR reading OR like`——这是处理 FTS5 关键词鸿沟的实用招数。我们的 M2 偷懒没做，进 M3 用向量检索就解决了。

### 3.4 M3 · +Semantic（~200 行 累计）

这是记忆系统的**真正心脏**。前面两层都是"存原始消息"，从这一层开始我们要**抽取稳定事实**并做向量检索。

```python
import os, time, json, math, struct
import numpy as np
import redis
from redis.commands.search.field import VectorField, TextField, NumericField, TagField
from redis.commands.search.indexDefinition import IndexDefinition, IndexType
from redis.commands.search.query import Query
from openai import OpenAI

oa = OpenAI()
r = redis.Redis(host="localhost", port=6379, decode_responses=False)

DIM = 1536
INDEX = "idx:facts"
PREFIX = "fact:"

# 评分系数（核心调参点）
ALPHA, BETA, GAMMA = 0.7, 0.2, 0.1     # semantic / recency / importance
HALF_LIFE_DAYS = 7


# ───────────────── 1. 事实抽取 ─────────────────
EXTRACT_PROMPT = """\
你是事实抽取器。从用户消息中提取关于用户的**稳定事实**（属性、偏好、关系、经历）。

规则：
- 只提取明确陈述的事实，不推测
- 每条 ≤ 25 字，第三人称（"用户..."）
- 不提取临时状态（"用户现在生气"❌）
- 标注 importance ∈ [1,2,3]（1=普通偏好/2=身份属性/3=关键决定）
- 输出 JSON: {{"facts": [{{"text": "...", "importance": N}}]}}

消息: {msg}
"""

def extract_facts(message: str) -> list:
    resp = oa.chat.completions.create(
        model="gpt-4o-mini",
        messages=[{"role": "user", "content": EXTRACT_PROMPT.format(msg=message)}],
        response_format={"type": "json_object"},
    )
    try:
        return json.loads(resp.choices[0].message.content).get("facts", [])
    except Exception:
        return []


# ───────────────── 2. Embedding ─────────────────
def embed(text: str) -> bytes:
    v = oa.embeddings.create(
        model="text-embedding-3-small", input=text
    ).data[0].embedding
    return np.asarray(v, dtype=np.float32).tobytes()


# ───────────────── 3. 索引（幂等）─────────────────
def ensure_index():
    try:
        r.ft(INDEX).info()
        return
    except redis.ResponseError:
        pass
    schema = (
        TextField("content"),
        TagField("user_id"),
        NumericField("ts"),
        NumericField("importance"),
        NumericField("access_count"),
        NumericField("invalid_at"),  # M4 才用，先开字段
        VectorField("embedding", "HNSW", {
            "TYPE": "FLOAT32", "DIM": DIM, "DISTANCE_METRIC": "COSINE"
        }),
    )
    r.ft(INDEX).create_index(
        schema,
        definition=IndexDefinition(prefix=[PREFIX], index_type=IndexType.HASH),
    )


# ───────────────── 4. 写入 ─────────────────
def add_semantic(user_id: str, message: str) -> list:
    ensure_index()
    facts = extract_facts(message)
    now = time.time()
    for f in facts:
        text = f["text"]
        imp = f.get("importance", 1)
        fid = f"{PREFIX}{user_id}:{int(now*1000)}:{abs(hash(text)) & 0xffff}"
        r.hset(fid, mapping={
            "content": text,
            "user_id": user_id,
            "ts": now,
            "importance": imp,
            "access_count": 0,
            "invalid_at": 0,
            "embedding": embed(text),
        })
    return facts


# ───────────────── 5. 检索（多信号融合）─────────────────
def search_semantic(user_id: str, query: str, top_k: int = 5) -> list:
    q_vec = embed(query)
    knn = (
        Query(f"(@user_id:{{{user_id}}} @invalid_at:[0 0])"  # 只取 valid（M4 起作用）
              f"=>[KNN {top_k*3} @embedding $vec AS dist]")
        .sort_by("dist")
        .return_fields("content", "ts", "importance", "access_count", "dist")
        .dialect(2).paging(0, top_k * 3)
    )
    res = r.ft(INDEX).search(knn, query_params={"vec": q_vec})
    now = time.time()
    scored = []
    for d in res.docs:
        sem = 1 - float(d.dist)               # cosine distance → similarity
        recency = math.exp(-((now - float(d.ts)) / 86400) / HALF_LIFE_DAYS)
        imp = math.log1p(int(d.importance) + int(d.access_count))
        score = ALPHA * sem + BETA * recency + GAMMA * imp
        scored.append({"id": d.id, "content": d.content, "score": score})
    scored.sort(key=lambda x: x["score"], reverse=True)
    # 命中加 access_count
    for s in scored[:top_k]:
        r.hincrby(s["id"], "access_count", 1)
    return scored[:top_k]


# ───────────────── 6. Agent 装配 ─────────────────
class AgentM3:
    def __init__(self):
        from collections import deque
        self.wm = deque(maxlen=10)

    def chat(self, user_id: str, user_input: str) -> str:
        # 1) 检索语义记忆
        hits = search_semantic(user_id, user_input, top_k=5)
        ctx = ""
        if hits:
            ctx = "【关于用户的已知事实】\n" + "\n".join(
                f"- {h['content']} (相关度 {h['score']:.2f})" for h in hits
            )

        msgs = []
        if ctx:
            msgs.append({"role": "system", "content": ctx})
        msgs.extend(self.wm)
        msgs.append({"role": "user", "content": user_input})

        reply = oa.chat.completions.create(
            model="gpt-4o-mini", messages=msgs
        ).choices[0].message.content

        # 2) 写入：Working + Semantic
        self.wm.append({"role": "user", "content": user_input})
        self.wm.append({"role": "assistant", "content": reply})
        added = add_semantic(user_id, user_input)
        if added:
            print(f"  [+ {len(added)} facts]: {[f['text'] for f in added]}")
        return reply


# ───────────────── Demo ─────────────────
if __name__ == "__main__":
    agent = AgentM3()
    for t in TURNS:
        agent.chat("alice", t)
    print("\n=== 查询 ===")
    print(agent.chat("alice", QUERY))
```

**预期输出**：

```

  [+ 2 facts]: ['用户喜欢科幻小说', '用户最喜欢《三体》']
  [+ 1 facts]: ['用户搬到北京']
  [+ 1 facts]: ['用户更喜欢历史类的书']

=== 查询 ===

```

**注意观察**：
- "上海"和"北京"**共存**（M3 还没加冲突解决）——靠 recency 让北京排前面
- 重复触发同一查询，access_count 上升，importance 项让"高频访问"的记忆更稳
- **重要硬核细节**：检索用了 `top_k * 3` 多取再 rerank——这是因为向量近邻召回不一定按真实分数排，必须二阶段打分。Mem0 v3 的"multi-signal scoring"本质就是这个。

> 这是新手最容易写垮的地方。看看专业玩家是怎么写的。

**Hermes**（`agent/prompt_builder.py` 中的 SKILLS_GUIDANCE 片段，[R35](../06-%E5%B7%A5%E5%85%B7%E4%B8%8E%E7%94%9F%E6%80%81/R35_HermesAgent%E8%AE%B0%E5%BF%86%E4%B8%8ESkill%E8%87%AA%E8%BF%AD%E4%BB%A3%E6%BA%90%E7%A0%81%E6%8B%86%E8%A7%A3.md) §6）：

### 3.5 M4 · +Conflict Resolution（~260 行 累计）

问题：M3 让"上海"和"北京"共存——靠 recency 让北京排前面，但旧事实仍然会被检索到，可能污染回答。M4 解决这个。

**两种范式选哪个**：

| 范式 | 代表 | 做法 | 适合 |
|---|---|---|---|
| **共存 + 时间排序** | Mem0 v3 | 旧事实保留，按 ts 排序 | 需要事实历史（"用户曾喜欢科幻"也是有用信息）|
| **invalid_at 标记** | Zep | 旧事实加失效时间戳，检索时过滤 | 需要事实最新（CRM/医疗）|
| **DELETE 删除** | 早期 Mem0 v2 | 直接干掉旧的 | 已被废弃——丢失审计能力 |

**我们抄 Zep**——保留可追溯，但读取默认只取 valid。

```python
# 续 M3 代码

CONFLICT_PROMPT = """\
判断"新事实"是否与"已知事实"中的某条**矛盾**（指同一主语+谓语，宾语不同）。
注意：
- "用户喜欢科幻" + "用户喜欢历史" → 不一定矛盾（可以都喜欢）
- "用户住上海" + "用户住北京" → 矛盾（一个人同时只住一处）
- "用户名为 Alice" + "用户是软件工程师" → 不矛盾（不同维度）

输出 JSON: {{"contradicts": [<已知事实在列表中的下标>], "reason": "..."}}
若无矛盾: {{"contradicts": [], "reason": ""}}

新事实: {new_fact}
已知事实:
{known_facts}
"""

def detect_conflict(user_id: str, new_fact: str) -> list:
    """返回与新事实冲突的旧事实 id 列表"""
    # 取该 user 同主题的已知事实
    candidates = search_semantic(user_id, new_fact, top_k=10)
    if not candidates:
        return []
    listed = "\n".join(f"{i}. {c['content']}" for i, c in enumerate(candidates))
    resp = oa.chat.completions.create(
        model="gpt-4o-mini",
        messages=[{"role": "user", "content": CONFLICT_PROMPT.format(
            new_fact=new_fact, known_facts=listed
        )}],
        response_format={"type": "json_object"},
    )
    try:
        idx_list = json.loads(resp.choices[0].message.content).get("contradicts", [])
        return [candidates[i]["id"] for i in idx_list if 0 <= i < len(candidates)]
    except Exception:
        return []


def invalidate(fact_ids: list):
    now = time.time()
    for fid in fact_ids:
        r.hset(fid, "invalid_at", now)


# 替换 M3 的 add_semantic
def add_semantic_v2(user_id: str, message: str) -> list:
    ensure_index()
    facts = extract_facts(message)
    now = time.time()
    for f in facts:
        text = f["text"]
        imp = f.get("importance", 1)
        # ★ 写入前检测冲突
        conflicting = detect_conflict(user_id, text)
        if conflicting:
            invalidate(conflicting)
            print(f"  [⚠ invalidated {len(conflicting)} old facts for: {text}]")
        fid = f"{PREFIX}{user_id}:{int(now*1000)}:{abs(hash(text)) & 0xffff}"
        r.hset(fid, mapping={
            "content": text, "user_id": user_id, "ts": now,
            "importance": imp, "access_count": 0, "invalid_at": 0,
            "embedding": embed(text),
        })
    return facts
```

注意 M3 里 `search_semantic` 早就加了 `@invalid_at:[0 0]` 过滤——M4 把它激活。

**预期输出**：

```
  [+ 3 facts]: ['用户名为 Alice', '用户住在上海', '用户是软件工程师']
  [+ 2 facts]: ['用户喜欢科幻小说', '用户最喜欢《三体》']
  [⚠ invalidated 1 old facts for: 用户搬到北京]
  [+ 1 facts]: ['用户搬到北京']
  [⚠ invalidated 1 old facts for: 用户更喜欢历史类的书]
  [+ 1 facts]: ['用户更喜欢历史类的书']

=== 查询 ===
... 你住在北京，是软件工程师 ... 你现在更喜欢历史类的书 ...
```

#### 关键决策：冲突检测要不要走 LLM

| 方案 | 速度 | 准确率 | 成本 |
|---|---|---|---|
| 完全规则（同主语+谓语字符串匹配）| ~0ms | 60% | 0 |
| Embedding 相似度阈值 | ~50ms | 75% | 低 |
| **LLM 判断（我们用的）** | ~400ms | 90%+ | 中 |
| LLM + 缓存（同事实只判一次）| 摊薄 ~50ms | 90%+ | 低 |

**生产建议**：走 LLM，但加缓存（同 user 的同一新事实只判一次）。Zep 的 Graphiti 走 LLM 路线，所以延迟 ~200ms。

#### 五家源码对照 · L4

| 框架 | 怎么做 | 源码 |
|---|---|---|
| **Zep / Graphiti** | 抽实体+关系建图 → 新边写入时检测时序矛盾 → 旧边 invalid_at | `graphiti-core/edges.py: invalidate_edges()` |
| **Mem0 v3** | ADD-only，不检测冲突，靠时间排序 | 论文 arXiv:2504.19413 §3.2 |
| **Letta** | Agent 自己用 `core_memory_replace` 改写 | 完全交给模型 |
| **Hermes** | 没冲突检测，让模型在写入时直接覆盖 MEMORY.md 同行 | [R35](../06-%E5%B7%A5%E5%85%B7%E4%B8%8E%E7%94%9F%E6%80%81/R35_HermesAgent%E8%AE%B0%E5%BF%86%E4%B8%8ESkill%E8%87%AA%E8%BF%AD%E4%BB%A3%E6%BA%90%E7%A0%81%E6%8B%86%E8%A7%A3.md) §3.3 |
| **我们的 M4** | LLM 二阶段判断 + invalid_at 标记 | 抄 Zep 简化版 |

### 3.6 M5 · +Forget / Consolidation（~330 行 累计）

问题：聊几个月后 invalid_at 的"垃圾"和重复的相似事实越积越多——检索池子里 50% 是无用条目，影响速度和质量。

**三个动作**：

1. **删 invalid 超 30 天的**（已失效又老）
2. **合并相似 valid 事实**（"用户喜欢拿铁咖啡"+"Alice 偏爱拿铁"→合一条）
3. **清理低分长期未用**（access_count=0 且 ts > 90 天）

```python
# 续 M4

def consolidate(user_id: str, dry_run: bool = False):
    """后台整理：删失效、合相似、清低分"""
    now = time.time()

    # 1) 删 invalid_at 超 30 天的
    cur = r.ft(INDEX).search(
        Query(f"@user_id:{{{user_id}}} @invalid_at:[1 +inf]")
        .return_fields("invalid_at").paging(0, 10000)
    )
    deleted = 0
    for d in cur.docs:
        if now - float(d.invalid_at) > 30 * 86400:
            if not dry_run:
                r.delete(d.id)
            deleted += 1

    # 2) 合并相似 valid 事实（O(N²) 简化版，N 大时改用聚类）
    cur = r.ft(INDEX).search(
        Query(f"@user_id:{{{user_id}}} @invalid_at:[0 0]")
        .return_fields("content", "ts", "importance", "access_count")
        .paging(0, 10000)
    )
    docs = list(cur.docs)
    merged = 0
    seen_ids = set()
    for i, a in enumerate(docs):
        if a.id in seen_ids: continue
        for b in docs[i+1:]:
            if b.id in seen_ids: continue
            # 用 embedding 算相似度（生产建议预先 cache embedding）
            sim = cosine_sim(a.id, b.id)  # 见下方 helper
            if sim > 0.92:                # 阈值调参
                # 保留 importance 高的、ts 新的
                keeper, dropper = (a, b) if (
                    int(a.importance) > int(b.importance) or
                    (int(a.importance) == int(b.importance) and float(a.ts) >= float(b.ts))
                ) else (b, a)
                if not dry_run:
                    r.delete(dropper.id)
                seen_ids.add(dropper.id)
                merged += 1

    # 3) 清低分长期未用
    cur = r.ft(INDEX).search(
        Query(f"@user_id:{{{user_id}}} @invalid_at:[0 0] @access_count:[0 0]")
        .return_fields("ts", "importance").paging(0, 10000)
    )
    pruned = 0
    for d in cur.docs:
        if int(d.importance) < 2 and (now - float(d.ts)) > 90 * 86400:
            if not dry_run:
                r.delete(d.id)
            pruned += 1

    return {"deleted_invalid": deleted, "merged_dup": merged, "pruned_cold": pruned}


def cosine_sim(id_a: str, id_b: str) -> float:
    a = np.frombuffer(r.hget(id_a, "embedding"), dtype=np.float32)
    b = np.frombuffer(r.hget(id_b, "embedding"), dtype=np.float32)
    return float(np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b)))
```

**触发时机选择**：

| 时机 | 优点 | 缺点 |
|---|---|---|
| **每 N 轮触发**（在线）| 简单 | 阻塞当前对话，影响延迟 |
| **写入后异步任务**（推荐）| 不阻塞 | 需要任务队列（Celery/RQ）|
| **离线 cron**（夜间）| 资源充足 | 老数据可能短期影响检索 |
| **Letta 路线**（sleep-time agent）| Agent 自主决定 | 实现复杂，Token 贵 |

**推荐做法**：每天凌晨 cron 跑一次全 user 的 consolidate（轻量场景）；高频场景用 Celery 异步触发。

#### 五家源码对照 · L5

| 框架 | 整理机制 | 触发 |
|---|---|---|
| **Letta** | sleep-time agent（一个独立 Agent 离线读 archival 整理）| 用户配置时间窗 |
| **Mem0** | 写入时同步合并相似度高的 | 每次 add() |
| **Zep** | Graphiti 自动 community detection 重组节点 | 后台定时 |
| **Hermes** | 文件 + LLM patch（写入时同步替换）| 在 nudge 子 Agent 里 |
| **我们的 M5** | 后台 consolidate() 函数 | cron / 异步队列 |

## 🔍 关键决策点的五家源码对照

把上面散落的对照集中成一张总表，做技术决策时回头查这张。

| 决策点 | Mem0 | Letta | Zep | Hermes | LangMem | M5 抄了哪家 |
|---|---|---|---|---|---|---|
| 抽取触发时机 | 每条消息 | Agent 自决 | thread.add_messages | 5+ 工具调用后 | Background mode | Mem0（每条）|
| 抽取 prompt | JSON facts | 工具调用 | 自动建图谱 | SKILLS_GUIDANCE | 用户自定义 | Mem0+Hermes 融合 |
| 检索打分 | multi-signal | recency+vec | graph traversal | FTS5+LLM rerank | vec only | Mem0 多信号 |
| 时序处理 | timestamp 排序 | FIFO+recall | valid_at/invalid_at | 文件覆盖 | metadata | Zep invalid_at |
| 冲突解决 | ADD-only 共存 | Agent 工具调用 | LLM 判断 | 文件覆盖 | 无 | Zep 简化版 |
| 遗忘机制 | UPDATE/DELETE | archival fade | 不删（仅 invalid）| 字符上限+替换 | 工具调用 | 三招混合 |
| 用户隔离 | user_id | 单 Agent 单 user | user_id+thread_id | 进程级 | namespace tuple | TagField user_id |
| 外部 store | 多种向量库 | PostgreSQL | Neo4j+Postgres | SQLite+插件 | LangGraph Store | Redis |

**反 cheat-sheet 直觉**：你以为五家是"五种不同方案"。手搓一遍后会发现——**它们是同一个系统的不同参数化**。M3+M4+M5 的 ~330 行覆盖了所有家的核心抽象，区别只在于参数选择和工程包装。

## 🕳️ 自建专属避坑指南

> R72 §避坑指南覆盖了"框架使用"层面的坑，本节专注"自建实现"层面的坑——R72 没讲。

| # | 坑 | 触发场景 | 解法 |
|---|---|---|---|
| A1 | **抽取 prompt 写得太宽，闲聊也存** | "用户说了你好" 也变成事实 | 加"只提取稳定的、≥ 1 周后还有效的"约束；importance 1 的批量过滤 |
| A2 | **同一事实多次写入，instance 暴增** | 用户每次说"我喜欢咖啡"都新增一条 | 写入前用 embedding 查相似度 ≥ 0.95 的，已有就 access_count++ 而非新增 |
| A3 | **冲突检测漏判同义词** | "用户已婚" vs "用户老婆是 Bob" 模型判不矛盾 | 抽取阶段就归一化（都改写成 `用户配偶: Bob`）|
| A4 | **invalid_at 字段忘了过滤** | 检索时把失效事实也返回了 | 在所有 search 入口强制加 `@invalid_at:[0 0]`，做单测覆盖 |
| A5 | **embedding 模型升级灾难** | 想把 text-embedding-3-small 升 large，全库重算耗时数小时 | 写入时存 `embed_version` 字段，检索时强制版本一致；后台 reindex 双写 |
| A6 | **Redis HNSW 索引 OOM** | 100w 条 1536 维向量 ≈ 6GB RAM | 用 `INITIAL_CAP` 预分配；超过 100w 切 RediSearch + 多分片或换 Qdrant |
| A7 | **冲突 LLM 调用失控成本** | 每条新事实都触发 LLM 判断 | 加缓存（`conflict_cache:{user_id}:{fact_hash}`，TTL 7 天）|
| A8 | **consolidate 跑时锁住索引** | dry_run=False 直接删，并发请求看到不一致 | 先标记 `pending_delete=1`，下次检索过滤；24 小时后真删 |
| A9 | **多用户 user_id 注入** | user_id 来自外部，没校验 | TagField 注入前必须 `re.sub(r'[^a-zA-Z0-9_]', '', user_id)` |
| A10 | **importance 字段被模型乱填** | 啥都填 3 | 抽取 prompt 加"importance 必须遵循:1=普通/2=身份/3=安全或医疗关键"且加示例 |
| A11 | **L1 Working 和 L3 Semantic 重复注入** | 同一信息在系统提示和 messages 里都出现 | 检索 L3 时排除"过去 30 分钟产生"的事实（已在 L1 里）|
| A12 | **没监控记忆系统的健康指标** | 跑 3 个月发现"用户都没记忆"才知道抽取挂了 | 加指标：`facts_extracted_per_message`（理想 0.3-1.5）/ `valid_ratio` / `avg_retrieval_score` |

## 🔑 核心洞见

1. **三层记忆 = 三类失败模式**。先定位症状再补层，不要无脑上全套——L1 缺位 = 忘最近，L2 缺位 = 说不清时序，L3 缺位 = 跨会话忘事实。
2. **事实抽取的 prompt 决定记忆质量上限**。它是整个系统最重要的一行代码，但 95% 的教程一笔带过——本文 §3.4 做了五家 prompt 对照。
3. **记忆冲突有两种范式**：Mem0 让冲突共存靠时间排序，Zep 用 invalid_at 给旧事实下毒。选择取决于业务需要"事实历史"还是"事实最新"，不是技术优劣。
4. **检索打分 = 语义 × 新鲜度 × 重要度的加权**，不是单一向量相似度。三系数（α/β/γ）比公式本身更影响效果。
5. **80% 工程量在写入侧**（抽取/去重/冲突/遗忘），不在读取侧。但大多数教程只教读取——这是为什么"看完还是不会做"。
