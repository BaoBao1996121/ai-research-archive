## 1. 问题本质分析

### 场景描述

```
仓库 A (你正在编辑)
  └── 依赖 仓库 B (工具库/框架)
        └── 依赖 仓库 C (底层库)

示例：
  your-webapp (A)
    └── your-component-lib (B)
          └── your-design-system (C)
```

### 关键挑战

| 挑战 | 说明 |
|------|------|
| **体量问题** | A+B+C 可能有数百万行代码，远超任何 LLM 的上下文窗口（最大 ~200K tokens ≈ ~15万行） |
| **Token 成本** | 即使能塞进去，全量发送的 API 费用极高 |
| **信噪比** | 编辑 A 的某个文件时，B+C 中 99% 的代码是噪声 |
| **依赖深度** | 需要理解 A→B→C 的调用链，但不需要 C 的全部实现 |
| **实时性** | B 和 C 可能频繁更新，索引需要跟上 |

### 核心思路：不是"怎么塞更多"，而是"怎么选更准"

> "Rather than relying on an agent to reason its way to a solution, it is crucial to build good tools to insert the **right context** into the prompt."
> — Moatless Tools 作者

**你需要的不是 B+C 的全部代码，而是：**
- B 中你正在使用的类和函数的 **签名 + 文档**
- C 中被 B 暴露出来的 **类型定义**
- 跨仓库的 **调用关系图谱**

| 方案 | 原理 | 对多仓支持 | 精度 | 成本 | 复杂度 | 代表项目 |

## 3. 方案一：Repository Map（仓库地图）

### 核心思想

> **不发代码，发"目录"。** 用 Tree-sitter 解析源码 AST，提取每个文件中的类名、方法签名、类型定义，生成一个极其精简的"仓库骨架地图"。

### Aider 的实现（最成熟的方案）

**原理：**
1. Tree-sitter 解析所有源文件 → 提取定义（class/function/type）和引用
2. 构建文件依赖图：文件是节点，引用关系是边
3. 用 **PageRank 类似的图排序算法** 选出最重要的符号
4. 将这些符号的签名拼接成 repo map，控制在 ~1K tokens 以内
5. 每次 LLM 调用都带上这个 map 作为上下文

**实际效果（Aider 的 repo map 示例）：**

```
aider/coders/base_coder.py:
⋮...
│class Coder:
│    abs_fnames = None
⋮...
│    @classmethod
│    def create(self, main_model, edit_format, io, **kwargs):
⋮...
│    def abs_root_path(self, path):
⋮...
│    def run(self, with_message=None):
⋮...

aider/commands.py:
⋮...
│class Commands:
│    voice = None
⋮...
│    def get_commands(self):
⋮...
│    def run(self, inp):
⋮...
```

**关键优势：**
- LLM 看到签名就知道 API 怎么用，不需要看实现
- 如果需要更多细节，LLM 自己会说"给我看 `base_coder.py:120-180`"
- 动态调整：根据当前对话状态，扩展或缩小 map 的范围

### 扩展到多仓场景（A 依赖 B 依赖 C）

```python
# 多仓 Repo Map 构建策略

def build_multi_repo_map(repo_a, repo_b, repo_c, current_file):
    """
    策略：越近的仓库 map 越详细，越远的越精简
    """

    # 1. 仓库 A（正在编辑）：完整 map
    map_a = build_repo_map(
        repo_a,
        detail_level="full",        # 类+方法+签名+属性
        token_budget=2000,
        focus_files=[current_file],  # 重点展开当前编辑文件周围
    )

    # 2. 仓库 B（直接依赖）：只 map 被 A 引用的模块
    imports_from_b = extract_imports(repo_a, target=repo_b)  # A 中 import B 的内容
    map_b = build_repo_map(
        repo_b,
        detail_level="interface",   # 只要公开接口、类型定义
        token_budget=1000,
        filter_modules=imports_from_b,  # 只索引被引用的模块
    )

    # 3. 仓库 C（间接依赖）：极简 map，只要类型
    types_from_c = extract_exported_types(repo_c, used_by=repo_b)
    map_c = build_repo_map(
        repo_c,
        detail_level="types_only",  # 只要 type/interface 定义
        token_budget=500,
    )

    return combine_maps(map_a, map_b, map_c)
```

**Token 预算分配示意：**

```
┌────────────────────────────────────────┐
│          LLM Context Window            │
│                                        │
│  ┌──────────────────────────────────┐  │
│  │ System Prompt (~500 tokens)       │  │

│  │ 当前文件完整内容 (变长)             │  │
│  ├──────────────────────────────────┤  │
│  │ 用户指令                          │  │
│  └──────────────────────────────────┘  │
└────────────────────────────────────────┘
```

### 自己实现的核心代码片段

```python
import tree_sitter_languages  # pip install tree-sitter-languages

def extract_symbols(filepath: str, language: str) -> list[dict]:
    """用 tree-sitter 提取文件中的符号定义"""
    parser = tree_sitter_languages.get_parser(language)
    
    with open(filepath, "r") as f:
        source = f.read()
    
    tree = parser.parse(source.encode())
    symbols = []
    
    # 不同语言的查询模式
    queries = {
        "python": """
            (class_definition name: (identifier) @class.name) @class.def
            (function_definition name: (identifier) @func.name) @func.def
        """,
        "typescript": """
            (class_declaration name: (type_identifier) @class.name) @class.def
            (function_declaration name: (identifier) @func.name) @func.def
            (interface_declaration name: (type_identifier) @iface.name) @iface.def
            (type_alias_declaration name: (type_identifier) @type.name) @type.def
        """,
    }
    
    query = tree_sitter_languages.get_language(language).query(queries[language])
    captures = query.captures(tree.root_node)
    
    for node, tag in captures:
        if tag.endswith(".def"):
            # 提取定义的第一行（签名）
            start_line = node.start_point[0]
            lines = source.split("\n")
            # 取签名部分（到冒号或左花括号为止）
            signature_lines = []
            for line in lines[start_line:start_line + 5]:
                signature_lines.append(line)
                if ":" in line or "{" in line:
                    break
            
            symbols.append({
                "type": tag.replace(".def", ""),
                "name": node.children[1].text.decode() if node.children else "",
                "signature": "\n".join(signature_lines),
                "line": start_line + 1,
                "file": filepath,
            })
    
    return symbols


def build_repo_map(repo_path: str, token_budget: int = 1000) -> str:
    """构建仓库地图"""
    import os
    
    all_symbols = []
    for root, dirs, files in os.walk(repo_path):
        # 跳过 node_modules, .git 等
        dirs[:] = [d for d in dirs if d not in {
            "node_modules", ".git", "__pycache__", "dist", "build"
        }]
        for f in files:
            if f.endswith((".py", ".ts", ".tsx", ".js", ".jsx")):
                filepath = os.path.join(root, f)
                lang = "python" if f.endswith(".py") else "typescript"
                try:
                    symbols = extract_symbols(filepath, lang)
                    all_symbols.extend(symbols)
                except Exception:
                    pass
    
    # 按文件分组，生成 map
    from collections import defaultdict
    by_file = defaultdict(list)
    for sym in all_symbols:
        rel_path = os.path.relpath(sym["file"], repo_path)
        by_file[rel_path].append(sym)
    
    # 生成文本 map（控制 token 预算）
    map_lines = []
    for filepath in sorted(by_file.keys()):
        map_lines.append(f"\n{filepath}:")
        for sym in by_file[filepath]:
            map_lines.append(f"  {sym['signature']}")
    
    return "\n".join(map_lines)
```

## 4. 方案二：Code Graph + LSP 导航

### 核心思想

> **不预读代码，给 Agent 导航工具。** 利用 Language Server Protocol（LSP）提供 "去定义"、"查引用"、"查类型" 等能力，Agent 按需跳转。

### 为什么这对多仓特别有效

```
编辑 A 中的 user_service.py
  → Agent 看到 `from lib_b import UserValidator`
  → Agent 工具调用: goto_definition("UserValidator")
  → 返回: lib_b/validators.py:45 - class UserValidator(BaseValidator)
  → Agent 工具调用: goto_definition("BaseValidator")
  → 返回: lib_c/base.py:12 - class BaseValidator(ABC)
  → Agent 现在理解了整条继承链，只读了 3 处代码！
```

**对比直接读取：** 全量读要加载 3 个仓库的全部文件；Code Graph 只需 3 次精准跳转。

### 实际实现：Sourcegraph Cody 的方法

Sourcegraph 的方案最成熟，支持 10 万+ 仓库：

```
用户查询 → 
  ① 查询预处理（token化 + 清洗）→ 
  ② BM25 搜索（跨所有选定仓库）→ 
  ③ Code Graph 分析（符号关系）→ 
  ④ 相关性排序（BM25 + 代码结构权重）→ 
  ⑤ 选取 Top-N snippet → 
  ⑥ 组装到 LLM Prompt
```

**关键发现：Sourcegraph 已放弃 Embeddings！**

> "While embeddings worked for retrieving context, they had some drawbacks... Your code has to be sent to a 3rd party for processing... As codebase size increases, vector database becomes complex... We replaced embeddings with Sourcegraph's native search platform."
> — Sourcegraph 官方博客 (2024.02)

替代方案：改用 **BM25 关键词搜索 + Code Graph 结构分析**，零额外配置，原生支持大规模多仓。

### Sourcebot：轻量级自托管替代品

对于不想用 Sourcegraph 商业版的团队，Sourcebot 是一个开源替代：

```yaml

{
    "connections": {
        "internal-repos": {
            "type": "github",
            "repos": [
                "myorg/repo-a",
                "myorg/repo-b",
                "myorg/repo-c"
            ]
        }
    }

```

特性：
- 🔍 跨仓代码搜索（正则 + 语义）
- 🧭 跨仓代码导航（goto definition / find references）
- 💬 Ask Sourcebot：用自然语言问代码问题
- ⚡ 基于 Zoekt 搜索引擎，毫秒级响应

### 给你的 Agent 加上 Code Navigation 工具

```python
# 给 Agent 定义代码导航工具

@tool
def goto_definition(symbol: str, file_context: str) -> str:
    """跳转到符号的定义位置，返回定义处的代码片段
    
    Args:
        symbol: 要查找定义的符号名（类名、函数名、变量名等）
        file_context: 当前文件路径，用于定位搜索上下文
    """
    # 方案1: 调用 LSP 服务器
    result = lsp_client.send_request("textDocument/definition", {
        "textDocument": {"uri": file_context},
        "position": find_symbol_position(symbol, file_context),
    })
    
    # 方案2: 调用 Sourcegraph API
    result = sourcegraph_api.search(
        query=f"type:symbol ^{symbol}$ repo:myorg/.*",
        count=5,
    )
    
    # 返回定义处的代码片段（前后各 10 行）
    return extract_context(result, context_lines=10)


@tool
def find_references(symbol: str, scope: str = "all_repos") -> str:

        scope: 搜索范围 - "current_repo" 或 "all_repos"
    """
    results = lsp_client.send_request("textDocument/references", {...})
    
    # 返回格式化的引用列表
    return format_references(results)


@tool 
def find_implementations(interface_name: str) -> str:
    """查找接口/抽象类的所有实现（跨仓库）"""
    results = sourcegraph_api.search(

    return format_implementations(results)
```

## 5. 方案三：分层摘要（Hierarchical Summarization）

### 核心思想

> **预先让 LLM 总结每个文件和目录，建立层级理解。** 编辑时不读代码，读摘要。

### 工作流程

```
阶段1: 预计算（离线）
  仓库 B
  ├── src/
  │   ├── validators/
  │   │   ├── user.py      → LLM 总结："用户验证器，包含 UserValidator 类，
  │   │   │                    支持 email/phone/name 验证，依赖 BaseValidator"
  │   │   ├── order.py     → LLM 总结："订单验证器，..."
  │   │   └── __init__.py  → LLM 总结："导出所有验证器"
  │   │   
  │   │   目录摘要 → "validators 目录包含 3 个验证器（User/Order/Payment），
  │   │              全部继承自 BaseValidator，实现 validate() 接口"
  │   │
  │   ├── models/
  │   │   └── ...          → 类似的层级总结
  │   │
  │   仓库摘要 → "repo-b 是一个验证和数据模型库，提供 UserValidator,
  │              OrderValidator 等验证器和 UserModel, OrderModel 等数据模型，
  │              核心依赖 repo-c 的 BaseValidator 和 BaseModel"

阶段2: 使用（在线 - 编辑 A 时）
  用户编辑 A/src/api/users.py
    → 检测到 import: from repo_b.validators import UserValidator
    → 拉取 B/validators/user.py 的摘要（而非源码）
    → 拉取 B/validators/ 的目录摘要
    → 如果需要更深入，再拉取具体方法的摘要
```

### 代表项目: Autodoc

Autodoc（context-labs/autodoc，2.3K stars）实现了这个思路：

1. 深度优先遍历仓库所有文件
2. 对每个文件调用 LLM 生成文档（使用最便宜的能完成任务的模型）
3. 对每个目录，综合子文件的文档生成目录级总结
4. 总结存在 `.autodoc/docs/` 目录中，随代码版本管理

### 多仓扩展方案

```python
import hashlib
import json
from pathlib import Path

class HierarchicalSummarizer:
    """分层摘要系统 — 专为多仓代码库设计"""
    
    def __init__(self, llm_client, cache_dir=".code_summaries"):
        self.llm = llm_client
        self.cache_dir = Path(cache_dir)
    
    def summarize_file(self, filepath: str, detail_level: str = "standard") -> str:
        """总结单个文件"""
        content = Path(filepath).read_text()
        content_hash = hashlib.md5(content.encode()).hexdigest()
        
        # 缓存检查（内容未变则跳过）
        cache_key = f"{filepath}_{detail_level}_{content_hash}"
        cached = self._get_cache(cache_key)
        if cached:
            return cached
        
        prompts = {
            "types_only": "只列出该文件导出的类型定义、接口、类名和方法签名，不要实现细节。",
            "standard": "总结该文件的用途、导出的公开API（类/函数/类型/常量），以及关键依赖。",
            "detailed": "详细描述该文件中每个类和方法的功能、参数、返回值和使用示例。",
        }
        
        summary = self.llm.generate(
            f"请总结以下代码文件。\n{prompts[detail_level]}\n\n```\n{content}\n```"
        )
        
        self._set_cache(cache_key, summary)
        return summary
    
    def summarize_directory(self, dir_path: str, file_summaries: list[str]) -> str:
        """基于子文件摘要，生成目录级总结"""
        combined = "\n---\n".join(file_summaries)
        return self.llm.generate(
            f"以下是目录 {dir_path} 中各文件的摘要，"
            f"请生成一个目录级别的总结（关注整体架构和文件间关系）：\n\n{combined}"
        )
    
    def build_multi_repo_context(
        self,
        current_file: str,
        repo_a_path: str,
        repo_b_path: str,
        repo_c_path: str,
    ) -> str:
        """为多仓编辑场景构建上下文"""
        
        # 1. 分析当前文件的依赖
        imports = self._analyze_imports(current_file)
        
        # 2. 对 B 仓库：生成被 A 引用模块的 standard 摘要
        b_context = []
        for module in imports.get("repo_b", []):
            summary = self.summarize_file(
                f"{repo_b_path}/{module}",
                detail_level="standard"
            )
            b_context.append(f"## {module}\n{summary}")
        
        # 3. 对 C 仓库：只生成 types_only 摘要
        c_context = []
        for module in imports.get("repo_c", []):
            summary = self.summarize_file(
                f"{repo_c_path}/{module}",
                detail_level="types_only"
            )
            c_context.append(f"## {module}\n{summary}")
        
        return self._format_context(b_context, c_context)
```

**优缺点：**

| 优点 | 缺点 |
|------|------|
| 极致压缩（万行代码 → 几百 token 摘要） | 预计算成本（首次索引大仓可能要 $几十~$几百） |
| 自然语言描述，LLM 理解友好 | 摘要可能丢失细节（需要时得回源码） |
| 天然支持多仓、多语言 | 代码更新需要重新生成（增量更新是关键） |

## 6. 方案四：依赖感知的选择性索引

### 核心思想

> **解析 A 的 import/依赖声明，只索引 B 中被实际使用的符号，忽略 B 的其余 95%。**

### 这是最实用的"自建"方案

```python
import ast
import os
from pathlib import Path

class DependencyAwareIndexer:
    """依赖感知索引器 — 只索引你真正用到的代码"""
    
    def analyze_imports(self, file_path: str) -> dict:
        """分析 Python 文件的 import 语句"""
        with open(file_path) as f:
            tree = ast.parse(f.read())
        
        imports = {}
        for node in ast.walk(tree):
            if isinstance(node, ast.ImportFrom):
                module = node.module or ""
                names = [alias.name for alias in node.names]
                imports[module] = names
            elif isinstance(node, ast.Import):
                for alias in node.names:
                    imports[alias.name] = ["*"]
        
        return imports
    
    def resolve_cross_repo_imports(
        self, 
        repo_a_file: str,
        repo_b_path: str,
        repo_c_path: str
    ) -> dict:
        """解析跨仓导入，定位具体符号"""
        imports = self.analyze_imports(repo_a_file)
        
        resolved = {"repo_b": {}, "repo_c": {}}
        
        for module, names in imports.items():
            # 判断属于哪个仓库
            module_path = module.replace(".", "/")
            
            if os.path.exists(f"{repo_b_path}/{module_path}.py"):
                for name in names:
                    resolved["repo_b"][f"{module}.{name}"] = \
                        self._extract_symbol_code(
                            f"{repo_b_path}/{module_path}.py", name
                        )
            
            elif os.path.exists(f"{repo_c_path}/{module_path}.py"):
                for name in names:
                    resolved["repo_c"][f"{module}.{name}"] = \
                        self._extract_symbol_code(
                            f"{repo_c_path}/{module_path}.py", name
                        )
        
        return resolved
    
    def _extract_symbol_code(self, file_path: str, symbol_name: str) -> str:
        """只提取文件中特定符号的代码"""
        with open(file_path) as f:
            source = f.read()
            tree = ast.parse(source)
        
        for node in ast.walk(tree):
            if isinstance(node, (ast.ClassDef, ast.FunctionDef, ast.AsyncFunctionDef)):
                if node.name == symbol_name:
                    lines = source.split("\n")
                    return "\n".join(lines[node.lineno - 1:node.end_lineno])
        
        return f"# Symbol '{symbol_name}' not found in {file_path}"
    
    def build_focused_context(self, current_file: str, repos: dict) -> str:
        """构建专注的上下文 — 只包含被使用的符号"""
        resolved = self.resolve_cross_repo_imports(
            current_file,
            repos["b"],
            repos["c"]
        )
        
        context_parts = []
        
        if resolved["repo_b"]:
            context_parts.append("=== 直接依赖 (repo-b) 中被使用的符号 ===")
            for symbol_path, code in resolved["repo_b"].items():
                context_parts.append(f"\n# {symbol_path}\n{code}")
        
        if resolved["repo_c"]:
            context_parts.append("\n=== 间接依赖 (repo-c) 中被使用的类型 ===")
            for symbol_path, code in resolved["repo_c"].items():
                context_parts.append(f"\n# {symbol_path}\n{code}")
        
        return "\n".join(context_parts)


# 使用示例
indexer = DependencyAwareIndexer()
context = indexer.build_focused_context(
    current_file="repo_a/src/api/users.py",
    repos={
        "b": "/path/to/repo-b",
        "c": "/path/to/repo-c",
    }
)
# context 只包含 users.py 实际 import 的类和函数的代码
# 而不是整个 repo-b 和 repo-c
```

### 这个方案的核心优势

```
传统方法：
  A (100 文件) + B (500 文件) + C (300 文件) = 900 文件 → 塞不进 LLM

依赖感知索引：
  A/users.py 的 imports:
    - from repo_b.validators import UserValidator     → 提取 1 个类
    - from repo_b.models import UserModel             → 提取 1 个类
    - from repo_c.base import BaseValidator           → 提取 1 个类 (签名)
  
  实际发给 LLM 的内容：
    - users.py 全文 (100 行)
    - UserValidator 类定义 (50 行)
    - UserModel 类定义 (30 行)
    - BaseValidator 接口定义 (20 行)
    
  总共 ~200 行，占 900 文件总量的 < 0.1%
```

## 7. 方案五：AST 感知的代码搜索

### 核心思想

> **不搜文本，搜代码结构。** 在 Abstract Syntax Tree 中搜索类、方法、调用关系，比文本搜索精确得多。

### AutoCodeRover 的方法（SWE-bench 46.2% 解决率）

AutoCodeRover 提供了一组 **程序结构感知的搜索 API**，让 LLM 像用 IDE 一样搜代码：

```python
# AutoCodeRover 给 LLM 的搜索 API（LLM 可以通过 function calling 调用这些）

# 搜索类定义
search_class("UserValidator")
# → 返回: repo_b/validators/user.py 中 UserValidator 类的完整定义

# 搜索方法定义
search_method("validate_email")
# → 返回: 所有仓库中名为 validate_email 的方法

# 搜索方法在特定类中的定义
search_method_in_class("validate", "UserValidator")
# → 返回: UserValidator.validate() 的实现

# 搜索代码模式
search_code("class.*Validator.*BaseValidator")
# → 返回: 所有继承 BaseValidator 的验证器

# 在特定文件中搜索
search_code_in_file("import", "repo_a/src/api/users.py")
# → 返回: users.py 中所有 import 语句
```

**关键区别：结构搜索 vs 文本搜索**

```
文本搜索 "UserValidator":
  ✗ 找到注释里的 "// TODO: fix UserValidator"
  ✗ 找到字符串里的 "print('UserValidator created')"
  ✗ 找到变量名 "userValidator = new UserValidator()"  ← 这个有用
  ✗ 找到测试代码里的 "def test_UserValidator"

AST 搜索 "class UserValidator":
  ✓ 精准找到 class UserValidator(BaseValidator) 的定义位置
  ✓ 包含完整的类签名、方法列表、继承关系
  ✓ 不会被注释、字符串、测试代码干扰
```

### 用 Tree-sitter 自建 AST 搜索

```python
class ASTCodeSearch:
    """AST 感知的代码搜索引擎"""
    
    def __init__(self, repo_paths: list[str]):
        self.index = {}  # 预建索引
        for path in repo_paths:
            self._index_repo(path)
    
    def _index_repo(self, repo_path: str):
        """索引一个仓库的所有代码结构"""
        for filepath in self._walk_source_files(repo_path):
            symbols = extract_symbols(filepath, self._detect_language(filepath))
            for sym in symbols:
                key = f"{sym['type']}:{sym['name']}"
                if key not in self.index:
                    self.index[key] = []
                self.index[key].append({
                    **sym,
                    "repo": repo_path,
                })
    
    def search_class(self, class_name: str) -> list[dict]:
        """搜索类定义"""
        return self.index.get(f"class:{class_name}", [])
    
    def search_function(self, func_name: str) -> list[dict]:
        """搜索函数/方法定义"""
        return self.index.get(f"func:{func_name}", [])
    
    def search_callers(self, symbol_name: str) -> list[dict]:
        """查找谁调用了这个符号（需要引用索引）"""
        results = []
        for key, entries in self.index.items():
            for entry in entries:
                if symbol_name in entry.get("references", []):
                    results.append(entry)
        return results
    
    def search_inheritance(self, base_class: str) -> list[dict]:
        """查找所有继承某个基类的子类"""
        results = []
        for key, entries in self.index.items():
            if key.startswith("class:"):
                for entry in entries:
                    if base_class in entry.get("bases", []):
                        results.append(entry)
        return results
```

## 10. 为什么传统 RAG 对代码不好用？

你的直觉是对的。传统 RAG（切chunk → embedding → 向量搜索）对代码有严重问题：

### 问题分析

| 问题 | 说明 | 示例 |
|------|------|------|
| **切块破坏结构** | 按 token 数切块会把一个函数切成两半 | `class UserValidator:` 在 chunk A，`def validate(self):` 在 chunk B |
| **语义鸿沟** | 代码的"含义"不在文本表面，在结构和调用关系里 | `x = get_user(id)` 的含义取决于 `get_user` 的定义在哪个仓库 |
| **变量名不语义** | `a`, `tmp`, `result` 的embedding向量几乎相同 | 搜索 "验证邮箱" 找不到 `def validate_email_format(s: str)` |
| **跨文件依赖** | RAG 找到的 chunk 是孤立的，丢失了 import 上下文 | 找到 `validator.validate(data)` 但不知道 `validator` 是什么类型 |
| **代码变量多态** | 同名函数在不同文件有不同实现 | `save()` 在 User、Order、Payment 类中实现完全不同 |

### 如果你一定要用 RAG，怎么改善？

```python
# ❌ 传统 RAG: 按 token 切块
chunks = split_by_tokens(code, chunk_size=512)

# ✅ 改良 RAG: 按 AST 结构切块
def smart_chunk_code(filepath: str) -> list[dict]:
    """按代码结构切块，保持语义完整性"""
    symbols = extract_symbols(filepath, language)
    
    chunks = []
    for sym in symbols:
        chunk = {
            "content": sym["full_code"],           # 完整的类/函数定义
            "metadata": {
                "file": filepath,
                "type": sym["type"],                # class/function/interface
                "name": sym["name"],
                "signature": sym["signature"],
                "imports": sym["imports"],           # 这个符号的依赖
                "exported": sym["is_exported"],
                "docstring": sym["docstring"],
            }
        }
        chunks.append(chunk)
    
    return chunks

# ✅ 改良 RAG: 搜索时加入结构过滤
def search_code_rag(query: str, filters: dict = None):
    results = vector_store.search(query, top_k=20)
    
    if filters:
        # 按代码结构过滤
        if filters.get("type"):
            results = [r for r in results if r.metadata["type"] == filters["type"]]
        if filters.get("exported_only"):
            results = [r for r in results if r.metadata["exported"]]
    
    return results
```

### RAG vs 其他方案的选择

```
选 RAG 如果:
  ✓ 你需要用自然语言搜索代码（"处理用户登录的代码在哪？"）
  ✓ 代码有大量注释和文档
  ✓ 搜索范围很大，需要语义理解
  
选 Repo Map + AST 搜索 如果:
  ✓ 你知道要找什么符号（类名、函数名）
  ✓ 需要理解代码结构和调用关系
  ✓ 多仓跨依赖的精确导航

最佳实践: 两者组合
  先用 Repo Map 给 LLM 全局视野
  再用 AST 搜索精确定位
  RAG 作为"最后手段"在需要语义搜索时使用
```

### 按团队规模选方案

#### 个人/小团队（1-5人，2-5个仓库）


#### 中型团队（5-50人，10-50个仓库）


```python
"""
多仓代码 Agent — 组合方案实现
"""
import json
from typing import Literal

class MultiRepoCodeAgent:
    """能跨仓库理解和修改代码的 Agent"""
    
    def __init__(self, llm_client, repos: dict[str, str]):
        self.llm = llm_client
        self.repos = repos  # {"a": "/path/to/a", "b": "/path/to/b", ...}
        
        # Layer 0: 预计算全局上下文
        self.repo_maps = {}
        self.dependency_graph = {}
        self._build_global_context()
    
    def _build_global_context(self):
        """预计算 Layer 0 — 全局视野"""
        for name, path in self.repos.items():
            # 生成 repo map（token 预算按依赖距离递减）
            budget = 2000 if name == "a" else 1000 if name == "b" else 500
            self.repo_maps[name] = build_repo_map(path, token_budget=budget)
        
        # 分析仓库间依赖关系
        self.dependency_graph = self._analyze_repo_dependencies()
    
    def _build_layer0_prompt(self) -> str:
        """构建 Layer 0 全局上下文"""
        parts = ["# 仓库全局视野\n"]
        
        # 依赖关系
        parts.append("## 仓库依赖关系")
        parts.append(json.dumps(self.dependency_graph, indent=2, ensure_ascii=False))
        
        # 各仓库的 map
        for name, repo_map in self.repo_maps.items():
            parts.append(f"\n## 仓库 {name} 的代码结构")
            parts.append(repo_map)
        
        return "\n".join(parts)
    
    def _build_layer1_prompt(self, current_file: str) -> str:
        """构建 Layer 1 — 当前焦点上下文"""
        parts = ["# 当前编辑上下文\n"]
        
        # 当前文件
        with open(current_file) as f:
            content = f.read()
        parts.append(f"## 当前文件: {current_file}\n```\n{content}\n```")
        
        # 依赖感知：提取被 import 的跨仓符号
        indexer = DependencyAwareIndexer()
        cross_repo_deps = indexer.build_focused_context(current_file, self.repos)
        if cross_repo_deps:
            parts.append(f"\n## 跨仓依赖的源码\n{cross_repo_deps}")
        
        return "\n".join(parts)
    
    # Layer 2 工具
    tools = [
        {
            "name": "search_code",
            "description": "在仓库中搜索代码",
            "function": "_tool_search_code",
        },
        {
            "name": "read_file_range",
            "description": "读取文件指定行范围",
            "function": "_tool_read_file_range",
        },
        {
            "name": "goto_definition",
            "description": "跳转到符号定义（支持跨仓库）",
            "function": "_tool_goto_definition",
        },
        {
            "name": "find_references",
            "description": "查找符号的所有引用",
            "function": "_tool_find_references",
        },
    ]
    
    async def run(self, task: str, current_file: str) -> str:
        """运行 Agent"""
        
        system_prompt = f"""你是一个代码编辑 Agent，可以跨多个仓库理解和修改代码。

{self._build_layer0_prompt()}

{self._build_layer1_prompt(current_file)}

如果你需要更多信息，使用以下工具：
- search_code: 搜索代码
- read_file_range: 读取文件指定行
- goto_definition: 跳转到符号定义
- find_references: 查找引用

先分析已有信息，只在确实需要时才调用工具。"""

        messages = [
            {"role": "system", "content": system_prompt},
            {"role": "user", "content": task},
        ]
        
        # Agent 循环
        while True:
            response = await self.llm.chat(messages, tools=self.tools)
            
            if response.tool_calls:
                for tc in response.tool_calls:
                    result = await self._execute_tool(tc)
                    messages.append({"role": "tool", "content": result})
            else:
                return response.content
```

### 核心洞察总结

> **"与其把代码塞给 LLM，不如把工具给 Agent"**

1. **不要试图把 A+B+C 的代码全部塞进上下文** — 这是错误的方向
2. **Repo Map 是性价比最高的方案** — ~1k tokens 就能给 LLM 全局视野
3. **依赖感知索引是最精确的方案** — 只提取被实际使用的符号
4. **工具化是最灵活的方案** — Agent 按需获取，不浪费 token
5. **Embeddings/RAG 对代码效果不佳** — Sourcegraph 已弃用，改用 BM25 + Code Graph
6. **Tree-sitter 是底层基石** — 几乎所有方案都用它来理解代码结构
7. **最佳实践是组合** — Layer 0 (Repo Map) + Layer 1 (依赖索引) + Layer 2 (工具)
