# Code Wiki — 用知识库方法组织代码仓库业务知识的方法讨论

## 1. 问题定义

### 1.1 核心问题

本文讨论 **LLM Wiki 三层架构**（Raw Sources → Wiki → Schema）。问题是：**这套方法能否移植到代码仓库上，让 Copilot 更好地理解业务逻辑？**

具体来说：

- Skills 擅长告诉 AI "怎么在这个模块里工作"，但不擅长告诉 AI "这个系统是什么"
- 能否用 Wiki 编译的方式，将散落在代码中的业务知识提炼为 Copilot 可以直接消费的编译知识？

## 2. 理论框架

### 2.1 LLM Wiki 三层架构回顾

```
Layer 1: Raw Sources（原始资料）
  ├── LLM 只读，是 truth source
  └── 代码仓库场景 = 源代码 + 注释 + 配置文件 + 提交历史

Layer 2: Wiki（编译知识）
  ├── LLM 全权维护的 Markdown 文档
  ├── 从 Raw Sources 编译而来
  └── 代码仓库场景 = 业务知识文档（术语表、工作流、设计决策...）

Layer 3: Schema（控制指令）
  ├── 定义 AI 行为的元规则
  └── 代码仓库场景 = copilot-instructions.md / .instructions.md
```

### 2.2 五个核心原则与代码场景的映射

| # | 原则 | 知识库场景 | 代码仓库场景 |
|---|------|---------|-----------|
| P1 | 让知识适配 LLM | 将散文编译为结构化条目 | 将代码中隐含的业务规则编译为 Markdown |
| P2 | 从检索到编译 | 预处理而非运行时搜索 | 预先提炼"为什么"而非让 AI 逆向工程代码 |
| P3 | LLM 作为维护者 | LLM 自主更新 Wiki | LLM 在代码变更时同步更新 Wiki |
| P4 | Schema 是灵魂 | CLAUDE.md 定义行为 | copilot-instructions.md 引用 Wiki |
| P5 | 知识覆盖目标 | 尽量避免知识丢失 | 记录重要架构决策并检查遗漏 |

### 2.3 Wiki 法 vs Skill 法的本质差异

| 维度 | Wiki 法 | Skill 法 |
|------|--------|---------|
| **解决的问题** | 知识问题（What / Why） | 流程问题（How） |
| **知识形态** | 声明式 — "系统是什么样的" | 程序式 — "在这个模块里怎么做" |
| **激活方式** | 始终可用（注入 context） | 按需激活（用户/路由器触发） |
| **粒度** | 跨模块、全局视角 | 单模块、局部专家 |
| **典型内容** | 术语表、工作流、决策记录 | 陷阱清单、代码模式、API 用法 |
| **维护者** | AI 编译 + 人工审校 | 人工编写 + AI 辅助 |
| **类比** | 百科全书 | 操作手册 |

**关键洞察**: 它们不是替代关系，而是互补关系。就像你既需要《内科学》教材（Wiki）也需要《住院医师手册》（Skill）。

## 3. 方案讨论

### 3.1 Code Wiki 的潜在优势

1. **补全 Skills 的结构性盲区**: Skills 天生是模块级专家，无法提供全局业务视图。Wiki 的跨模块叙事填补了这个空白。

2. **Playbook 提供端到端修改路线**: 这是 Skills 最难做到的——因为 Skills 按模块组织，而需求往往跨模块。

### 3.2 Code Wiki 的局限

1. **不适合记录代码级细节**: "这个函数的第 3 个参数在某些边界条件下会 throw"这类知识，Skill 的粒度更合适。

2. **维护成本高于知识库 Wiki**: 代码变更频繁，Wiki 需要人工审校业务正确性（不能像知识库那样完全交给 LLM）。

3. **需要领域专家参与**: Wiki 中的"Why"需要资深开发者/产品经理提供，不能纯靠 AI 从代码反推。

4. **规模天花板**: Wiki 页面不宜超过 20 页（~40K tokens），否则注入成本过高。适合提炼**核心**业务知识，不适合穷举所有知识。

### 3.3 建议方案：三层上下文架构

```
┌──────────────────────────────────────────────┐
│              Layer 3: Schema                  │
│     copilot-instructions.md (~2K tokens)      │
│     "Copilot 应该怎么行为" + Wiki/Skill 索引   │
├──────────────────────────────────────────────┤
│              Layer 2: Wiki                    │
│     wiki/ 目录 (按需编译与读取)            │
│     "系统是什么 / 为什么这样设计"              │
│     全局业务知识 — 始终可用                    │
├──────────────────────────────────────────────┤
│              Layer 1: Skills                  │
│     skills/ 目录 (按模块组织)       │
│     "在这个模块里怎么工作"                    │
│     模块级专家 — 按需激活                     │
├──────────────────────────────────────────────┤
│              Layer 0: Raw Sources             │
│     源代码 + 配置 + 提交历史                   │
│     源文件 — Copilot 按需读取                 │
└──────────────────────────────────────────────┘

注入策略：
  Schema → 每次对话自动注入（~2K，可承受）
  Wiki   → 由 Schema 按需引用
  Skills → 用户手动激活 或 路由器自动选择（每次 ~3-5K）
  Raw    → Copilot 按需搜索/读取
```

## 4. 实施建议

### 4.1 Code Wiki 编写原则

| 原则 | 说明 | 反例 |
|------|------|------|
| **写 Why 不写 What** | 记录设计理由，不复述代码 | ❌ "这个函数接收 3 个参数..." |
| **用户视角叙事** | 从用户操作说起，再映射到代码 | ❌ 从类继承关系开始 |
| **术语双向映射** | 中文→英文→代码变量名 | ❌ 只写英文术语 |
| **修改路线图要端到端** | 从需求描述到所有涉及文件 | ❌ 只列一个模块的文件 |
| **保持精简** | 每页 150 行以内，总量 <20 页 | ❌ 把所有代码注释搬过来 |
| **标注知识来源** | 注明来自哪个配置/代码/PBI | ❌ 没有溯源的断言 |

### 4.2 知识维护机制

可在 Schema 层定义知识维护触发条件及更新目标，在代码变更后检查对应文档是否需要更新。

### 4.3 外部文档输入管线

可按文档类型设计标准化灌入接口：

| 文档类型 | 价值定位 | 灌入目标 |
|---------|---------|---------|
| 培训手册/用户指南 | 用户操作动线的权威来源 | → 用户场景图谱 + 用户工作流 |
| PBI 验收标准 | 业务边界条件 | → 用户场景图谱(约束表) + 设计决策记录 |
| 功能说明/风险手册 | 安全约束、合规要求 | → 设计决策记录 + 用户场景图谱 |
| 测试用例 | 场景穷举、异常流程 | → 用户场景图谱 + 修改场景手册(验证节) |
