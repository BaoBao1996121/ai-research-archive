## 1. 问题本质

### 场景

```
庞大知识库（数百页到数万页文档/wiki/手册/SOP/历史记录）
        ↓
  Agent 需要按需获取相关业务知识
        ↓
  作为上下文注入 → LLM 生成高质量回答
```

### 关键挑战

| 挑战 | 说明 |
|------|------|
| **体量 vs 窗口** | 知识库可能有数百万 tokens，远超单次上下文窗口（当前最大 ~200K tokens） |
| **召回率** | 传统 RAG 的 embedding 检索会丢失关键信息，尤其是精确匹配和跨文档推理 |
| **精确度** | 业务知识往往需要精确的数值、流程、规范，不能"差不多" |
| **关联性** | 知识之间有复杂的关联关系（A 依赖 B 的定义，B 引用 C 的公式） |
| **实时性** | 知识库可能频繁更新 |
| **成本** | 大量 token 的 API 调用费用 |

### 核心思路

**不是"怎么召回更准"，而是"怎么让知识变得更容易被 LLM 消化"**

## 3. 方案一：Wiki 法（Karpathy 路线）

### 核心理念

这是 Karpathy 在 2025 年 YC 演讲中反复强调的思路：**把知识整理成 LLM 友好的格式，直接喂给 LLM，而不是让 LLM 通过检索去"找"信息**。

> "I copy-pasted the whole thing (Manim documentation) to an LLM. And I just grabbed what I wanted, and it just worked out of the box."  
> — Andrej Karpathy, YC AI Startup School 2025

### 具体做法

#### 第一步：知识预处理为 Markdown

将所有业务知识整理为**纯 Markdown 格式**：

```
knowledge-base/
├── 00-overview.md          # 知识库整体概览
├── 01-core-concepts.md     # 核心概念定义
├── 02-business-rules.md    # 业务规则
├── 03-workflows.md         # 工作流程
├── 04-reference-data.md    # 参考数据/表格
├── 05-faq.md               # 常见问题
└── index.md                # 目录索引
```

#### 第二步：创建 llms.txt 风格的索引

Karpathy 提到的 `llms.txt` 规范（参考 llmstxt.org）：在知识库根目录放一个 LLM 友好的索引文件：

```markdown
# 知识库名称

> 一句话描述这个知识库的用途

## 核心文档

- 核心概念（原稿引用文件未随本次归档发布）: 所有基础概念和定义
- 业务规则（原稿引用文件未随本次归档发布）: 业务逻辑和约束条件
- 工作流程（原稿引用文件未随本次归档发布）: 标准操作流程

## 常用查询

- 如何计算 X → 参见 business-rules.md#section-3
- Y 的审批流程 → 参见 workflows.md#approval
```

#### 第三步：按需拼装上下文

根据用户问题，选择相关的 Markdown 文件，拼装成上下文：

```python
# 伪代码
def build_context(question, knowledge_base):
    # 1. 始终包含概览和核心概念
    context = [
        read("00-overview.md"),
        read("01-core-concepts.md"),
    ]
    
    # 2. 根据问题关键词选择相关文档
    relevant_docs = keyword_match(question, knowledge_base.index)
    context.extend([read(doc) for doc in relevant_docs])
    
    # 3. 确保不超过上下文窗口
    return truncate_to_fit(context, max_tokens=150000)
```

### 关键工具

| 工具 | 功能 | 链接 |
|------|------|------|
| **Repomix** | 将整个项目/知识库打包成单个 AI 友好文件（XML/MD/JSON） | github.com/yamadashy/repomix |
| **Gitingest** | Python 生态的仓库打包工具 | github.com/cyclotruc/gitingest |
| **DeepWiki** | 自动为 GitHub 仓库生成 wiki 文档 | deepwiki.com |
| **Devon Wiki** | Devin（AI 编程 Agent）为代码仓库自动生成的分析文档 | cognition.ai |

### Repomix 实操示例

```bash
# 把知识库目录打包成单个 Markdown 文件
npx repomix --style markdown --include "**/*.md" -o knowledge-packed.md

# 压缩模式，保留结构但减少 token
npx repomix --compress --style xml -o knowledge-packed.xml

# 查看 token 分布
npx repomix --token-count-tree
```

### 优缺点

| 优点 | 缺点 |
|------|------|
| 召回率 100%（给了就一定在上下文里） | 知识库不能太大（受上下文窗口限制） |
| 实现极简，无需复杂基础设施 | 大量 token 消耗 |
| LLM 能看到完整的上下文关联 | 超过窗口需要分段 |
| 无需维护向量数据库 | 知识更新需重新打包 |

### 适用规模

- **理想范围**：< 500 页文档（~200K tokens）
- **勉强可用**：500-2000 页（需要分段 + 智能选择）
- **不适合**：> 2000 页（需要配合其他方案）

## 4. 方案二：Context Stuffing（全量塞入）

### 核心理念

最暴力也最有效的方法：**直接把所有知识塞进上下文窗口**。

> "If your knowledge base is smaller than 200,000 tokens (about 500 pages of material), you can just include the entire knowledge base in the prompt."  
> — Anthropic, Contextual Retrieval Blog

### 为什么有效

2024-2025 年，长上下文能力出现质变：

| 模型 | 上下文窗口 | 等效页数 |
|------|-----------|----------|
| Claude 3.5/4 | 200K tokens | ~500 页 |
| Gemini 2.0 | 2M tokens | ~5000 页 |
| GPT-4.1 | 1M tokens | ~2500 页 |

**关键发现**：长上下文 LLM 在有充足资源时**一致性地优于 RAG**，尤其在需要跨文档推理的任务上。

> 论文 "Retrieval Augmented Generation or Long-Context LLMs? A Comprehensive Study and Hybrid Approach" (arXiv:2407.16833, EMNLP 2024) 的结论：  
> "When resourced sufficiently, LC consistently outperforms RAG in terms of average performance."

### 实操建议

```python
# 使用 Gemini 的 2M 上下文窗口，直接注入全部知识
system_prompt = f"""
你是业务知识专家。以下是完整的业务知识库：

<knowledge_base>
{entire_knowledge_base}  # 直接放入全部内容
</knowledge_base>

请基于以上知识回答用户问题。如果知识库中没有相关信息，请明确说明。
"""
```

### 优缺点

| 优点 | 缺点 |
|------|------|
| 零召回损失，信息完整保留 | 受限于上下文窗口大小 |
| 无需任何检索基础设施 | token 成本高（但在下降） |
| 跨文档推理能力最强 | "针在干草堆中"问题（信息过多可能稀释注意力） |
| 实现零成本 | 延迟较高（处理大量 token 需要时间） |

## 5. 方案三：Prompt Caching + 全文注入

### 核心理念

Context Stuffing 的成本优化版：**利用 API 提供商的 Prompt Caching 功能，将知识库缓存下来，后续查询复用缓存**。

### 工作原理

```
第一次请求：
  [知识库全文 200K tokens] + [用户问题]  → 全价计费，同时建立缓存

第二次及之后的请求：
  [缓存引用] + [新的用户问题]  → 知识库部分 90% 折扣
```

### 各家支持情况

| 平台 | 功能名称 | 节省比例 | 缓存有效期 |
|------|----------|----------|-----------|
| **Anthropic** | Prompt Caching | 输入 token 90% 折扣 | 5 分钟（自动续期） |
| **OpenAI** | Automatic Caching | 50% 折扣 | 5-10 分钟 |
| **Google** | Context Caching | 按缓存存储时间收费 | 可自定义 |

### Anthropic Prompt Caching 示例

```python
import anthropic

client = anthropic.Anthropic()

# 知识库作为 system prompt 的一部分，标记为缓存
response = client.messages.create(
    model="claude-sonnet-4-20250514",
    max_tokens=4096,
    system=[
        {
            "type": "text",
            "text": entire_knowledge_base,   # 200K tokens 的知识库
            "cache_control": {"type": "ephemeral"}  # 标记为可缓存
        }
    ],
    messages=[
        {"role": "user", "content": "用户的具体问题"}
    ]
)
# 后续请求自动命中缓存，知识库部分仅收 10% 费用
```

### 成本估算

假设知识库 200K tokens，每天 100 次查询：

| 方案 | 日成本（Claude） | 月成本 |
|------|--------------|--------|
| 每次全量发送 | ~$6.00 | ~$180 |
| 使用 Prompt Caching | ~$0.90 | ~$27 |
| 传统 RAG | ~$0.50 | ~$15 |

> Prompt Caching 只比 RAG 贵一点，但**召回率是 100%**。

### 适用场景

- 知识库在上下文窗口内（< 200K tokens）
- 查询频率高（缓存命中率高）
- 对召回率有极高要求
- 不想维护向量数据库

## 6. 方案四：知识蒸馏/预摘要法

### 核心理念

当知识库超大（>500页）时，**先用 LLM 将知识库"蒸馏"为精炼版本**，然后用精炼版本作为上下文。

### 工作流

```
原始知识库（5000 页）
        ↓ LLM 预处理
精炼知识库（500 页）  ← 保留核心信息，去除冗余
        ↓
直接注入上下文（使用 Wiki 法或 Context Stuffing）
```

### 蒸馏策略

#### 策略 1：分层摘要

```python
def distill_knowledge(documents):
    summaries = {}
    
    for doc in documents:
        # 第一层：每个文档生成详细摘要
        summaries[doc.name] = {
            "brief": llm_summarize(doc, level="brief"),       # 1-2 句
            "detailed": llm_summarize(doc, level="detailed"),  # 1-2 段
            "key_facts": llm_extract_facts(doc),               # 关键事实列表
            "definitions": llm_extract_definitions(doc),       # 术语定义
        }
    
    # 第二层：跨文档整合
    global_summary = llm_synthesize(summaries)
    
    return {
        "overview": global_summary,
        "per_document": summaries,
    }
```

#### 策略 2：Wiki 生成

让 LLM 读取原始知识库，生成结构化的 Wiki：

```python
prompt = """
请阅读以下原始文档，生成一份结构化的知识 Wiki。

要求：
1. 提取所有核心概念并给出精确定义
2. 整理所有业务规则为 IF-THEN 格式
3. 绘制流程图（用 Mermaid 语法）
4. 整理数值参数为表格
5. 标注信息来源（原始文档页码）
6. 去除重复内容，合并相关知识

<source_documents>
{documents}
</source_documents>
"""
```

#### 策略 3：QA 对生成

将知识转化为问答对：

```python
# 让 LLM 从知识库中生成所有可能的问答对
qa_pairs = llm_generate_qa(knowledge_base)

# 输出格式
# Q: 产品 A 的保质期是多少？
# A: 产品 A 的保质期为 24 个月（常温存储），开封后需在 30 天内使用。
#    来源：产品规格书 v3.2，第 15 页
```

### 优缺点

| 优点 | 缺点 |
|------|------|
| 可以处理任意大小的知识库 | 蒸馏过程可能丢失细节 |
| 精炼后的知识更高效 | 预处理成本高 |
| 跨文档整合能力强 | 知识更新需要重新蒸馏 |
| 结果可人工审查和修正 | 需要设计蒸馏策略 |

## 7. 方案五：RAPTOR（树状分层检索）

### 核心理念

Stanford 提出的方案：**递归地对文本进行聚类和摘要，构建一棵从细节到抽象的树**，查询时从不同层级检索。

> 论文：RAPTOR: Recursive Abstractive Processing for Tree-Organized Retrieval (arXiv:2401.18059)

### 工作原理

```
                    [全局摘要]               ← 层级 3：鸟瞰
                   /          \
         [主题A摘要]          [主题B摘要]     ← 层级 2：主题级
        /    |    \          /    |    \
    [chunk1][chunk2][chunk3][chunk4][chunk5][chunk6]  ← 层级 0：原始文本
```

**预处理阶段**：
1. 将知识库分割为 chunks
2. 用 embedding 将相似 chunks 聚类
3. 对每个聚类生成摘要
4. 对摘要再聚类、再摘要...递归进行
5. 构建完整的树结构

**查询阶段**：
1. 查询同时在所有层级进行
2. 从叶子节点获取精确细节
3. 从高层节点获取全局理解
4. 融合不同粒度的信息

### 为什么比传统 RAG 好

| 维度 | 传统 RAG | RAPTOR |
|------|---------|--------|
| 检索粒度 | 仅检索固定大小的 chunks | 多层级检索（从细节到全局） |
| 跨文档推理 | 需要检索到所有相关 chunks | 高层摘要已整合跨文档信息 |
| 上下文理解 | chunk 脱离上下文 | 树结构保留了上下文层次 |
| 全局问题 | 几乎无法回答 | 高层摘要天然适合 |

### 性能数据

在 QuALITY benchmark 上，RAPTOR + GPT-4 比传统 RAG 方案**绝对精度提升 20%**。

### 适用场景

- 知识库有清晰的层次结构
- 经常有"总结性"问题
- 需要同时回答细节和全局问题

## 8. 方案六：GraphRAG（知识图谱增强）

### 核心理念

Microsoft Research 提出：**从知识库中提取知识图谱，构建实体-关系网络和社区层次，查询时利用图结构增强检索**。

> 项目地址：github.com/microsoft/graphrag

### 工作原理

```
原始知识库 → LLM 抽取实体和关系 → 构建知识图谱
                                      ↓
                               Leiden 社区发现算法
                                      ↓
                              层次化社区结构
                                      ↓
                           每个社区生成摘要
                                      ↓
                         查询时利用图结构检索
```

### 查询模式

| 模式 | 适用场景 | 原理 |
|------|----------|------|
| **Global Search** | "这个知识库讲了什么？" | 利用社区摘要回答全局问题 |
| **Local Search** | "X 和 Y 有什么关系？" | 从特定实体出发，扩展关联 |
| **DRIFT Search** | "X 的详细情况？" | Local Search + 社区上下文 |
| **Basic Search** | 简单关键词查询 | 回退到标准向量检索 |

### 核心优势

1. **连接分散的信息**：传统 RAG 无法回答需要"连点成线"的问题，GraphRAG 通过图结构天然支持
2. **全局理解**：传统 RAG 几乎无法回答"总结类"问题，GraphRAG 的社区摘要专门解决此问题
3. **可解释性**：知识图谱提供了清晰的推理路径

### 限制

- **预处理成本极高**：需要对每个 chunk 调用 LLM 提取实体/关系
- **索引时间长**：大型知识库可能需要数小时
- **需要调优**：提取 prompt 需要针对具体领域优化

## 9. 方案七：Contextual Retrieval（上下文增强检索）

### 核心理念

这是 Anthropic 提出的 **RAG 改良版**：在 embedding 之前，先用 LLM 为每个 chunk 添加上下文说明。

> "Contextual Retrieval reduces the top-20-chunk retrieval failure rate by 49%."  
> — Anthropic Blog, 2024

### 传统 RAG 的问题

```
原始文本："The company's revenue grew by 3% over the previous quarter."

问题：这是哪家公司？哪个季度？chunk 丢失了上下文！
```

### Contextual Retrieval 的解法

```
原始 chunk："The company's revenue grew by 3% over the previous quarter."

+ 上下文增强 →

"This chunk is from an SEC filing on ACME corp's performance in Q2 2023; 
the previous quarter's revenue was $314 million. 
The company's revenue grew by 3% over the previous quarter."
```

### 技术栈

```
1. 分割文档为 chunks
2. 对每个 chunk，用 LLM 生成上下文说明（利用 Prompt Caching 降低成本）
3. 将"上下文 + chunk"一起做 embedding → Contextual Embedding
4. 将"上下文 + chunk"一起做 BM25 索引 → Contextual BM25
5. 查询时：
   a. 用 embedding 检索 top chunks（语义匹配）
   b. 用 BM25 检索 top chunks（精确匹配）
   c. Rank Fusion 合并去重
   d. Reranking 模型重排序
   e. Top-K 输入 LLM
```

### 性能提升（相比标准 RAG）

| 技术组合 | 召回失败率降低 |
|---------|--------------|
| Contextual Embedding 单独 | -35% |
| Contextual Embedding + Contextual BM25 | **-49%** |
| + Reranking | **-67%** |

### 如果"非要用 RAG"

这是**目前已知最强的 RAG 改良方案**。如果知识库太大必须用检索，Contextual Retrieval + BM25 + Reranking 是最佳选择。

## 10. 方案八：Agent 自主检索（工具化检索）

### 核心理念

不预先检索，而是**给 Agent 一套搜索工具，让它自己决定搜什么、看什么、深入到什么程度**。

### 工具设计

```python
# Agent 可用的知识库工具
tools = [
    {
        "name": "search_knowledge",
        "description": "在知识库中搜索关键词，返回相关段落",
        "parameters": {"query": "string", "top_k": "int"}
    },
    {
        "name": "read_document",
        "description": "读取指定文档的完整内容",
        "parameters": {"doc_id": "string", "section": "string?"}
    },
    {
        "name": "list_topics",
        "description": "列出知识库中的所有主题分类",
        "parameters": {}
    },
    {
        "name": "get_related",
        "description": "获取与指定概念相关的所有文档",
        "parameters": {"concept": "string"}
    }
]
```

### 工作流

```
用户问题 → Agent 分析需要什么信息
                ↓
        Agent 调用 search_knowledge("核心关键词")
                ↓
        Agent 阅读搜索结果，判断是否足够
                ↓ 不够
        Agent 调用 read_document("相关文档ID")
                ↓
        Agent 调用 get_related("关联概念")
                ↓
        Agent 综合所有信息，生成回答
```

### 优势

- **自适应深度**：简单问题查一次，复杂问题多轮探索
- **可解释**：Agent 的检索过程透明可见
- **灵活**：不需要预定义检索策略
- **渐进式**：类似人类查资料的方式

### 实现参考

Claude Code 和 Cursor 等编程 Agent 就是这个模式：它们不是一次性把所有代码塞进上下文，而是通过文件搜索、grep、读取文件等工具**按需获取**。

## 11. 方案九：Fine-tuning / 知识内化

### 核心理念

将知识直接"烧入"模型权重，让模型"记住"知识而不是临时注入。

### 适用条件

- 知识非常稳定，不频繁更新
- 需要极低延迟（不能等检索）
- token 成本敏感（不想每次都注入知识）
- 有足够的训练数据和计算资源

### 方式

| 方式 | 成本 | 效果 | 适用 |
|------|------|------|------|
| **全量微调** | 极高 | 最好 | 核心业务知识 |
| **LoRA/QLoRA** | 中 | 好 | 垂直领域知识 |
| **Continued Pre-training** | 高 | 好 | 大量领域文档 |

### 局限

- 知识更新需要重新训练
- 可能造成"幻觉"（模型过度自信）
- 难以精确控制模型"记住了什么"
- 无法引用来源

## 12. 方案十：Self-Route 混合路由

### 核心理念

来自 EMNLP 2024 论文 "Retrieval Augmented Generation or Long-Context LLMs? A Comprehensive Study and Hybrid Approach" (arXiv:2407.16833) 的核心发现：**不必在 RAG 和长上下文之间二选一，可以让模型自己判断用哪种**。

> "We propose Self-Route, a simple yet effective method that routes queries to RAG or LC based on the model's self-reflection on its own generation."

### 工作原理

```
用户查询
    ↓
先用 RAG 检索 + 生成初步回答
    ↓
模型自我评估: "我对这个回答有信心吗？"
    ├── 有信心 → 直接输出 RAG 结果 (省 token)
    └── 没信心 → 切换到 Long Context 模式重新回答 (保质量)
```

### 为什么有效

| 场景 | 最优策略 | 原因 |
|------|----------|------|
| 简单事实查询 | RAG | 精确匹配几个 chunk 就够了，无需全量注入 |
| 复杂推理 / 跨文档 | Long Context | 需要看到完整上下文才能正确推理 |
| 总结 / 全局问题 | Long Context | RAG 天然无法处理全局问题 |
| 带精确编号的查询 | RAG + BM25 | BM25 精确匹配优于语义搜索 |

### 实现方案

```python
class SelfRouteRetriever:
    def __init__(self, knowledge_base, model):
        self.kb = knowledge_base
        self.model = model
        self.rag_retriever = RAGRetriever(knowledge_base)
    
    def query(self, question: str) -> str:
        # Step 1: 先用 RAG 尝试回答
        rag_chunks = self.rag_retriever.retrieve(question, top_k=20)
        rag_answer = self.model.generate(
            context=rag_chunks,
            question=question,
            system="回答问题，并在末尾用 [CONFIDENT] 或 [UNCERTAIN] 标记你的确信度"
        )
        
        # Step 2: 检查模型自我评估
        if "[CONFIDENT]" in rag_answer:
            return rag_answer.replace("[CONFIDENT]", "").strip()
        
        # Step 3: 不够自信 → 切换到全量上下文
        full_context = self.kb.get_full_text()  # 可配合 Prompt Caching
        lc_answer = self.model.generate(
            context=full_context,
            question=question
        )
        return lc_answer
```

### 优缺点

| 优点 | 缺点 |
|------|------|
| 兼顾成本和质量 | 不自信时会产生双倍延迟 |
| 简单查询用 RAG 省 token | 需要模型有良好的自我评估能力 |
| 复杂查询自动升级到 LC | 路由决策本身有一定错误率 |
| 不需要人为指定何时用哪种 | 需要同时维护 RAG 和 LC 两套管线 |

### 论文关键数据

- 在 ∞Bench 和 RULER 等长上下文基准上，Self-Route 方法在**只使用约 60% LC 调用次数**的情况下达到了纯 LC 方案 **95%+ 的性能**
- 意味着可以节省约 40% 的 token 成本，而几乎不损失质量

## 13. 进阶：语义分块与格式优化

### 13.1 语义分块（Semantic Chunking）

传统 RAG 按固定大小（如 512 tokens）切分文档，**完全忽略内容边界**。语义分块是所有检索策略的底层改进。

#### 分块策略对比

| 策略 | 原理 | 优势 | 劣势 |
|------|------|------|------|
| **固定大小** | 每 N tokens 切一刀 | 简单一致 | 可能切断句子/段落 |
| **按段落/章节** | 按 Markdown 标题、双换行分割 | 保留自然结构 | 段落大小差异大 |
| **语义分块** | 计算相邻句子的 embedding 相似度，在"语义断崖"处切分 | 每个 chunk 语义完整 | 计算成本高 |
| **递归分块** | 先按大标题分，再递归按小标题、段落、句子细分 | 保留层次 | 需预定义分割符层级 |
| **Agentic Chunking** | 让 LLM 判断每个段落应属于哪个 chunk | 质量最高 | 成本最高，速度最慢 |

#### 语义分块实现

```python
from sentence_transformers import SentenceTransformer
import numpy as np

def semantic_chunk(text: str, threshold: float = 0.3) -> list[str]:
    """在语义断崖处切分文本"""
    model = SentenceTransformer("all-MiniLM-L6-v2")
    sentences = text.split(". ")  # 简化：按句分割
    embeddings = model.encode(sentences)
    
    chunks, current_chunk = [], [sentences[0]]
    for i in range(1, len(sentences)):
        # 计算相邻句子的余弦相似度
        sim = np.dot(embeddings[i-1], embeddings[i]) / (
            np.linalg.norm(embeddings[i-1]) * np.linalg.norm(embeddings[i])
        )
        if sim < threshold:  # 语义断崖 → 切分
            chunks.append(". ".join(current_chunk))
            current_chunk = [sentences[i]]
        else:
            current_chunk.append(sentences[i])
    chunks.append(". ".join(current_chunk))
    return chunks
```

#### 推荐：结合结构的语义分块

对 Markdown 知识库最有效的方式：**先按标题切分，再在大段落内部用语义分块细分**。

```python
def hybrid_chunk(markdown_text: str, max_tokens: int = 1000) -> list[str]:
    """先按标题结构分，再语义细分"""
    # 第一层：按 Markdown 标题切
    sections = re.split(r'\n(?=#{1,3} )', markdown_text)
    
    chunks = []
    for section in sections:
        tokens = len(section) // 4
        if tokens <= max_tokens:
            chunks.append(section)  # 小节直接作为一个 chunk
        else:
            # 大节：语义细分
            sub_chunks = semantic_chunk(section, threshold=0.3)
            chunks.extend(sub_chunks)
    return chunks
```

### 13.2 格式优化：XML vs Markdown vs JSON

不同格式对 LLM 理解效率有**显著影响**。

#### 格式对比实测

| 格式 | LLM 理解准确率 | Token 效率 | 适用场景 |
|------|--------------|-----------|----------|
| **Markdown** | ⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | 通用知识库，文档 |
| **XML** | ⭐⭐⭐⭐⭐ | ⭐⭐⭐ | 需要精确边界时（如代码+文档混合） |
| **JSON** | ⭐⭐⭐ | ⭐⭐ | 结构化数据表 |
| **YAML** | ⭐⭐⭐⭐ | ⭐⭐⭐⭐ | 配置、规则型知识 |
| **纯文本** | ⭐⭐ | ⭐⭐⭐⭐⭐ | 不推荐（缺少结构信号） |

#### 格式选择指南

```
知识类型           最佳格式           原因
──────────────────────────────────────────
文档/手册/SOP     Markdown            标题层级天然表达结构
业务规则          YAML                IF-THEN 规则用层级表达最清晰
API 参考          XML                 精确的标签边界防止 LLM 混淆
数据表/报表       Markdown 表格       LLM 对 Markdown 表格理解最好
代码+文档混合     XML                 <code> 和 <doc> 标签明确分离
问答对            Markdown             Q:/A: 格式简洁有效
```

```xml
    </section>

  </document>

```

当知识库刚好超出窗口一些时，可以通过压缩技术勉强塞入：

### 14.1 知识库六维度画像

### 14.2 第七维度：使用意图（决定性因素）

六个客观维度描述知识库"是什么"，但**"用来做什么"同样甚至更加重要**。同一个知识库，用于不同场景时，最佳策略可能完全不同：

| 使用场景 | 最佳格式 | 策略修正 | 核心需求 |

| **文字创作规则参考** | YAML + Markdown | 规则显式化为 IF-THEN + 示例完整保留 | 规则无遗漏、反面案例 |
| **业务 SOP/流程** | Markdown + Mermaid | 流程图提取 + 步骤序列化 | 步骤顺序、条件分支完整 |
| **客服/问答系统** | Q&A Markdown | QA 对生成 + BM25 精确搜索 | 快速定位、答案精确 |
| **研究/分析素材** | Markdown + 表格 | GraphRAG 权重上调 | 跨文档推理、来源追溯 |
| **培训/教育材料** | 分层 Markdown | RAPTOR 权重上调 | 渐进式理解、概念层次 |

**示例对比**：一个 300K tokens 的技术文档库

```

场景 C：给 AI 客服用
  → 策略 D + QA 生成修正：蒸馏为 QA 对
  → 格式：Q&A Markdown + BM25 索引
  → 输出：核心 FAQ 常驻 + 长尾 QA 按需检索
```

### 14.4 效果评估指标

部署后，用以下指标衡量方案效果：

| 指标 | 定义 | 目标值 |
|------|------|--------|
| **召回率** | 正确答案的信息是否在检索结果中 | > 95% |
| **首次命中率** | Top-1 结果就包含答案的比例 | > 70% |
| **回答准确率** | LLM 基于检索结果回答正确的比例 | > 90% |
| **延迟** | 从查询到回答的总时间 | < 10s |
| **Token 成本** | 每次查询消耗的 token 数 | 按预算定 |
| **"我不知道"准确率** | 知识库中确实没有时，模型拒绝回答的比例 | > 85% |

#### 简易评估流程

```python
def evaluate_strategy(strategy, test_set):
    """
    test_set: [{"question": "...", "expected_answer": "...", "source_doc": "..."}, ...]
    """
    results = {"recall": 0, "accuracy": 0, "latency": [], "tokens": []}
    
    for case in test_set:
        start = time.time()
        retrieved = strategy.retrieve(case["question"])
        answer = strategy.generate(case["question"], retrieved)
        elapsed = time.time() - start
        
        # 召回率：预期来源文档是否在检索结果中
        results["recall"] += case["source_doc"] in retrieved
        # 准确率：回答是否包含关键信息
        results["accuracy"] += evaluate_answer(answer, case["expected_answer"])
        results["latency"].append(elapsed)
        results["tokens"].append(count_tokens(retrieved))
    
    n = len(test_set)
    return {
        "recall": results["recall"] / n,
        "accuracy": results["accuracy"] / n,
        "avg_latency": sum(results["latency"]) / n,
        "avg_tokens": sum(results["tokens"]) / n,
    }
```

## 15. 进阶：知识生命周期管理

### 问题

知识库不是静态的。无论你用哪种组织策略，都需要一套**更新机制**：

### 15.1 按策略的更新方式

| 策略 | 更新成本 | 更新方式 |
|------|---------|---------|
| Context Stuffing | 零 | 直接替换源文件 |
| Wiki 法 | 低 | 重新打包（Repomix 秒级） |
| Prompt Caching | 低 | 替换内容，缓存自动失效 |
| 知识蒸馏 | **高** | 需要 LLM 重新蒸馏变更部分 |
| RAPTOR | **高** | 树结构需要重建（或局部更新） |
| GraphRAG | **极高** | 知识图谱需要增量更新或全量重建 |
| Contextual Retrieval | 中 | 变更文档需重新生成上下文+重新 embed |
| Fine-tuning | **极高** | 需要重新训练 |

### 15.2 增量更新策略

最实用的增量更新方案：

```python
class KnowledgeBaseManager:
    """知识库生命周期管理"""
    
    def __init__(self, kb_path: str, strategy: str):
        self.kb_path = kb_path
        self.strategy = strategy
        self.file_hashes = {}  # 文件hash缓存
    
    def detect_changes(self) -> dict:
        """检测知识库变更"""
        changes = {"added": [], "modified": [], "deleted": []}
        current_files = scan_directory(self.kb_path)
        
        for f in current_files:
            h = hash_file(f)
            if f not in self.file_hashes:
                changes["added"].append(f)
            elif self.file_hashes[f] != h:
                changes["modified"].append(f)
            self.file_hashes[f] = h
        
        for f in set(self.file_hashes) - set(current_files):
            changes["deleted"].append(f)
            del self.file_hashes[f]
        
        return changes
    
    def incremental_update(self, changes: dict):
        """增量更新组织后的知识库"""
        if self.strategy in ("context_stuffing", "wiki", "prompt_caching"):
            # 轻量策略：直接重新打包
            self.repack()
        elif self.strategy == "contextual_retrieval":
            # 中量策略：只重新处理变更文档
            for f in changes["added"] + changes["modified"]:
                self.reindex_document(f)
            for f in changes["deleted"]:
                self.remove_from_index(f)
        elif self.strategy in ("raptor", "graphrag"):
            # 重量策略：评估变更范围决定局部还是全量更新
            change_ratio = len(changes["modified"]) / len(self.file_hashes)
            if change_ratio > 0.2:  # >20% 文件变更 → 全量重建
                self.full_rebuild()
            else:
                self.partial_rebuild(changes)
```

## 16. 传统 RAG 为什么召回率不够？

### 根本问题

| 问题 | 具体表现 |
|------|----------|
| **chunk 脱离上下文** | "revenue grew by 3%" —— 什么公司？哪个季度？ |
| **编码损失** | Embedding 是有损压缩，语义相似 ≠ 相关 |
| **精确匹配缺失** | 搜 "Error code TS-999"，embedding 找到的是泛泛的"错误码"文档 |
| **跨文档推理** | 答案分散在 3 个文档中，单独看任何一个 chunk 都不完整 |
| **全局问题无解** | "总结一下所有产品的保质期" → RAG 只能找到几个 chunks |
| **Top-K 天花板** | k 太小会漏信息，k 太大会引入噪声 |
| **Embedding 模型通用性** | 通用 embedding 模型对专业领域术语理解不足 |

### 量化数据

Anthropic 的实验显示，标准 RAG 的 top-20 召回失败率为 **5.7%**，意味着约 1/18 的查询会漏掉关键信息。对于高精度业务场景，这是不可接受的。

## 17. 实战推荐：组合方案

### 按知识库规模选择

```
知识库 < 50 页（~20K tokens）
  → 方案 2：Context Stuffing，直接全量塞入，最简单最有效

知识库 50-500 页（~200K tokens）
  → 方案 3：Prompt Caching + 全量注入
  → 配合方案 1 的 Markdown 格式化

知识库 500-2000 页
  → 方案 4：知识蒸馏，将 2000 页浓缩为 500 页
  → 然后用方案 3 注入
  → 或方案 1：Wiki 法 + 按需选择

知识库 > 2000 页
  → 方案 6：GraphRAG（需要跨文档推理时）
  → 方案 5：RAPTOR（需要多层次理解时）
  → 方案 8：Agent 自主检索（灵活度优先时）
  → 方案 7：Contextual Retrieval（如果必须用 RAG 范式）
  → 方案 10：Self-Route（兼顾成本和质量，自动分流）

💡 不确定选哪个？→ 参见第 14 节"知识库分析与评估框架"的决策树
```

### 终极组合方案

对于大型业务知识库的最佳实践：

```
第一层：知识预处理
  - 用 LLM 将原始知识蒸馏为结构化 Wiki（方案 4）
  - 构建知识图谱提取关键实体和关系（方案 6 的预处理部分）

第二层：核心知识缓存
  - 将最重要的核心知识（蒸馏后的 Wiki）通过 Prompt Caching 常驻上下文（方案 3）
  - 这确保了 Agent 始终拥有基础业务理解

第三层：按需深入检索
  - Agent 通过工具按需查询详细信息（方案 8）
  - 使用 BM25 + Contextual Embedding 进行精确检索（方案 7）

效果：
  核心知识 = 100% 召回（在上下文中）
  详细信息 = 通过工具按需获取
  成本 = Prompt Caching 降低重复消耗
  灵活性 = Agent 自主决定检索深度
```

## 附录：Karpathy 原始观点汇总

来自 2025 YC AI Startup School 演讲：

1. **文档 → Markdown**："Stripe、Vercel 等公司已经开始将文档转为 Markdown，直接面向 LLM 可读"
2. **llms.txt**："在域名下放一个 llms.txt，就像 robots.txt 一样，用 Markdown 告诉 LLM 这个网站是做什么的"
3. **Copy-paste 整个文档**："我把 Manim 的文档全塞给 LLM，然后就直接用了，完美运行"
4. **Devon Wiki**："Devon 不只是给你原始文件，它会对 GitHub 仓库做分析，生成一整套 wiki 页面，这对 LLM 来说更有价值"
5. **GitHub Ingest**："只要改一下 URL，从 GitHub 变成 GitHub Ingest，它就把所有文件拼接成一个大文本，准备好直接粘贴到 LLM"

核心哲学：**让知识适配 LLM，而不是让 LLM 去"找"知识。** 这和传统 RAG 的思路完全相反。

---

> 总结：如果你的知识库不超过 500 页，**Wiki 法 + Prompt Caching** 是性价比最高的方案，召回率 100%，实现简单。  
> 如果知识库很大，**知识蒸馏 + Agent 自主检索 + Contextual Retrieval** 的组合是最强方案。  
> 如果兼顾成本和质量，**Self-Route 混合路由** 可在保持 95%+ 质量的同时节省 40% token 成本。  
> 无论选哪种方案，先用第 14 节的知识库画像框架评估你的知识库特征，再决策。  
> 配套 Skill（`skills/knowledge-base-organizer/SKILL.md`）可自动化完成分析和策略选择。
