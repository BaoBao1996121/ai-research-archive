# R168 · Agent 与过程 RSI 落地方案

> 读完这篇你应该能做到三件事：
> 1. 用一句话讲清 RSI 在 2025–2026 年到底指什么、不指什么；

## 0. 一页纸版本（先背这页）

**RSI 是什么**：系统对自己做**持久修改**，修改后的系统又参与**下一轮**改进的生成或选择，并且改进能**跨任务复用**。三条缺一条都不算 RSI，只是“调优”。

**2026 年的主流做法**：冻结模型权重，进化模型外面的东西。

```
          ┌──────────────── 档案库（所有版本 + 分数 + 父代）────────────────┐
          ↓                                                               │
   选父代 ──→ LLM 提出修改 ──→ 执行 ──→ 程序化评估 ──→ 统计门槛 ──→ 入库 ─┘
                                                     │
                                                     └─ 不过 → KEEP_BASE（不改也是合法结果）
```

**被进化的对象有两类**：

| 类型 | 改什么 | 代表 | 本文实验 |
|---|---|---|---|
| 过程 RSI | 一段算法/启发式代码 | FunSearch、AlphaEvolve、OpenEvolve | 实验 B：装箱启发式 |
| Agent RSI | 系统提示、经验手册、工具、agent 自身代码 | ACE、Darwin Gödel Machine、Harness² | 实验 A：经验手册自优化 |

**一句话判断能不能做**：先问“谁来打分、多少钱一次、会不会被骗”。打分便宜且可信 → 能做；只能靠 LLM 打分 → 慎做；没法打分 → 别做。

**本机实测的两个结论**（§4、§5 详述）：

- 实验 B（过程 RSI）：20 代、80 次 LLM 调用、约 15 万 token，进化出的启发式在训练集上比 Best Fit 少用约 0.23% 的箱，**但在两组没见过的测试集上只剩约 0.06% 和 0.45%，波动明显**。训练集最优 ≠ 测试集最优，选择偏差肉眼可见。
- 实验 A（Agent RSI）跑了两次，正好一反一正：
  - **小样本（30 题 × 2 次）**：12 个候选**全部没过统计门槛**，系统一直保持原版本。最后 test 集上“原版 0.683 → 最终 0.75”，看着涨了 6.7 个点，但最终版本**就是原版**——这 6.7 个点纯属噪声。没有门槛，它就会被当成“进化成功”写进周报。
  - **加大样本（50 题 × 3 次）**：9 个候选里 1 个过了门槛，内容是“字符串操作先拆成字符列表再处理”。在从未参与选择的 test 集上 0.693 → 0.827，置信下界 +7.3 个点，确认是真改进。代价约 100 万 token。

## 1. 概念：面试时别说错的五件事

### 1.1 RSI 不等于“模型自己改权重”

经典 RSI（I. J. Good 1965 的“智能爆炸”、Schmidhuber 的 Gödel Machine）设想的是系统改写自身、能力指数增长。现实中 2025–2026 年落地的几乎都是**改外部 scaffold**：prompt、记忆、工具、workflow、agent 代码。模型的下一个 token 能力没变，变的是“怎么用这个模型”。

面试说法：**“现在能工程化的 RSI 基本是 harness-level 的，权重层面的自改进（self-training、RL）成本和风险都高一个量级，而且通常需要可验证奖励。”**

### 1.2 “递归”体现在哪

一次 prompt 调优不是 RSI。要满足：

1. **持久**：修改被保存成版本，而不是只在这次对话里生效；
2. **递归**：下一轮的候选是从**改过的版本**出发生成的；
3. **复用**：改进在没参与选择的任务上依然有效。

R167 引用的审计论文显示，被审的 90 篇自称 RSI 的论文里只有 22% 审计了两轮以上的完整循环。面试时能指出这一点，说明你读过证据而不只是读过摘要。

### 1.3 Gödel Machine → Darwin Gödel Machine 的关键转变

- **Gödel Machine**（Schmidhuber 2003）：只有能**形式化证明**修改有益时才改。理论优雅，实践中几乎不可能证明。
- **Darwin Gödel Machine**（Zhang, Hu, Lu, Lange, Clune，arXiv 2505.22954，2025-05）：把“证明”换成“**跑 benchmark 实测**”，把“单线改进”换成“**开放式档案库**”。在 SWE-bench 上从 20.0% 提到 50.0%，Polyglot 从 14.2% 到 30.7%（已核对 arXiv 摘要）。

一句话：**用经验验证代替形式证明，用种群探索代替贪心爬山。**

### 1.4 为什么要档案库而不是只留最优

贪心爬山（每次只在当前最优上改）容易卡在局部最优。DGM 保留所有有效变体，按“分数高 + 子代少”采样父代，让一些暂时不是最优的版本有机会成为“垫脚石”。DGM 论文的消融实验显示，去掉开放式探索后提升明显变小。

本文实验 B 的族谱也印证了这点：最终最优程序 `g13_1` 的父代 `g6_0` **在第 7 代之后就不再是当时的最优**（`g7_1` 更好），但正是从它分出了最终胜者。如果只保留最优，这条路径会被剪掉。

### 1.5 “自进化”最大的敌人是评估器

两类经典翻车：

- **Objective hacking**：DGM 论文记录过 agent 伪造工具调用日志、删除幻觉检测标记来“提分”。
- **噪声当信号**：LLM 输出有随机性，样本少时，一个候选“看着涨了 5 个点”经常只是运气。本文实验 A 就是活例子。

对策是**评估器独立于被测系统 + 统计门槛 + held-out**。§3 展开。

## 2. 判断你的问题能不能做 RSI

| 问题类型 | 有无可信自动打分 | 推荐路线 | 例子 |
|---|---|---|---|
| A. 可程序判定的过程优化 | 有，毫秒到秒级 | 进化式代码搜索（实验 B） | kernel 提速、调度/排序启发式、SQL 改写、数学构造 |
| B. 可程序判定的 Agent 任务 | 有（终态比对、单测） | Harness 自优化闭环（实验 A） | τ-bench、修 bug、表单/工单处理 |
| C. 只能主观判定的 Agent 任务 | 只能 LLM/人评 | 经验库 + 人工审核，不自动采纳 | 写作、调研报告、会议纪要 |
| D. 需要改权重 | 有大量可验证奖励 | RL / 蒸馏 | 专用小模型 |

**C 类强行上自动 RSI，最常见的结局是把评估器偏好（更长、更自信、格式更花）固化成“进化”。**

## 3. 任何 RSI 闭环都要有的六个零件

不管是进化代码还是进化 agent，零件都一样。实验 A、B 的代码就是按这六个零件写的，可以对照着读。

| 零件 | 作用 | 实验 B 里是 | 实验 A 里是 | 缺了会怎样 |
|---|---|---|---|---|
| 1. 被进化对象 | 明确“能改什么、不能改什么” | `priority()` 函数源码 | 系统提示 + playbook 条目 | 改动面失控，无法归因 |
| 2. 变异算子 | 产生候选 | LLM 读 3 个已有程序及分数，写新程序 | LLM 读失败轨迹，提 add/update/delete 一条经验 | — |
| 3. 评估器 | 给候选打分 | 子进程执行装箱，算用箱数/下界 | 程序比对答案，不用 LLM 判分 | 被骗、被噪声误导 |
| 4. 选择 / 门槛 | 决定谁留下 | 锦标赛选父代（3 选 1） | 配对 bootstrap，90% 置信下界 > 0 才采纳 | 噪声被固化 |
| 5. 档案库 | 保存全部历史 | `db.json`：所有有效程序 + 父代 | `archive.json`：所有候选含落选 | 只能贪心爬山，回不了头 |
| 6. 隔离验收 | 证明不是过拟合 | 训练实例 seed=11，测试 seed=22/33 | 优化集 / held-out / test 三份互不重叠 | 训练集上自嗨 |

**再加两条安全零件**（生产系统必须有）：

- **沙箱**：实验 B 的候选代码先过 AST 检查（禁 import、禁 `__` 属性、禁 `eval/open` 等），再在独立子进程里用受限 builtins 执行，30 秒超时。
- **人工闸口**：权限、生产配置、不可逆操作永远不让系统自己改。

## 4. 实验 B：过程 RSI（迷你 AlphaEvolve）

### 4.1 问题设定

**在线装箱**：300 个物品依次到达，体积在 (0,1]，箱容量 1。每来一个物品，对所有能装下它的箱子调用 `priority(item, remaining)` 打分，放进分最高的箱；都装不下就开新箱。目标是用的箱子越少越好。

这正是 DeepMind FunSearch（Nature 2023）展示过的经典问题。选它是因为：评估器纯程序、几秒出分、**不可能被“说服”**。

分数 = 平均（用箱数 / 理论下界 ⌈Σ体积⌉），越接近 1 越好。

两个种子程序：

```python
def priority(item, remaining):   # First Fit：所有箱同分，取第一个
    return 0.0

def priority(item, remaining):   # Best Fit：装完后剩余越小越好
    return -(remaining - item)
```

### 4.2 闭环怎么转

```python
for g in range(generations):                 # 每代并行生成 4 个
    parent = tournament(db, k=3)             # 3 选 1，挑分最好的当父代
    shown  = [parent] + random.sample(db, 2) # 再给 2 个“灵感程序”
    prompt = 按分数从差到好排列这些程序 + 任务描述
    src    = LLM(prompt)                     # qwen3.7-plus，temperature=1.0
    score  = sandbox_eval(src, seed=TRAIN)   # AST 检查 → 子进程执行 → 超时 30s
    if score is not None:
        db.append({src, score, parent, gen}) # 不管好坏都入库
最后：拿训练集最优程序，在 seed=22、33 两组从未见过的实例上复验
```

关键设计（都来自 FunSearch / AlphaEvolve）：

- **把分数写进 prompt**，并且按“差 → 好”排序。LLM 看得到什么方向是改进。
- **所有有效程序都入库**，不只留最优。
- **温度开到 1.0**，要多样性，正确性交给评估器把关。

### 4.3 实测结果（2026-11-05，本机）

配置：20 代 × 4 个 = 80 次生成，qwen3.7-plus，约 12.1 万输入 token + 3.3 万输出 token。80 个程序全部通过沙箱（前两次运行的教训见 §4.5）。

**进化曲线（训练集，越小越好）**：

| 代 | 当代最优 | 来源 |
|---|---|---|
| 0 | 1.02490 | Best Fit（种子） |
| 1–4 | 1.02490 | 无改进 |
| 5 | 1.02433 | g5_0 |
| 6 | 1.02427 | g6_0 |
| 7 | 1.02263 | g7_1 |
| 13 | 1.02261 | g13_1 |
| 14–20 | 1.02261 | 平台期 |

**族谱**：`best_fit → g3_1 → g6_0 → g13_1`。注意 `g6_0` 在第 7 代就被 `g7_1` 超过了，但最终胜者是从 `g6_0` 而不是 `g7_1` 分出来的——这就是档案库的价值。

**跨数据集复验（越小越好）**：

| 程序 | 训练 seed=11 | 测试 seed=22 | 测试 seed=33 |
|---|---|---|---|
| First Fit | 1.02885 | 1.02881 | 1.02926 |
| Best Fit | 1.02490 | 1.02597 | 1.02644 |
| g13_1（训练集最优） | **1.02261** | 1.02541 | **1.02192** |
| g7_1（训练并列第二） | 1.02263 | 1.02263 | 1.02361 |
| g11_3（训练并列第二） | 1.02263 | **1.02207** | 1.02362 |

**怎么读这张表**：

1. 进化确实找到了比 Best Fit 更好的启发式。在 3 组数据上，训练集前几名都稳定优于 Best Fit。
2. 但幅度很小：每组 20 个实例的理论下界约 1770 箱，0.2% 的差距只相当于**省了 4 箱左右**。
3. **训练集第一不等于测试集第一**。g13_1 在 seed=22 上只比 Best Fit 好 0.05%，反而不如训练集上的“并列第二”。这就是选择偏差：在训练集上挑最优，挑到的有一部分是运气。
4. 平台期很长（第 14–20 代无改进）。真实系统（AlphaEvolve、ShinkaEvolve）会用岛模型、新颖性过滤、多模型 bandit 来打破平台期，本实验没做。

### 4.4 进化出了什么

```python
def priority(item, remaining):
    new_rem = remaining - item
    if new_rem < 1e-9:              # 正好装满：最优先
        return 1e9
    score = -new_rem                # 底子还是 Best Fit
    if new_rem < 0.03:              # 几乎装满：重奖，尽快“关箱”
        score += 200.0 * (0.03 - new_rem)
    elif new_rem < 0.15:            # 留下难用的碎片：重罚
        score -= 5.0 / (new_rem + 0.001)
    elif new_rem > 0.6:             # 留下大块灵活空间：小奖
        score += 0.2 * new_rem
    elif 0.3 < new_rem < 0.5:       # 中等剩余：轻罚
        score -= 0.05
    return score
```

人能读懂它的思路：**在 Best Fit 基础上，惩罚“装不了东西又没装满”的碎片，奖励装满**。这是 FunSearch 论文强调的优点：产物是可解释的代码，而不是黑盒权重。上线前可以 code review、写单测、看边界。

### 4.5 跑实验时踩的坑（真实发生，比结果更有教学价值）

| 现象 | 原因 | 修法 | 一般教训 |
|---|---|---|---|
| 前 10 代约一半候选被拒 | 安全过滤用正则匹配 `open` 等词，误伤了注释里的“open a new bin” | 改成 AST 级检查，只看代码结构 | **评估器的误杀会悄悄饿死搜索**，要监控拒绝率和拒绝原因 |
| 大量 `unterminated triple-quoted string` | `max_tokens=800` 不够，模型写了长注释被截断 | 提到 2000，并在 prompt 里限制“≤25 行、≤3 行注释” | 变异算子的输出预算要和任务匹配 |
| 模型写 `import math` 被拒 | 模型习惯性导入 | 剥掉 `import math`（沙箱已提供），其他 import 仍拒 | 区分“格式问题”和“真违规” |
| Windows 下进程崩溃（pickle 截断、段错误） | `multiprocessing` spawn 与线程池并发冲突 | 改成 `subprocess` 跑独立评估脚本，stdin/stdout 传 JSON | 评估器要和主进程彻底隔离，越朴素越稳 |

修完之后 80/80 有效。**这四个坑，任何自己搭进化系统的人都会遇到**，面试时讲出来比背论文更有说服力。

## 5. 实验 A：Agent RSI（经验手册自优化）

### 5.1 设定

- **执行模型**（被冻结）：qwen3.8-flash，关思考模式，temperature 0.7。故意选弱一点的，让 harness 的作用看得见。
- **编辑器模型**：qwen3.7-plus，负责读失败、提修改。
- **Harness** = 系统提示 + 条目化 playbook（ACE 风格，每次只做一条 add / update / delete）。
- **任务**：5 类可程序判定的题（长字符串数字母、五位数×四位数、日期推算、长字符串倒序、28 个数找第 k 小），每类 6 题。
- **三份数据**：优化集（编辑器能看到失败样例）、held-out 集（只用于门槛，编辑器看不到）、test 集（只在最后用一次）。三份由不同随机种子生成，互不重叠。

### 5.2 一轮怎么转

```
1. 当前 harness 在优化集上每题跑 2 次 → 每题成功率 + 失败轨迹
2. 编辑器读 10 条失败样例 → 提 3 个候选，每个只改一条经验
3. 每个候选在同一优化集上每题跑 2 次
4. 门槛：按题配对 delta_i = 候选_i − 当前_i，bootstrap 2000 次，
         90% 置信区间下界 > 0 才算赢
5. 赢家再跑 held-out：不退步才采纳；否则 KEEP_BASE
6. 所有候选（含落选）进档案库
最后：原版 H0 与最终版本在 test 集上各跑一次
```

为什么用**配对**比较：同一道题对两个版本的难度一样，配对能消掉“题目难易”这部分方差，比直接比平均分灵敏得多。

### 5.3 实测结果（2026-11-05，本机，第一次完整运行）

基线 H0（“你是一个助手。回答要简洁。”，空 playbook）：优化集 0.683。分类型看：日期推算 1.0、找第 k 小 0.92、乘法 0.75、数字母 0.67、**倒序 0.08**。

**12 个候选，全部没过门槛**：

| 轮 | 候选 | 改动摘要 | 平均 delta | 90% CI 下界 | 结果 |
|---|---|---|---|---|---|
| R1 | C0 | 拆成字符列表逐个计数 | +0.033 | −0.083 | 不过 |
| R1 | C1 | 找第 k 小时先写出排序序列 | **+0.083** | −0.033 | 不过 |
| R1 | C2 | 倒序时从最后一个字符往前记录 | +0.017 | −0.067 | 不过 |
| R2 | C2 | 字符任务完成后二次校验长度和首尾 | +0.050 | −0.050 | 不过 |
| R3 | C1 | 乘法展示竖式或分配律 | **−0.050** | −0.150 | 不过 |
| R4 | … | （其余 7 个类似，delta 在 −0.05 到 +0.05） | | | 不过 |

四轮都是 `KEEP_BASE`，最终版本就是 H0。

**最后的 test 集对比**：H0 0.683，“最终版本”0.75，delta +0.067，CI 下界 0.0。

### 5.4 怎么读这个结果（本文最重要的一节）

**第一，+6.7 个点完全是噪声。**最终版本和 H0 是**同一个 harness**，两次跑 test 集差了 6.7 个点。也就是说，在 30 题 × 2 次的规模下，**同一个系统自己和自己比，就能差出 6–7 个点**。如果没有统计门槛，R1C1 的 +8.3 个点会被直接采纳，后面每一轮都在噪声上叠噪声，最后写报告说“经过 4 轮自进化提升了 X%”。

**第二，门槛是在保护你，不是在拖后腿。**R3C1（“展示竖式计算”）delta 是 −5 个点：让弱模型写长过程，它在长过程里出错更多。直觉上“好”的经验，实测可能有害。

**第三，要想检出真实的小改进，必须加样本。**粗算：配对 delta 的标准差约 0.3，想检出 +5 个点的改进（90% 单侧），需要大约 (1.28 × 0.3 / 0.05)² ≈ 60 个配对单位，每单位还得多次重复降低方差。本实验 30 题 × 2 次明显不够。这就是为什么 Harness² 论文明说“单次 rollout 只能算弱证据”。

**第四，有些失败 harness 救不了。**倒序任务基线 0.08，三个专门针对倒序的经验都没救回来：flash 模型在 token 层面就看不清长随机字符串里的单个字母。这类问题的正确答案是**给工具**（让 agent 调 Python 做 `s[::-1]`），而不是写更多提示。这也是 Harness² 把 scripts、tool guidance 列为可编辑组件的原因。

### 5.5 加大样本后的复跑

配置改成每类 10 题（共 50 题）× 每题 3 次，跑 3 轮。约 2100 次调用、28 万输入 + 75 万输出 token。

| 轮 | 候选 | 改动摘要 | delta | 90% CI 下界 | 结果 |
|---|---|---|---|---|---|
| R1 | C0 | 字符串倒序/计数：先拆成字符列表打印，再逆向拼接或计数 | +0.067 | −0.000 | 差一点，不过 |
| R1 | C1 | 乘法用分配律拆整百整千 | +0.033 | −0.020 | 不过 |
| R1 | C2 | 星期推算用模 7 公式 | +0.000 | −0.047 | 不过 |
| R2 | **C0** | 与 R1C0 几乎同义 | **+0.067** | **+0.007** | **通过 → held-out +0.02，不退步 → 采纳** |
| R2 | C1、C2 | 乘法按位拆、日期手动数 | 0.000 / −0.020 | — | 不过 |
| R3 | C0 | 删掉刚采纳的那条 | −0.053 | −0.127 | 不过（反向验证这条确实有用） |
| R3 | C1、C2 | “直接输出、不展示步骤” | −0.020 / +0.033 | — | 不过 |

最终 harness 只多了一条经验：

> 处理字符串反转或计数时，禁止直接输出结果。必须先将字符串拆分为单字符列表并打印，再基于列表进行逆向拼接或逐项统计，确保每一步可验证。

**test 集（从未参与选择）**：H0 0.693 → 0.827，配对 delta +0.133，90% CI 下界 +0.073，**通过**。分类型：数字母 0.70 → 0.97，倒序 0.10 → 0.40，乘法 0.67 → 0.77（未针对乘法改，可能是噪声），其余两类本来就满分。

**这次复跑说明了什么**：

1. **样本加大后，真实改进才检得出来。**同一类经验在第一次运行（30 题 × 2 次）里 CI 下界一直是负的；50 题 × 3 次后过了门槛，并在 test 集上得到确认。
2. **门槛边缘有运气成分。**R1C0 和 R2C0 内容几乎一样，一个下界 −0.000 被拒、一个 +0.007 通过。这正是为什么还需要 held-out 和 test 两道关：单看一次门槛，等于把“刚好过线”当成确定性结论。
3. **多重比较要记账。**这次一共试了 9 个候选，90% 单侧门槛下，纯靠运气混过去 1 个的概率并不低。真正保护结论的是**最后只用一次的 test 集**，它在这里给出了 +13.3 个点、下界 +7.3 的确认。
4. **删除测试是很好的反证。**R3C0 尝试删掉刚采纳的条目，delta −5.3 个点。“去掉它就变差”比“加上它变好了”更有说服力。
5. **倒序仍只有 0.40。**经验帮了忙，但离可用还远。§5.4 第四点的判断不变：字符级操作该给工具。
6. **成本**：为了得到一条经验，花了约 100 万 token。真实系统里，评估成本通常远大于生成成本，这也是 Dream-RSI 这类“先在历史轨迹上离线模拟”的工作想解决的问题。

## 6. 套到你自己的项目

### 6.1 通用落地清单

| 步骤 | 做什么 | 验收标准 |
|---|---|---|
| 1 | 找一个**可程序判定**的子问题 | 能写出 `score(task, output) -> float`，不需要 LLM |
| 2 | 建三份数据：优化 / held-out / test | test 集锁起来，只在最后用 |
| 3 | 测**噪声底**：同一版本跑两次，看差多少 | 得到“自己和自己比”的差距，后面任何改进必须明显大于它 |
| 4 | 定义可编辑面，写成文件 | 每个候选 = 一个 diff，可 `git revert` |
| 5 | 跑闭环，全量记录 | 轨迹 JSONL + 档案库 JSON |
| 6 | 配对统计门槛 + held-out | 默认 `KEEP_BASE` |
| 7 | 定期人工审计档案库 | 删过时 / 冲突条目 |

第 3 步是绝大多数人跳过、也最该先做的一步。

### 6.2 Personal Agent（τ-bench 方向）

τ-bench 按数据库终态判分，属于 §2 的 B 类，可以直接套实验 A 的框架：

| 阶段 | 内容 | 进入下一阶段的条件 |
|---|---|---|
| 0 地基 | agent loop 拆成“harness 目录 + 运行器 + 轨迹记录 + τ-bench 适配器” | 测出同版本两次运行的噪声底 |
| 1 L2 经验库 | 实验 A 的 playbook 机制，换成 τ-bench 任务 | 至少一个候选过配对门槛 + held-out |
| 2 L4 工具/skill | 编辑器可以提议新工具或改 tool guidance（对应 §5.4 第四点） | 两轮以上递归且 held-out 不退步 |
| 3 档案库探索 | 实验 B 的锦标赛 + 档案库，套到 harness 版本上 | 成本/收益可接受 |

**打榜合规**：对着公开 benchmark 自优化本身就有过拟合与泄漏风险。最终报告用未接触过的切分；评估时断网；对外写明“经过 N 轮 harness 自优化，优化集与报告集分离”。

### 6.3 什么时候该换框架而不是自己写

本文两个实验各约 200 行，目的是看清原理。要认真做时：

- 过程优化 → [OpenEvolve](https://github.com/codelion/openevolve)（Apache-2.0，MAP-Elites + 岛模型，用 `EVOLVE-BLOCK-START/END` 标出可进化区域）或 [ShinkaEvolve](https://github.com/SakanaAI/ShinkaEvolve)（Apache-2.0，新颖性过滤、UCB 选模型、异步进化，ICLR 2026）。
- Agent 经验库 → 参考 [ACE](https://arxiv.org/abs/2510.04618) 的 Generator / Reflector / Curator 三角色。
- 完整 harness 进化 → 参考 R167 里的 Harness² 源码结构。

## 7. 面试问答（按被问概率排序）

**Q1：什么是 RSI？现在的 agent 真的能自我改进吗？**
RSI 是系统持久地修改自己，且修改后的版本参与后续改进。现在能工程化的主要是 harness-level：冻结模型，进化 prompt、记忆、工具、agent 代码。真实案例有 AlphaEvolve 在 Google 内部的调度启发式（平均回收约 0.7% 全球算力，已上线一年以上）和 DGM 在 SWE-bench 上 20% → 50%。但权重层面的、无人监督的“智能爆炸”式 RSI 没有可信证据。

**Q2：怎么证明 agent 真的变好了，而不是噪声？**
三件事。一，先测噪声底：同一版本跑两次差多少。我自己的实验里，30 题 × 2 次的规模下，同一个 harness 自己和自己比就能差出 6.7 个点。二，配对比较 + bootstrap 置信区间，下界大于 0 才采纳。三，用没参与选择的 held-out 和 test 集复验，因为试了很多候选，总有一个会碰巧过门槛（多重比较）。我把样本加到 50 题 × 3 次后，一条经验过了门槛，test 集上 +13.3 个点、下界 +7.3，这时才敢说是真的。再加一个反证：尝试删掉这条经验，分数掉 5.3 个点。

**Q3：为什么要档案库，不直接保留最优？**
贪心爬山会卡局部最优。档案库保留所有有效变体，允许从暂时不是最优的版本继续分支。DGM 的消融实验证明去掉开放式探索收益明显变小。我自己跑装箱进化时，最终最优程序的祖先在中途已经不是当代最优，只保留最优的话这条路会被剪掉。

**Q4：自进化系统最大的风险是什么？**
评估器被骗或被噪声误导。DGM 论文里 agent 伪造过工具日志、删过幻觉检测标记。对策：评估器与被测系统隔离（日志由运行器写，不由 agent 自报）、评估时断网、候选代码沙箱执行、生产变更人工审批。

**Q5：ACE 和普通的 prompt 优化有什么区别？**
普通 prompt 优化每轮重写整段提示，ACE 论文指出两个问题：brevity bias（越改越短，丢掉领域细节）和 context collapse（反复重写侵蚀积累的知识）。ACE 用 Generator / Reflector / Curator 三个角色，把经验做成条目，只做增量的增删改。论文报告 agent 任务 +10.6%、金融任务 +8.6%（已核对 arXiv 摘要，ICLR 2026）。

**Q6：AlphaEvolve 适合什么问题，不适合什么问题？**
适合有便宜、自动、可信打分函数的问题：kernel、调度启发式、数学构造。它的产物是可读代码，可以 review。不适合打分要靠人或 LLM 主观判断的问题，也不适合单次评估很贵的问题。

**Q7：你自己做过吗？遇到什么问题？**
做过两个最小实验（§4、§5）。印象最深的三点：一是安全过滤用正则会误杀注释里的普通单词，导致一半候选被拒，搜索被悄悄饿死，改成 AST 检查才好；二是小样本下 agent 经验优化的 12 个候选全部没过统计门槛，看起来最合理的“展示竖式”反而降了 5 个点，样本加大后才检出一条真改进；三是进化出的装箱启发式，训练集第一在测试集上不一定第一，选择偏差很明显。最后的判断是：评估成本和统计设计比生成算法更决定成败；弱模型的字符级失败应该给工具，而不是加提示。

**Q8：怎么防止过拟合 benchmark？**
数据切三份（优化 / held-out / test），test 只在最后用一次；限制每轮编辑量（RRSI 的做法）；经验条目要求是“通用方法”而不是“某题答案”，并在入库前检查有没有泄漏评分标准（Harness² 的做法）。

## 开放问题

1. 实验 A 若给执行模型加工具，经验库能否学会“何时用工具”，倒序任务能否从 0.40 继续提升？
2. 进化式搜索的选择偏差（训练集最优 ≠ 测试集最优）能否靠“多 seed 平均选最优”缓解，代价多大？
3. τ-bench 的噪声底有多大？需要多少任务 × 重复次数才能检出 3 个点的真实提升？
