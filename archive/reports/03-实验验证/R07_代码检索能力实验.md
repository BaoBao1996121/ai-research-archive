# 实验4: 代码检索能力测试 — 从用户意图到代码定位

## 核心问题

上一轮实验证明了 AST 结构化方法能把 759 万 token 的代码库压缩 30-370 倍。但压缩 ≠ 检索：

> **用户说 "修改权限检查"，这些结构能帮我定位到 `bashPermissions.ts` 吗？**

本实验直接回答这个问题。

---

## 实验设计

### 测试标本
Claude Code 源码，1,884 文件 / 47.7 万行 / 11,113 个唯一符号。

### 构建的索引体系

| 索引层 | 内容 | 大小 |
|--------|------|------|
| **符号倒排索引** | symbol_name → [{file, type, line, signature}] | 11,113 key |
| **BM25 文本索引** | 路径分词 + 符号分词 + 注释 + 字符串常量 | 93,732 token / 468,276 bigram |
| **依赖关系图** | file → {imports_from, imported_by} | 1,884 节点 |
| **PageRank 排名** | 全局重要性评分 | 基于依赖图计算 |

索引构建耗时: **5.03 秒**（含 AST 解析 + 依赖分析 + PageRank）

### 四种检索策略

1. **Symbol Match** — 精确/模糊符号名匹配
2. **BM25** — 经典文本检索 + PageRank 加权
3. **Multi-Signal** — 符号×3 + BM25 + 路径匹配 + PageRank 加权
4. **Intent-Routed** — 先识别用户意图(查找/修改/调试/重构)，再路由到最优策略组合

### 10 个测试查询

| # | 查询 | 期望文件 | 意图类型 |
|---|------|----------|----------|
| 1 | BashTool 权限检查 | bashPermissions.ts, BashTool.tsx | 修改功能 |
| 2 | MCP client 连接 | mcp/client.ts, mcp/auth.ts | 修改功能 |
| 3 | 添加新的 Tool | Tool.ts, tools.ts | 修改功能 |
| 4 | 修改 commit 命令 | commands/commit.ts | 修改功能 |
| 5 | 会话存储 session | sessionStorage.ts, sessionHistory.ts | 修改功能 |
| 6 | buildTool 在哪里定义 | Tool.ts | 查找符号 |
| 7 | logEvent 错误追踪 analytics | analytics/index.ts | 排查错误 |
| 8 | 重构 AgentTool 的输出类型 | AgentTool.tsx, UI.tsx | 重构 |
| 9 | REPL 界面的键盘快捷键 | screens/REPL.tsx, keybindings/ | 修改功能 |
| 10 | bridge 远程连接 token 认证 | bridgeMain.ts, jwtUtils.ts | 修改功能 |

## 关键发现

### 发现1: 语义鸿沟是最大瓶颈

| 用户查询(中文) | 需要匹配的英文 | 纯结构索引能否匹配 |
|:---:|:---:|:---:|
| 权限检查 | permission, security | ✗ 不能 |
| 快捷键 | keybinding, shortcut | ✗ 不能 |
| 认证 | auth, jwt, trusted | ✗ 不能 |
| 连接 | client, connection | △ 部分 |
| 会话存储 | sessionStorage | △ 部分 |
| 工具 | Tool | ✓ 能（恰好同形） |
| 命令 | commands, commit | ✓ 能（查询含英文） |

**结论**: 纯结构化索引的天花板是 **"语义映射"** —— 用户用自然语言（尤其中文）描述需求时，无法桥接到英文代码标识符。

### 发现2: 路径匹配是最可靠的信号

在 6 个成功案例中，**5 个靠路径匹配（path）定位**，仅 1 个靠纯 BM25。

这说明：
- 好的目录结构和命名约定 = 最好的检索"索引"
- `tools/BashTool/`、`services/mcp/`、`commands/commit.ts` 这种结构本身就是 key-value 关联
- 当目录下文件过多时（bridge/ 有 24 个文件），路径匹配的区分度下降

### 发现3: PageRank 提供有价值的校准

bootstrap/state.ts（PageRank #1）在"会话存储"查询中排到第3位，即使 "session" 不在其路径中。这是因为它是全局最核心的文件，BM25 分数被 PageRank 放大了。

但 PageRank 也有副作用：它让**核心文件总是倾向上浮**，可能遮蔽更具体的小文件。

### 发现4: 意图路由有潜力但规则太粗

当前基于关键词的意图识别只能做基础路由：
- "在哪里定义" → find_symbol ✓
- "错误追踪" → debug_error ✓
- "重构" → structural ✓（但搜索执行有 bug）

实际价值体现在：自动追加依赖上下文（multi_signal_with_deps 策略会给 Top1 结果补充其依赖文件）。

## 核心结论: 这些结构适合检索吗？

### 回答: **适合，但只能覆盖 60-70% 的场景。要达到 90%+ 需要 LLM 参与。**

#### 能力矩阵

```
                        纯结构索引    + LLM Query Rewrite    + Embedding

精确符号查找              ●●●●●        ●●●●●                 ●●●●●
相同语言关键词搜索         ●●●●○        ●●●●●                 ●●●●●
路径/目录定位             ●●●●●        ●●●●●                 ●●●●○
跨语言语义搜索(中→英)      ●○○○○        ●●●●○                 ●●●●●
"添加类似功能" (模式搜索)   ●●○○○        ●●●○○                 ●●●●○
"为什么这样实现" (意图理解)  ○○○○○        ●●●●○                 ●●○○○
```

### 三层检索架构建议

```
┌─────────────────────────────────────────────────┐
│  Layer 3: LLM 语义层 (Query → Rewrite → Search) │  ← 处理语义鸿沟
│  "权限检查" → "permission check security auth"   │
├─────────────────────────────────────────────────┤
│  Layer 2: 结构索引层 (本实验构建的)               │  ← 快速定位
│  符号索引 + BM25 + 依赖图 + PageRank             │
├─────────────────────────────────────────────────┤
│  Layer 1: 文件系统层                             │  ← 最基础
│  路径匹配 + 目录结构 + 文件名                      │
└─────────────────────────────────────────────────┘
```

**工作原理:**
1. 用户输入 "修改 BashTool 的权限检查"
2. **Layer 3 (LLM)**: 识别意图(修改功能) + 翻译关键词("权限检查" → "permission", "security", "authorization")
3. **Layer 2 (结构索引)**: 多信号融合搜索 → 排名 → 取 Top N
4. **Layer 1 (路径)**: "BashTool" 匹配 `tools/BashTool/` 目录
5. **最终结果**: `bashPermissions.ts` (#1), `bashSecurity.ts` (#2), `BashTool.tsx` (#3)

### 为什么不直接用 Embedding？

| 维度 | 结构索引 + LLM Rewrite | Embedding |
|------|----------------------|-----------|
| 构建速度 | 5 秒 | 数小时(大库) |
| 更新成本 | 增量解析单文件 | 重新嵌入 |
| 可解释性 | 完全可解释(哪个信号命中) | 黑盒 |
| 精确匹配 | 完美 | 较弱 |
| 语义匹配 | 依赖 LLM rewrite | 内建 |
| 存储成本 | KB 级 | GB 级 |

Sourcegraph 的生产实践也印证了这点：他们**放弃了 Embedding**，改用 BM25 + Code Graph，和我们的架构思路一致。

## 与上一轮实验的整合

| 实验 | 解决的问题 | 核心发现 |
|------|-----------|---------|
| 实验1 (Repo Map) | 代码库压缩 | 369x 压缩率，20K token 概览全局 |
| 实验2 (依赖图) | 编辑上下文 | 直接依赖可控，2层依赖爆炸(3.7-25x) |
| 实验3 (PageRank) | 重要性排名 | 核心文件识别优于原始引用计数 |
| **实验4 (检索)** | **意图→代码定位** | **MRR=0.68，语义鸿沟是天花板，需 LLM rewrite** |

**完整流程拼图:**

```
用户意图 ─→ [LLM: 意图识别+关键词翻译]
              ↓
         [结构索引: 多信号融合检索]  ←── Repo Map (实验1)
              ↓                     ←── 依赖图   (实验2)  
         [排名: PageRank加权]       ←── PageRank  (实验3)
              ↓
         Top-K 相关文件
              ↓
         [Budget: 按 token 预算裁剪]
              ↓
         → 送入 LLM 上下文窗口
```

## 下一步可验证的方向

1. **LLM Query Rewrite**: 在检索前用小模型将中文查询翻译为英文代码关键词，预期将 MRR 从 0.68 提升到 0.85+
2. **符号关系图**: 不只是 import 关系，还要提取 "谁调用了谁"、"谁实现了谁接口"
3. **增量更新**: 单文件修改 → 只重新解析该文件 → 更新索引（不重建全量）
4. **与 LLM 的交互式检索**: LLM 看到第一轮结果后，决定是否需要扩展搜索范围
