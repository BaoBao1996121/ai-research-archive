## 二、三个缺失环节的补救方案

### 缺失1：效果度量闭环

**问题**：遵循率 100% 但返工率不下降，说明规则本身有问题——这个信号需要额外追踪。

**补救**：引入"返工计数器"（见建议1），将形式审计与效果指标交叉分析。

```
当前：  做 → 提炼规则 → 审计"规则被执行了吗" → 反思
                        ↓ ← 新增
               审计"执行规则后结果变好了吗"
```

### 缺失2：规则淘汰机制

**问题**：规则集单调递增。每条规则消耗 AI 上下文窗口和注意力。超过阈值后，边际遵循率断崖下降——新规则不仅自己不被执行，还稀释已有规则的执行质量。

**补救**：引入"规则断舍离三问"（见建议4），每 Sprint 执行一次。

### 缺失3：结构化案例库

**问题**：提炼质量取决于"还记得多少"而非"实际发生了多少"。重要但不显眼的事故被遗忘，反复出现的小摩擦因"不值得记"而从未被提炼为规则。

**补救**：建"踩坑速查表"（见建议2），一行一事故，30 秒追加。

## 三、六条可实操改进建议

### 建议1：返工计数器 — 最小成本效果度量

| 属性 | 值 |
|------|---|
| **解决** | 缺失1（效果度量闭环） |
| **优先级** | 立即执行 |
| **启动成本** | 改模板 1 分钟，每次会话多填 10 秒 |

**做法**：在 `_开发进度追踪.md` 每条会话日志中增加：

```markdown
**返工次数**：N（原因：xxx）
```

返工定义：本次会话中，因上次会话产出的质量问题（方案描述错误、代码 bug、文档遗漏）需要回头改的次数。

**验证标准**：规则迭代有效 → 这个数字随 Sprint 推进下降。不下降 → 规则"被遵循了"但"没改善质量"。

---

### 建议2：踩坑速查表 — 结构化案例库

| 属性 | 值 |
|------|---|
| **解决** | 缺失3（案例库） |
| **优先级** | 立即执行 |
| **启动成本** | 5 分钟填已知事故，后续每次 30 秒 |

**做法**：在 `_开发进度追踪.md` 末尾新增：

```markdown
## 五、踩坑速查

| 会话 | 事故 | 根因 | 产生的规则 | 规则有效？ |
|------|------|------|-----------|-----------|
```

**价值**：
- 步骤2 提炼方法论时翻表即可，不翻日志
- "规则有效？"列 = 效果度量
- 积累 10+ 行后可看事故模式分布

---

### 建议3：固定反思节奏 — 不靠灵感靠节律

| 属性 | 值 |
|------|---|
| **解决** | 反思频率不够 |
| **优先级** | 次日开始 |
| **启动成本** | 每日 2 分钟 + 每 Sprint 30 分钟 |

**每日微反思**（当天最后一个 dev 会话结束后，2 分钟）：

```
📝 今天什么重复了？[xxx]
📝 今天什么浪费了？[xxx]
📝 哪条规则今天多余了？[xxx / 无]
```

不分析不总结，只记原始观察。素材积累比分析重要。

**每 Sprint 深度反思**（Sprint 结束时，30 分钟）：
1. 翻本 Sprint 所有"每日微反思"
2. 翻"踩坑速查表"新增行
3. 执行规则断舍离（建议4）
4. 输出：本 Sprint 要**新增 / 修改 / 删除**哪些规则

---

### 建议4：规则断舍离

| 属性 | 值 |
|------|---|
| **解决** | 缺失2（规则淘汰机制） |
| **优先级** | 本周内 |
| **启动成本** | 15 分钟 |

**做法**：打开 `dev.agent.md` + `dev-workflow.instructions.md`，对每条规则问三个问题：

| 问题 | 如果答案是… | 动作 |
|------|-----------|------|
| 过去 5 个会话里执行了几次？ | 0 次 | 候选删除 |
| AI 跳过它，最坏后果？ | 后果可接受 | 候选删除 |
| 被违反后造成了什么问题？ | 没被违反过 | 可能是废话规则 |

**后续**：每 Sprint 或每 10 个会话执行一次，与深度反思合并。

---

### 建议5：区分指挥能力与领域能力

| 属性 | 值 |
|------|---|
| **解决** | 步骤1 隐患（提炼偏向指挥技巧而非领域判断） |
| **优先级** | 持续 |
| **启动成本** | 每周 30 分钟 |

指挥能力关注任务拆解与执行组织，领域能力关注独立判断技术方案。

**判断标准**：AI 在某技术点给了错误方案，你在 review 时能发现吗？不能发现的 = 盲区。

---

### 建议6：项目结束时整理冷启动包

| 属性 | 值 |
|------|---|
| **解决** | 经验迁移 |
| **优先级** | 项目告一段落时 |
| **启动成本** | 1 小时 |

```
冷启动包/
├── agent-template.md        # dev agent 骨架（T1-T4 + 会话协议，删项目专属内容）
├── checklist-first-week.md  # 第一周：建进度追踪 + 建踩坑表 + 跑第一个 Spike

```

下个项目从这个包开始，不从零开始——这是飞轮的产物。

## 四、可迁移方法

### 经验1：触发器设计优于过程清单

**迁移做法**：下次做 agent 规则，直接用触发器模式起步（`触发条件 + 动作 + Why`），不从过程清单开始再精简。

### 经验2：规则必须附带事故锚点

**迁移做法**：每条规则锚定一个事故或案例。没有锚点的规则 = 没有根基的规则 = 第一个被遗忘的规则。

### 经验3：先干活后提炼，提炼要趁热

**迁移做法**：每天结束 2 分钟微反思，不积攒一周后回忆。

### 经验4：精简靠淘汰不靠压缩

**迁移做法**：每 Sprint 规则断舍离三问，删掉问不出答案的规则。

### 经验5：形式审计 + 效果指标双轨并行

`_check_session.py` 告诉你"有没有做"，返工计数器告诉你"做了之后好了吗"。

**迁移做法**：同时追踪遵循率和效果指标，交叉分析才有意义。
