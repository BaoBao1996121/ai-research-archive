## 架构设计：双层分离

```
┌─ 通用层（跨项目复用，用户级）
│  ~/.copilot/instructions/dev-workflow.instructions.md  
│  ├── 质量触发器 T1(设计审查) / T2(编码前验证) / T3(会话结束)
│  ├── 会话生命周期（启动/结束/拆分建议）
│  ├── 编码原则 + 需求红线
│  ├── 文件锚定机制规格
│  └── 知识库优先协议 + 质量底线
│
├─ 项目层（项目专属，工作区级）
│  .github/agents/dev.agent.md  
│  ├── 启动必读文件表
│  ├── 会话结束同步目标
│  ├── 技术环境速查
│  ├── 需求与代码映射
│  ├── 知识库引用（只读）
│  └── 飞书/部署操作
│
└─ 辅助文件（项目内）
   docs/_check_session.py      ← T3 触发器执行的验证脚本
   docs/_假设验证.md            ← T2 触发器读取的状态文件
   docs/_环境清单.md            ← T2 触发器检查的环境记录
```

### 加载机制

- **通用层**：放在 `~/.copilot/instructions/` 下，VS Code 根据 `description` 语义匹配自动注入。做开发活动时加载，非开发场景不加载。
- **项目层**：放在项目的 `.github/agents/` 下，只有在该工作区用 `@dev` 时加载。不同工作区的 dev.agent.md 互不干扰。
- **两层叠加**：使用 `@dev` 时，通用层 + 项目层同时生效。

### 设计决策

| 决策 | 选择 | 为什么 |
|------|------|--------|
| 通用层放 instructions 而非 agent | instructions | instructions 靠 description 匹配，即使不用 @dev 也能在开发场景生效 |
| 项目层只放数据不放规则 | 纯数据 | 规则在通用层统一维护，避免多项目规则不一致 |
| 触发器用触发式而非顺序式 | 触发式 | "改 .py 文件前先读 _假设验证.md" 比 "第4步执行验证" 遵循度高 |
| 验证脚本独立于 agent | Python 脚本 | 即使 agent 忘记执行，用户也能手动跑——独立安全网 |

## 遵循度保障：四种机制

核心洞察：**不信任模型"记住规则"的能力，用工程手段检查关键步骤是否执行**。

### 机制 1：subagent 隔离（T1 设计审查）

**问题**：设计审查 Checklist 有 5 项，主 agent 在长对话中容易漏项。
**方案**：设计完成后 spawn `coding-reviewer` subagent，把 Checklist 传给它。subagent 每次拿到新鲜的、完整的 prompt，不受主对话历史稀释。

```
主 Agent 写完概念设计
    ↓
触发器 T1：runSubagent(agentName="coding-reviewer")
    prompt 包含设计内容 + 5 项 Checklist
    ↓
subagent 返回逐项 ✅/❌ 结果
    ↓
主 Agent 展示审查结果给用户
```

### 机制 2：文件锚定（T2 编码前验证）

**问题**：假设验证和环境发现容易在编码兴奋中被跳过。
**方案**：把状态写到文件里（`_假设验证.md`、`_环境清单.md`），触发器在首次修改代码文件时自动 `read_file`。文件里有 ❌ 就必须先处理。

**设计理由**：不需要模型"记住要验证"——触发条件是具体的工具调用动作（修改 .py 文件），行动是读一个文件。这比"在遥远的未来某个阶段记得做某事"可靠得多。

### 机制 3：触发式规则（替代顺序式）

**顺序式示例**：
```
开发工作流第4步：编码前验证所有外部依赖
```

**触发式示例**：
```
当你即将修改 .py 文件时：
如果本次会话还没有读取过 docs/_假设验证.md，先读一次。
```

触发条件和行动之间的距离更短——模型在做某个动作的当下看到关联规则，比"记住第4步"可靠。

### 机制 4：验证脚本硬门控（T3 会话结束）

**问题**：会话结束时最容易跳过文档同步。
**方案**：`_check_session.py` 在 `task_complete` 前执行，检查：
- 进度追踪是否在近 10 分钟内更新
- 假设验证文件是否有未处理项
- 环境清单是否存在

exit 1 = 阻断，必须修复。即使 agent 忘记跑脚本，用户也能手动执行。

### 四种机制的适用对照

| 改进项 | 机制 | 为什么选这个 |
|--------|------|-------------|
| 设计审查 | subagent 隔离 | 审查逻辑复杂，主 agent 记不住完整 Checklist |
| 假设验证 | 文件锚定 + 触发规则 | 创建文件一次性，后续靠读文件触发 |
| 逐功能验证 | 触发规则 | "改完→跑测试"足够简单 |
| 会话结束 | 验证脚本 | 独立安全网，agent 忘了用户也能跑 |
| 知识库查询 | 触发规则 | "选型决策→先查 KNOWLEDGE_INDEX" |
| 环境发现 | 文件锚定 | 清单创建一次，后续读取 |

## 使用方式

### 新项目示例（需先准备所引用的模板与脚本）

```powershell
# 1. 创建目录
mkdir .github\agents

# 2. 复制模板
copy "$env:USERPROFILE\.copilot\templates\dev-agent-template.md" ".github\agents\dev.agent.md"

# 3. 填写 {} 占位符（~5 分钟）
# 4. 按项目配置使用 @dev，并检查所需记录是否创建
```

### 短期小项目

不需要创建 `dev.agent.md`。通用层 `dev-workflow.instructions.md` 靠 description 匹配会在开发场景自动加载，触发器 T1-T3 照常生效。

## 开放问题与后续计划

1. **遵循度实测数据待收集**：T1-T3 触发器在真实开发中的实际遵循率需要 3-5 次会话验证。当前是设计阶段，还没有生产数据。
2. **Skill 化时机**：当这套模式在 3+ 个项目中验证有效后，可以固化为正式 Skill（含 SKILL.md + 脚手架脚本），自动生成项目层文件。
3. **触发器扩展**：当前 3 条触发器（设计审查/编码前验证/会话结束），随着实践可能需要新增（如"PR 提交前""部署前"）。
4. **验证脚本增强**：`_check_session.py` 设计为检查 3 项，可根据项目需要扩展（如"接口文档是否同步""飞书是否更新"）。
