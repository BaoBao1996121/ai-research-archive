# R87 — 技术文档转单人播客方案调研

> **核心结论**：技术文档转通勤可听内容，瓶颈不在语音合成（听书 App 自带 TTS 就够），而在**口播文本改写**——如何在"信息零丢失"和"听着不累"之间取平衡。最优路径是"LLM 分块改写 + 忠实性约束 Prompt → 口播文本 → 导入听书 App"。已提供 `doc2oral.py` 一键转换工具。

## 一、定位透镜

### 1.1 纵轴：技术演进

| 阶段 | 时间 | 特征 | 代表 |
|------|------|------|------|
| 萌芽 | 2022 前 | 简单 TTS 朗读原文，无改写 | macOS `say` / espeak |
| 起飞 | 2023-2024 | LLM 改写 + 神经 TTS，Google NotebookLM 引爆 | NotebookLM, Podcastfy |
| 成熟 | 2025-2026 | 开源方案追平闭源，多语言/长文/单人/多人全覆盖 | Podcastfy 0.4+, Fish Speech S2, CosyVoice v3 |

**生命周期定位**：上升期末段，接近成熟。核心技术路线已收敛（LLM 改写 + 神经 TTS），竞争焦点转向质量细节和成本优化。

### 1.2 横轴：同场景方案对比

| 方案 | 类型 | 核心差异 |
|------|------|----------|
| Google NotebookLM | 闭源 SaaS | 标杆品质，双人对谈，仅支持英文最佳，无 API |

纵轴：技术已成熟到"即插即用"程度，不需要从零造轮子。
横轴：**本库 P02 已有可用原型**，核心改进方向是——升级口播改写 Prompt 的内容保真度 + 替换更高质量的 TTS 引擎。

## 二、问题拆解：为什么不能直接 TTS 念原文？

技术文档直接用 TTS 朗读，听感极差。原因有三：

1. **书面语 ≠ 口语**：技术文档充满列表、表格、代码块、嵌套括号。耳朵无法处理 "详见表 3.2（第 47 页）" 这种引用
2. **信息密度过高**：一页 A4 的信息量，阅读需要 5 分钟但听要 15 分钟。不做精简/重组，听众会信息过载
3. **缺乏叙事结构**：文档是层级结构（H1→H2→列表），播客是线性流。需要加过渡语、前后呼应、节奏感

因此，核心技术挑战是"**改写**"而非"**合成**"。

## 三、两阶段管线深度分析

```
┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│ 原始 Markdown │────▶│ LLM 口播改写  │────▶│  TTS 语音合成 │────▶ MP3
│   技术文档     │     │ (Stage 1)    │     │ (Stage 2)    │
└──────────────┘     └──────────────┘     └──────────────┘
```

### 3.1 Stage 1：LLM 口播改写

这是整个管线中**最关键也最难**的环节。核心矛盾：

> 改写得越口语化 → 听感越好 → 但信息丢失越多
> 改写得越忠实 → 信息保全 → 但像念稿，没人想听

#### 3.1.1 改写策略：分块 + 位置感知 Prompt

本库 P02 已经实现的核心思路是正确的：

```
长文档 → 按章节分块（~8000字/块）→ 每块独立改写 → 拼接
```

关键改进点：

| 维度 | 当前 P02 做法 | 推荐改进 |
|------|--------------|---------|
| 分块粒度 | 按 H1/H2 标题分 | 保持现状，但增加重叠窗口（前一块最后 200 字作为上下文） |
| 位置 Prompt | 有 first/middle/last 区分 | 增加"全文摘要"注入每个 chunk 的 system prompt |
| 忠实性约束 | "严禁编造" | 增加结构化约束：要求逐段落映射，标注信息来源 |
| 数据保全 | "不要跳过数据" | 要求数字/百分比/指标必须原样保留，用口语化句式包裹 |

#### 3.1.2 口播文体转换的具体技巧

好的口播改写需要做到：

**要做的**：
- 把列表变成递进句：`"首先...其次...最关键的是..."` 替代 bullet 列表
- 把表格变成对比叙述：`"A 方案的延迟是 100ms，而 B 方案只要 30ms，差了三倍多"`
- 把代码块变成意图描述：`"这里的核心逻辑就一句话——遍历所有文件，过滤出 .ts 后缀的"`
- 加呼吸感：适当的停顿词、过渡语、总结回顾
- 给数据加语境：`"8192 个 token——大约相当于 6000 个中文字，差不多一篇长文章的量"`

**不要做的**：
- 不要加"让我们一起来学习吧！"这种空话
- 不要把 3 行信息展开成 30 行废话
- 不要省略关键数据只留定性结论
- 不要编造原文没有的例子或数据

#### 3.1.3 推荐的 Prompt 结构（单口模式）

```
你是一位资深技术播客主播，正在录制一期通勤路上听的技术播客。

## 改写规则
1. **信息保全**：原文的每个核心观点、数据、对比都必须保留，不可省略
2. **口语重构**：用说话的方式重新组织，但信息量不能缩水
3. **节奏控制**：每讲完一个概念，用一句话总结，再过渡到下一个
4. **数据口语化**：把表格/列表转成自然的递进或对比句式，保留原始数字
5. **术语解释**：首次出现的术语要用大白话解释一遍
6. **禁止编造**：只讲原文有的内容

## 文体要求
- 像对着一个技术朋友聊天，不是在教室上课
- 不用"首先第一点、其次第二点"这种机械结构，用自然过渡
- 适当加入"这里划重点""说到这个很有意思""你可能会好奇"等引导词
- 不要堆砌感叹号，不要用"让我们一起来看看吧"
```

#### 3.1.4 LLM 选型建议

| 模型 | 推荐度 | 理由 |
|------|--------|------|
| **Qwen-Max / Qwen-Plus** | ★★★★★ | 中文改写质量最佳，成本合理，本库已集成 |
| Claude 3.5 Sonnet+ | ★★★★☆ | 指令遵从好，但中文口语感略逊 Qwen |
| GPT-4o | ★★★★☆ | 稳定可靠，但中文播客风格需要更多 Prompt 调教 |
| DeepSeek-V3 | ★★★☆☆ | 成本极低，质量够用，适合批量处理 |
| Llama 3.3 70B | ★★★☆☆ | 可本地部署，但中文口语化能力弱于 Qwen |

### 3.2 Stage 2：TTS 语音合成

TTS 是管线中技术最成熟的环节。2025-2026 年的中文 TTS 已经到了"不仔细听分不出真假"的水平。

#### 3.2.1 TTS 方案横评

| TTS 方案 | 中文质量 | 成本 | 部署方式 | 延迟 | 适合场景 |
|----------|---------|------|---------|------|---------|
| **CosyVoice v3**（阿里） | ★★★★★ | ¥1/万字符 | API 调用 | 低 | **推荐：中文播客首选** |
| **Fish Speech S2** | ★★★★★ | 开源免费 | 本地 GPU | 极低 | 有 GPU 资源的场景 |
| **edge-tts** | ★★★★☆ | 完全免费 | API 调用 | 低 | **推荐：零成本方案** |
| Kokoro-82M | ★★★☆☆ | 开源免费 | 本地 CPU/GPU | 低 | 英文好，中文一般 |
| OpenAI TTS (tts-1-hd) | ★★★☆☆ | $15/百万字符 | API 调用 | 中 | 英文极佳，中文一般 |
| ElevenLabs | ★★★★☆ | $5/月起 | API 调用 | 低 | 英文极佳，中文可用 |
| Azure TTS (Neural) | ★★★★☆ | $16/百万字符 | API 调用 | 低 | 企业级稳定性 |

#### 3.2.2 单人播客 TTS 的特殊要求

与通用 TTS 不同，播客场景对 TTS 有额外要求：

1. **长文本连贯性**：10 分钟以上的音频，声音不能忽高忽低、节奏不能断裂
2. **情感自然度**：不能像机器人念稿，需要有语调起伏、适当的停顿
3. **语速可控**：通勤听播客最佳语速约 1.0x-1.2x，太快听不清，太慢犯困
4. **中文标点韵律**：句号要有明显停顿，逗号轻停，问号要有升调

**各方案在这些维度上的表现**：

- **CosyVoice v3**：长文连贯性最好，有多种中文音色可选（龙安洋/龙安欢等），单次最大 20000 字符
- **Fish Speech S2**：支持 `[pause]` `[emphasis]` 等情感标签，可细粒度控制韵律，但需要 GPU
- **edge-tts**：免费且质量不差，支持语速/音调控制，中文有 `zh-CN-XiaoxiaoNeural` 等高质量音色

#### 3.2.3 音频后处理

TTS 输出的原始音频还需要：
- **静音裁剪**：去掉分块间的多余静音
- **响度标准化**：统一到 -16 LUFS（播客行业标准）
- **格式转换**：MP3 128kbps 是播客分发标准
- **元数据写入**：标题、封面图、章节标记（供播客 App 显示）

工具：`pydub` + `ffmpeg` 即可完成。

## 四、与本库 P02_podcast-maker 的差距分析

本库已有 P02_podcast-maker（原稿引用文件未随本次归档发布） 原型，下面分析它与"最优单人播客方案"的差距：

| 维度 | P02 当前状态 | 理想状态 | 差距 |
|------|-------------|---------|------|
| 口播改写 | 有单口 Prompt，有分块 | 需要加忠实性约束、全文摘要注入 | 中 |
| TTS 引擎 | CosyVoice（阿里云） | CosyVoice 已是最优选之一 | 小 |
| 内容保真 | "严禁编造"规则 | 需要逐段映射验证 | 中 |
| 音频后处理 | 基本拼接 | 缺响度标准化、章节标记 | 小 |
| 输出格式 | WAV→MP3 | 需要加元数据供阅读 App 显示 | 小 |
| GUI | Tkinter 桌面 | 够用 | 无 |

**结论**：P02 的架构方向正确，主要改进空间在 Prompt 工程（Stage 1）和音频后处理细节。

## 五、推荐实施方案（纯文本路径）

### 5.0 最简路径：口播文本 + 听书 App

实际需求更简单——不需要自己跑 TTS，只需要生成高质量口播文本，导入听书 App（微信读书/静读天下/Moon Reader 等），用 App 自带的 TTS 朗读。

```
┌─────────────┐     ┌───────────────┐     ┌────────────┐     ┌──────────────┐
│ Markdown 文档 │────▶│ doc2oral.py   │────▶│ 口播 .txt   │────▶│ 听书 App 朗读 │
│ (reports/)   │     │ Qwen 口播改写   │     │ output/oral/│     │ 通勤听        │
└─────────────┘     └───────────────┘     └────────────┘     └──────────────┘
```

**工具已就绪**：`prototypes/P02_podcast-maker/doc2oral.py`

```bash
# 单篇转换
python doc2oral.py reports/04-工程实践/R30_RAG从入门到生产落地.md

# 指定模型（默认 qwen-plus）
python doc2oral.py reports/01-理论与架构/R37_Transformer原理从直觉到代码.md --model qwen-max

# 批量处理整个目录
python doc2oral.py reports/01-理论与架构/

# 输出到指定目录
python doc2oral.py reports/ --output ~/Desktop/oral/
```

**预估成本**（1 万字报告）：
- Qwen-Plus：~¥0.5
- Qwen-Max：~¥2（质量更好）
- 生成时间：2-3 分钟
- 输出：1-1.5 万字口播文本（约 20-30 分钟听书时长）

**导入听书 App 的方法**：
- **微信读书**：微信传 txt 文件给自己 → 用微信读书打开 → 自动语音朗读
- **静读天下 / Moon Reader**（Android）：txt 放进手机任意文件夹 → App 打开 → TTS 朗读
- **Apple Books**（iOS）：AirDrop 或 iCloud 传 txt → 打开 → 朗读功能
- **语音梦阅读器**（iOS）：支持多种 TTS 引擎，效果最好的 iOS 听书 App

### 5.1 进阶路径：自合成音频（P02 原有能力）

如果对听书 App 的 TTS 不满意，可以用 P02 的完整管线自行合成：

```
│ Markdown 文档 │────▶│ Qwen-Max 口播改写│────▶│ CosyVoice │────▶│ MP3 + 元数据│
│ (reports/)   │     │  分块+忠实 Prompt│     │  v3-flash │     │ → 阅读 App  │
└─────────────┘     └────────────────┘     └───────────┘     └────────────┘
```

**预估成本**（以一篇 1 万字的报告为例）：
- LLM 改写：Qwen-Plus ~¥0.5 / Qwen-Max ~¥2
- TTS 合成：CosyVoice ~¥1.5（改写后约 1.5 万字）
- **单篇总成本：¥2-4**
- **生成时间：3-5 分钟**
- **输出音频：约 25-35 分钟**

### 5.2 零成本替代方案

如果不想产生 API 费用：

```
Markdown → Qwen（DashScope 免费额度）→ edge-tts（完全免费）→ MP3
```

edge-tts 的中文音色推荐：
- `zh-CN-YunxiNeural`：年轻男声，适合技术讲解
- `zh-CN-XiaoxiaoNeural`：活泼女声，听感自然
- `zh-CN-YunjianNeural`：沉稳男声，适合长文

### 5.3 高质量本地方案（需 GPU）

```
Markdown → 本地 Qwen3-8B → Fish Speech S2（本地 GPU）→ MP3
```

优势：完全离线，无 API 费用，音质最佳。
劣势：需要至少 8GB VRAM 的 GPU。

## 六、导出到阅读软件的实操指南

### 6.1 推荐的"阅读软件"选项

| App | 平台 | 播客支持 | 推荐方式 |
|-----|------|---------|---------|
| **微信读书** | iOS/Android | 支持导入 MP3 | 传到"私人书架"即可 |
| **小宇宙** | iOS/Android | 播客 App | 需要 RSS 或手动导入 |
| **Pocket Casts** | iOS/Android | 支持本地文件 | 直接导入 MP3 |
| **AntennaPod** | Android | 支持本地文件夹 | 指定 MP3 目录 |
| **Apple Podcasts** | iOS | 不支持直接导入 | 需要 iTunes 同步 |
| **Moon FM** | iOS/Android | 支持本地音频 | 直接导入 |

**最简路径**：生成 MP3 → 微信传文件给自己 → 微信读书打开 → 通勤听。

### 6.2 MP3 元数据建议

用 `mutagen` 写入：
```python
from mutagen.mp3 import MP3
from mutagen.id3 import ID3, TIT2, TPE1, TALB

audio = MP3("output.mp3", ID3=ID3)
audio.tags.add(TIT2(encoding=3, text="R30 — RAG 从入门到生产落地"))
audio.tags.add(TPE1(encoding=3, text="AI 研究播客"))
audio.tags.add(TALB(encoding=3, text="Agent 研究知识库"))
audio.save()
```

## 八、开放问题

1. **自动质量校验**：如何自动检测改写后的播客脚本是否丢失了原文关键信息？可能的方案：用 LLM 做"信息覆盖率评分"
2. **语速自适应**：不同内容适合不同语速——概念讲解慢一点，列举数据快一点。当前 TTS 无法按段落调速
3. **章节标记**：长播客需要章节跳转功能（MP3 Chapter markers），P02 尚未支持
4. **批量处理**：80+ 篇报告如何批量转换？需要添加队列管理和错误重试
