## 1. 文档结构拆解

技术方案可采用**五大板块**结构，下图说明各板块的定位：

```
技术方案书
│
├── 更改记录/History ··················· 版本追踪，谁改了什么
│
├── 一、项目概述 ······················· WHY + WHAT
│   ├── 项目背景 ····················· 为什么要做这件事
│   ├── 建设目标 ····················· 做到什么程度算成功
│   ├── 适用范围/Scope ··············· 边界在哪，不做什么
│   ├── 定义和缩略语 ················· 统一术语
│   └── 参考文件 ····················· 前序依赖
│
├── 二、总体架构设计 ··················· HOW（宏观）
│   ├── 技术架构 ····················· 分层设计 + 架构图
│   └── 核心技术方案
│       ├── 技术选型 ················· 选什么、为什么选、评判维度
│       ├── 核心运行机制 ············· 系统怎么跑（含完整流程图）
│       ├── Skill 体系设计 ··········· 可配置能力单元
│       ├── 状态管理 ················· 核心实体的状态机
│       ├── 记忆系统 ················· 上下文管理
│       └── 外部系统集成 ············· 与谁对接、怎么对接
│
├── 三、功能设计 ······················· HOW（微观）——篇幅最大
│   ├── 功能模块 × N ················· 每个模块统一结构：
│   │   ├── 原始需求 ················ 业务方原话
│   │   ├── 痛点与期望 ·············· 现状问题 + 期望效果
│   │   └── 详细技术方案 ············ 步骤分解 + 时序图
│   └── 交互设计 ····················· 输入方式 + 反馈机制
│
├── 四、系统可靠性与安全保障 ··········· 生产级保障
│   ├── 数据安全 ····················· 脱敏/隔离/认证/审计
│   ├── 智能体风险控制 ··············· 人机协作/幻觉控制/注入防御
│   ├── 系统降级策略 ················· 每种故障的降级方案
│   ├── 部署方式 ····················· 组件部署表
│   ├── 高可用与并发 ················· 并发场景 + 针对性设计
│   └── 可观测性与运维 ··············· 基础设施监控 + 智能体监控
│
└── 五、实施规划 ······················· WHEN + HOW MUCH
    └── 阶段安排 + 工作量表格 ········ 按阶段拆任务，估人天
```

**设计哲学**：从 Why（项目概述）→ How-宏观（架构）→ How-微观（功能）→ 保障（可靠性安全）→ When（实施），这是一个符合读者心智模型的自然阅读顺序——先知道为什么做，再看全景，再钻细节，再看风险兜底，最后看计划。

## 2. 各章节内容要素详析

### 2.1 项目概述：定义"做什么"的边界

| 要素 | 组织方法 | 为什么重要 |
|:---|:---|:---|
| **建设目标分级** | 短期目标（部分流程 AI 代替）与长期目标（AI 接管大部分流程）分开写 | 避免"啥都要"的陷阱，给评审方清晰的预期 |
| **Scope 明确** | 写明业务范围、组织范围与不包含的事项 | 防止范围蔓延 |
| **术语表** | 列出非通用缩写、全称与含义 | 读者不用猜 |
| **参考文件引用** | 引用前序业务流程文档 | 建立追溯链 |

### 2.2 总体架构设计：方案的骨架

核心要素清单：

1. **分层描述**（必须有）：每层的名称、职责描述、关键组件
2. **架构图**（必须有）：可使用画板（whiteboard）、Mermaid 或 ASCII Art
3. **技术选型表**（必须有）：四列结构——`技术领域 | 选型 | 选型理由 | 选型维度`。特别注意"选型维度"这一列，它回答了"你按什么标准评判的"，而不只是"你选了什么"
4. **核心运行机制**（必须有）：用一张大流程图 + 文字描述，说清从事件触发到最终输出的完整链路
5. **状态管理**（必须有）：状态枚举 + 流转图 + 触发机制
6. **记忆/上下文系统**（AI 项目必须有）：说明每层的存储介质、内容与生命周期
7. **外部系统集成表**（必须有）：系统名 + 集成方式 + 用途

### 2.3 功能设计：方案的肉

```
功能模块
├── 原始需求 ·········· 用表格/引用呈现业务方原话
│   └── 痛点与期望 ···· 逐条列出
└── 详细技术方案 ······ 编号步骤 + 分支处理 + 时序图
```

**统一结构**是这一章节最大的优点。读者看完第一个模块就知道后面每个模块的展开方式，阅读效率极高。

每个功能模块的技术方案部分，遵循以下叙事结构：

1. **触发机制**：什么事件触发本功能？（Webhook、定时调度、手动触发）
2. **处理步骤**：按编号逐步描述，每步清楚说明输入、处理逻辑、输出
3. **分支处理**：用标题区分不同路径
4. **异常处理**：低置信度怎么办、超时怎么办、信息不全怎么办
5. **输出与流转**：结果写到哪里、通知谁、触发什么下游
6. **时序图**：每个模块必附一张 Mermaid sequenceDiagram

### 2.4 可靠性与安全保障：生产级必备

安全、降级、并发与可观测性应写到可实施的细节，而非只有原则性口号。

### 2.5 实施规划：落地路线图

按阶段拆解工作项，说明内容、工作量与业务方配合事项。

关键设计点：
- **按阶段分优先级**（P0/P1/P2），不是一股脑全列
- **业务方配合事项**列——提醒评审方"你也有活儿"，避免上线时才发现卡在业务方
- **工作量有具体数字**，不是"约 X 人月"的粗估

## 3. 写作手法提炼

### 3.1 表格驱动

技术选型、外部集成、监控指标和工作量估算适合用表格呈现。

**好处**：信息密度高、横向对比容易、不容易漏项。比起用段落文字描述"我们选了 A 因为 B"，表格一行就说清楚了。

### 3.2 时序图标配

每个功能模块必附时序图，不是可选的而是强制的。时序图用来展示参与方之间的交互顺序，尤其适合"多角色 + 多系统"的场景。

### 3.3 原始需求前置

功能设计章节不是上来就写方案，而是先贴业务方的原话。这建立了一条从"用户要什么"到"系统做什么"的追溯链。评审方可以直接对照看：这个方案解决了原始痛点吗？

### 3.4 异常路径不省略

每个功能模块都明确处理了"如果失败怎么办"——低置信度怎么办、信息不全怎么办、超时怎么办、人工转交怎么办。这是区分"demo 级方案"和"生产级方案"的关键分水岭。

### 3.5 先场景后方案

先识别并发场景，再逐项说明设计如何应对该场景。

## 4. 常见遗漏

1. **性能指标基线**：写清当前流程的耗时、质量或成本基线，再给出目标及计算口径。只有提升百分比而无基线，读者无法判断目标的实际意义。

2. **成本估算**：除工作量（人天）外，还应考虑运行成本估算——大模型推理的 Token 成本、基础设施的月度开销。对于决策者来说，"能不能做"和"做得起吗"是两个问题。

3. **测试策略**：可靠性章节除了安全和降级，还应包括测试计划——怎么验证方案正确性？单元测试 / 集成测试 / 端到端测试的策略是什么？

4. **风险清单**：除降级策略外，可增加独立的"技术风险识别"章节——列出 Top N 风险、影响程度、缓解措施、责任人。

## 5. 模板使用指南

完整模板文件已存放于 `wiki/templates/技术方案书模板.md`，使用要点：

### 裁剪规则

| 项目类型 | 必须保留 | 可裁剪 |
|:---|:---|:---|
| AI 智能体项目 | 全部章节 | 无 |
| 传统后端服务 | 一~五全部 | 2.2.3 Skill 体系、2.2.5 记忆系统、4.2 智能体风险控制 |
| 前端/小工具 | 一、三、五 | 二的大部分（保留技术选型）、四的大部分（保留部署方式） |

### 每章必须回答的核心问题

| 章节 | 核心问题 |
|:---|:---|
| 项目概述 | 为什么做？做什么？不做什么？做到什么程度算成功？ |
| 总体架构 | 系统长什么样？技术栈怎么选的？运行时怎么工作？ |
| 功能设计 | 每个功能解决了什么痛点？怎么实现？异常怎么处理？ |
| 可靠性安全 | 出了问题怎么兜底？数据怎么保护？系统怎么监控？ |
| 实施规划 | 分几期做？每期多少工作量？业务方要配合什么？ |

### 质量检查清单

写完方案书后，用以下 checklist 自检：

```
□ 每个技术选型都说了"为什么选这个"？
□ 每个功能模块都有时序图？
□ 每个功能都写了异常/降级处理？
□ 非功能需求（安全/监控/降级/并发）都有独立章节？
□ 实施规划有具体的工作量数字（人天）？
□ 术语表覆盖了所有非通用缩写？
□ 状态流转有清晰的流转图？
□ 文档中没有"后续补充""待定"超过 3 处？（超过说明方案还不成熟）
```
